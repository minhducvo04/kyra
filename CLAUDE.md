# Companion project (Kyra) — Claude Code instructions

An AI companion with persona-driven dialogue, long-term memory (RAG), and voice I/O. Built as a hands-on AI-pipeline learning project, and deliberately run the way a real engineering project is (planning, LLD, implementation, debugging, done for real).

Full design rationale: `docs/design.md`. Setup/usage: `README.md`. Don't duplicate those here — this file is for things you wouldn't get just by reading the code.

## Commands

- Setup: `python3 -m venv .venv && source .venv/bin/activate && pip install -r requirements.txt`
- Text chat: `python3 scripts/chat.py` — defaults to `--backend auto` (the `TurnRouter` decides claude/local/tool per turn). `--backend claude`/`--backend local` forces one backend for the whole session and skips the router entirely.
- Voice chat: `python3 scripts/voice_chat.py` — same `--backend auto|claude|local` (`--mode ptt` for push-to-talk, default is hands-free). Press the interrupt key while she's talking to cut her off (barge-in). Keys default to Enter for both PTT and interrupt, remap via `KYRA_PTT_KEY=space` / `KYRA_INTERRUPT_KEY=esc` (see `companion/keybindings.py`).
- Web UI: `python3 scripts/web_ui.py` → http://127.0.0.1:8420 — a HUD-style browser front end (`web/`). Three-way backend toggle (AUTO/CLAUDE/LOCAL, AUTO is default) in the header, each with its own accent color (violet/cyan/amber); in AUTO mode each Kyra reply shows a small badge with which backend/path actually answered. Same `ConversationManager`/`LLMBackend`/`TurnRouter` underneath, just a third front door alongside `chat.py`/`voice_chat.py`. **Voice now works here too** — a mic button with a PTT/hands-free switch next to the text input (`POST /api/voice`: browser recording → `faster_whisper.audio.decode_audio` → STT → router → TTS → base64 WAV back). Hands-free uses a plain `AnalyserNode` energy-threshold VAD (no external library), paused during playback for the same echo-avoidance reason the CLI is sequential.

- **Stopping a reply is two halves, and the browser is the easy one (2026-09-07)**: `POST /api/chat/cancel`. Aborting the fetch only stops the browser *listening* - the turn keeps running on the server and `ConversationManager._record_turn` files the whole reply into history and Chroma, so Kyra would remember saying something Duc never saw and quote it back next turn. Cancellation rides the `on_token` callback the streaming turn already calls per delta: the webapp's wrapper raises `llm.TurnCancelled`, `AnthropicLLM.respond()` catches it, leaves the stream context (which stops the API generating) and returns what was actually said plus `CANCELLED_MARKER` - the same honesty as `TRUNCATION_MARKER`, so a stopped reply can never read back as one Kyra finished. Each turn owns its own `threading.Event` and `_cancel_current` only points at the newest, so a stop pressed a moment too late sets a signal nobody reads instead of killing the turn that just started. In the UI, SEND becomes STOP while a reply streams and the input stays enabled (saying the next thing stops the current reply, and a voice utterance does too); Escape stops, **not** the space bar the plan first sketched, because an enabled input means a space is a space. Only a streamed text turn can be stopped - a tool turn has no `on_token` and runs to completion, which is what you want once a tool has begun doing something real.
- **Router round 5 (2026-09-08) measured that the retrain was not needed, and qualified the standing rule**: `search_kyra_data` and `set_application_resume` had no training data, so per the rule they got a round - four new categories (tool ×2 plus lookup bait, claude and local), 18 more handwritten held-out cases committed before any data was generated, 1,699/188 rows, two seeds. **The adapter that had never seen either tool already scored 11/13 on the new cases**; round 5 moved that to 12/13, one case. And it is a trade, not a gain: v4-s13 and v5-s13 make exactly five path errors each on 85 cases, with v5 fixing one new case while breaking two advice-bait cases v4 got right ("what does a good STAR answer for Ownership look like", "what does a reposted job usually mean") - the very cases round 4's advice bucket existed for. **Adding categories has a budget.** So the rule "when a tool is added, the adapter has to be retrained" is too strong; the honest version is **measure the current adapter on handwritten cases for the new tool first, and retrain only if it actually fails them**. **Not activated** - `KYRA_CLASSIFIER_ADAPTER` still points at `qwen1.5b-v4-s13`, since path accuracy (the metric that decides whether a tool loop runs at all) is identical at 94.1% and a wash does not justify the two regressions; `qwen1.5b-v5`/`-s13` are on disk and the switch is one line in `.env`. One phrasing no adapter of any round gets right: "what does CLAUDE.md say about the resume token budget" goes to text - it wants its own seeds next round. Numbers and the full trade: `docs/router-finetune.md`, round 5.
- **The MEMORY tab: Duc can finally see what Kyra durably believes about him (2026-09-08)** - a fifth tab in the TOOLS panel over `GET/POST /api/memory-notes` and `POST /api/memory-notes/delete`. Memory notes go into **every** system prompt in full and into every resume draft, and until now the only way to read them was to open `data/memory_notes/*.md` - the same transparency gap the PROFILE tab's "view raw record" closed for the applicant profile, and it matters more here because a true-but-irrelevant note has already become a fabricated resume entry once (2026-09-04). `MarkdownMemoryNotesStore` gained `list_notes()` (the same content `render()` gives the model, as rows) and `delete(category, text)`. **Deletion is a deliberate departure, and a narrow one**: the module docstring's append-only rule is about *code* never silently pruning history to resolve a contradiction, and nothing here resolves anything - it removes exactly the line a human clicked, after a confirm. Removing the last note in a category unlinks the file, or a bare `# heading` would keep going into every prompt as a category with nothing under it. Any new `MemoryNotesStore` implementation must supply both methods; they are on the ABC.

- **Outreach slice 2 (2026-09-08): the JOBS panel's OUTREACH tab, over the same tool objects the chat path uses** - `GET/POST /api/outreach`, plus `/{id}/draft`, `/{id}/copy` and `/{id}/status`, each a `_registry.run(...)` rather than a fresh `OutreachStore` call. That matters because the logic lives in the tools: drafting reads the linked application's status so a note can never claim Duc applied when he is only targeting, and `sent` schedules the follow-up reminder the digest surfaces. Two front doors, one implementation - the same reason `default_tool_registry()` exists after the three front doors really did drift. The one adaptation at the HTTP boundary is the error convention: a tool returns `{"error": ...}` because that is what a model reads, so `_outreach()` turns "no outreach contact with id N" into a 404 and everything else into a 400 rather than answering 200 with an error body. The tab reuses the tracker's item classes, like the TOOLS panel reuses the JOBS panel's; the only new shapes are the note blocks and a 3-line clamp on the role line, because a real outreach `role` often holds a paragraph of context that would otherwise bury every other contact.
- **The dash rule is a post-condition now, not a prompt request (2026-09-08)** - the first real draft through the new tab came back with `cutting deploy times - what turned out to be the bottleneck` *after* the humanizer critique pass had already run, which is exactly the ASCII stand-in CLAUDE.md warns a single pass misses. `outreach.py::has_dash()` catches em-dash, en-dash and a spaced hyphen (a hyphenated word like "new-grad" is not one), and `draft_outreach_note` does one `DEDASH_PROMPT` rewrite after the length check. It never raises - a usable draft with a flagged dash beats no draft - so a dash that survives comes back in `OutreachDraft.warnings`, which the tool returns and the panel prints as an error line. Verified on a real redraft: both note and follow-up clean, the personal angle still used. **If another outbound path grows its own drafting call, it needs this check too**; today only outreach has it.
- **`search_kyra_data` is the chat front door to search, and its safety property is an absence (2026-09-08)**: `SearchKyraDataTool` (`search.py`, registered in `default_tools.py`) has **no `include_sensitive` parameter**. The web panel can reach `data/private_docs/` because Duc ticks a box and watches the result; a chat turn has no such gesture and its far end is the Anthropic API, so the parameter simply does not exist rather than defaulting to False. Asking for the `private` kind is refused, not answered with an empty list, because empty reads as "nothing there" instead of "not yours to read". Two other properties: the index opens on first use, never in `default_tool_registry()` (which runs at startup in all three front doors - the registry still builds in 0.55 s and does not import chromadb), and every result carries the index's last-updated date. Search never reindexes on its own, so **`scripts/daily_digest.py` now reindexes as part of the 05:00 run** - best-effort inside a try/except because the digest is what Duc reads at 05:00 and a failed index must never be why it does not arrive, `--no-reindex` to skip, and `--dry-run` returns before reaching it so previewing stays read-only.
- **A generator that returns nothing must fail, not shrug (2026-09-08)**: `router_ft.generate_synthetic()` retries twice and then raises. `parse_json_array()` returns `[]` for any reply it cannot read, and on the first round-5 run two of four new categories came back `got=0` where the next run gave 60 - a category that silently contributes nothing is exactly how a tool ends up untrained while the run still looks like it worked, which is the gap round 3 existed to close.
- **A wrong reply needs somewhere to go, and it is memory notes not the vector store (2026-09-08)**: the web transcript now persists in `localStorage` (restored on load, forgotten by CLEAR) and every Kyra line carries a ✕ that posts to `POST /api/correction`, saving a `corrections` note. Notes are rendered in full into every system prompt, so a correction is in front of her on the very next turn; a Chroma record would only surface when it happened to be semantically similar to something. Two details that are easy to get wrong: `dataset.raw` keeps the reply apart from the meta/interrupted badges that also live inside `.line-text`, so a restore never reads a badge back in as something she said, and a stopped turn never receives the `done` event that would set it, so `markInterrupted` reads the partial back off the painted text nodes or a restored transcript shows an interruption with nothing before it.
- **The phone layout was broken, not cramped, and the cause was min-content (2026-09-08)**: `.header-controls` held a min-content width of 616px, so at 375px the header and the stage were pushed off *both* edges - wordmark, line tags and the mic button all clipped away - while `overflow-x: hidden` hid the evidence. The fix is `flex-wrap` on the header and the input bar, not more hiding: the previous narrow rule had hidden the PTT/HANDS-FREE toggle to buy room, which is the wrong trade on the one device that is all microphone. When a row does not fit on a phone, wrap it and check `document.documentElement.scrollWidth` against `clientWidth` - a clipped layout looks fine in a screenshot right up until the moment you notice the left edge is missing.
- **`ChromaMemoryStore.add()` dropped a record whose id already existed (found 2026-09-07, FIXED the same day)** - ids came from `str(self._next_id)`, seeded from `count()` at construction, and Chroma ignores a duplicate-id add with no exception and no warning: the record is simply gone and `count()` never moves. Any drift in that counter therefore lost memories with no error anywhere - a second store over the same collection (the web app and a CLI session at once), a store constructed while another was writing, a deleted row moving `count()` backwards. `add()` now writes `uuid.uuid4().hex`. Nothing ever read those ids as numbers, which is why the counter bought nothing: `retrieve()` ranks by the `timestamp` metadata, `search.py::ConversationSource` only echoes the id into a `source_id`, and `migrate_memory_embeddings.py` round-trips whatever it dumps - so existing rows keep their numeric ids, Chroma takes the mixed formats, and **no migration is needed**. The post-condition is `tests/test_memory.py`: a write must be retrievable, covering the two-instances-over-one-collection repro and the reopen-after-a-delete case; both failed red against the counter before the fix, which is the only reason to trust them. Verified past the suite with a real run under real BGE embeddings against a **copy** of the real `data/memory_db` (the original never opened): the repro that used to lose a write keeps all four, the existing numeric-id rows still retrieve, and new uuid rows land beside them. **The real store has a hole in it** - ids 30-37, four exchanges between 09-02 and 09-07, are absent, and Chroma's own write-ahead log (`embeddings_queue`) records ids 30 and 31 added twice, which is this defect's fingerprint. The log also holds DELETEs of 30-37 that nothing in this repo issues (`delete_collection` in the migration script is the only delete in the codebase, and it would take the whole collection, not a range), so the duplicate adds are explained and the deletes are not: treat "is anything else touching this collection" as open, and note the fix cannot undo a delete. **Correction (2026-09-08): the deletes were this session's own cleanup, not an unknown actor.** Ids 30-37 were verification turns made against the running web UI on 2026-09-07 evening and removed afterwards under the standing clean-up-test-pollution rule; the store is contiguous 0-29 and its newest real exchange is dated 2026-09-02, so none of Duc's conversations are missing. The duplicate adds of 30 and 31 are still the defect's real fingerprint - one of those verification turns streamed a reply to the browser, raised nothing and left no record, which is what started this investigation.

## Architecture pattern — preserve this

Every subsystem is a small ABC interface + a swappable concrete backend (Strategy pattern), specifically so that "how would you extend this" always has a clean answer. Existing examples:

- `MemoryStore` → `ChromaMemoryStore` (`src/companion/memory.py`); a separate, second memory layer, `MemoryNotesStore` → `MarkdownMemoryNotesStore` (`src/companion/memory_notes.py`) - see the key decision below, they're not the same thing
- `SpeechToText` → `FasterWhisperSTT`, `TextToSpeech` → `KokoroTTS` (`src/companion/voice.py`)
- `ListenMode` → `PushToTalkListener`, `VoiceActivityListener` (`src/companion/listening.py`)
- `LLMBackend` → `AnthropicLLM`, `LocalLLM` (`src/companion/llm.py`) — `ConversationManager` depends only on `LLMBackend`; `build_llm(backend)` is the factory, `LazyBackends` is a dict-like cache that only constructs a backend the first time it's actually asked for (so a session the router never sends to local doesn't pay local-model load time).
- `Tool` → `AddReminderTool`/`ListRemindersTool`/`CompleteReminderTool`/`SnoozeReminderTool` (`reminders.py`), `TechNewsTool` (`news.py`), `ScienceFactsTool` (`science.py`), `SaveLearningItemTool`/`DueReviewsTool`/`MarkReviewedTool` (`learning.py`), `HandoffTool` (`handoff.py`), `AddJobApplicationTool`/`ListJobApplicationsTool`/`UpdateJobApplicationStatusTool`/`DraftApplicationMaterialTool` (`job_applications.py`), `SaveMemoryNoteTool` (`memory_notes.py`), `AutofillJobApplicationTool` (`job_autofill.py`) (`src/companion/tools.py`) — `name`/`description`/`input_schema`/`run()` map 1:1 onto a Claude tool-use definition, so `ToolRegistry.schemas()` goes straight into `tools=` on a Messages API call with no translation. `default_tools.py::default_tool_registry()` is the one place all fifteen (reminders 4, learning 3, job applications 4, autofill 1, memory notes 1, news 1, science 1) get assembled - `chat.py`/`voice_chat.py`/`webapp.py` all call it instead of constructing `ToolRegistry(...)` separately, so they can't drift out of sync (they briefly did, once, before this factory existed). `news.py` and `science.py` share fetch/parse code via `feeds.py` - add a new RSS-backed tool there too rather than re-implementing the Atom/RSS handling. `job_autofill.py`'s `AutofillEngine` ABC → `GreenhouseAutofillEngine` (Playwright) is the same Strategy shape, ready for a Lever/Workday/iCIMS engine later without touching the tool.
- `TurnRouter` (`src/companion/router.py`) — the design Duc worked through across several sessions, now built and wired into all three front doors. Layered decisions, cheapest/most-certain first: explicit override phrase ("ask claude"/"use local") > sticky session mode (`session_state.py`, file-backed, shared across front doors, focus→claude/chill→local) > a small local classifier (`Llama-3.2-3B-Instruct-4bit`, separate from the conversational `LocalLLM` default) that decides text-vs-tool and, for text, claude-vs-local. The tool path always goes to Claude as the "Agent Specialist" (`AnthropicLLM.respond_with_tools()`, the real Anthropic tool-use loop against a `ToolRegistry`) - local models weren't trusted with structured tool calls per the benchmark. `route_and_answer()`/`route_and_answer_verbose()` in the same module are what a front door actually calls per turn - one function, not reimplemented three times. Every decision is logged (`router_log.py`, JSONL, `data/router.log`) with a reason, whether or not anything went wrong.
- Long, "complex-looking" turns (word-count/multi-ask heuristic, `_looks_complex()`) get biased toward Claude rather than actually decomposed into subtasks - real subtask decomposition/execution was scoped out as a separate, bigger feature (see `docs/agentic-roadmap.md`).

When adding a new subsystem, follow the same shape: a one-or-two-method ABC, a concrete class that does the real work, callers depend only on the interface. Full context for all of the above: `docs/agentic-roadmap.md`.

## Key decisions worth knowing

- **Voice is local/open-source on purpose** (faster-whisper + Kokoro + Silero VAD), not a cloud API like ElevenLabs/OpenAI/Deepgram. Chosen for $0/turn (this gets tested a lot), privacy, and because running real local inference is more of the point of this project than calling someone else's endpoint. The interface boundary makes a cloud backend a future drop-in class, not a rewrite, if a polished demo ever wants one.
- **Voice turn-taking is sequential, with keypress barge-in** (not voice-triggered). `speak_interruptibly()` in `voice_chat.py` plays her reply via `sd.play()` and polls a raw keypress (`companion.keybindings.read_key()`, `termios`/`tty` cbreak mode — not line-buffered `input()`) instead of blocking on `sd.wait()`; the configured interrupt key stops her immediately. Deliberately *not* voice-triggered — the mic would pick up her own TTS through the speakers, and without real echo cancellation that risks her cutting herself off mid-sentence. Full concurrent listen-while-speaking stays a Backlog item; see `docs/design.md`.
- **Keybindings are configurable, not hardcoded** — `companion/keybindings.py`, env vars `KYRA_PTT_KEY`/`KYRA_INTERRUPT_KEY`, default Enter for both (unchanged behavior if you don't touch them). Both `PushToTalkListener` (`listening.py`) and `speak_interruptibly()` (`voice_chat.py`) read a single raw keypress via the same `read_key()` — this needs a real interactive terminal (`sys.stdin.isatty()`); non-tty stdin returns `None` rather than hanging or misfiring (a piped/closed stdin busy-looping here was a real bug caught during testing - see the pty-based tests this was built with).
- **Local LLM choice**: `LocalLLM`'s default is `Qwen2.5-14B-Instruct-4bit` (`llm.py::DEFAULT_LOCAL_MODEL`) — picked from `docs/model-benchmark.md`, not guessed. It's within 0.1 of the benchmark's best local model (Qwen2.5-32B) at more than 2x the tokens/sec, which matters more for voice since replies get read out loud. Local LLM weights live in `data/local_llm_models/` (its own `HF_HOME`, set in `llm.py`) — separate from `scratchpad/bench/`'s throwaway benchmark cache, which is safe to delete anytime and won't break this.
- **Memory embedding is BGE, not Chroma's default** — `memory.py::bge_embedding_function()` (`BAAI/bge-small-en-v1.5`, normalized). Chroma's built-in default is *already* MiniLM-L6 (with a 256-token truncation cap) - swapping to that would have been a no-op improvement, so don't "fix" this back to MiniLM thinking it's an upgrade. `ChromaMemoryStore` also blends in recency (`RECENCY_WEIGHT`/`RECENCY_HALFLIFE_HOURS` class attrs) since casual chat leans on "what we just talked about." **Changing the embedding function again needs `scripts/migrate_memory_embeddings.py` rerun** - old vectors don't get retroactively re-embedded, so a silent swap degrades retrieval on everything stored before the change instead of improving it.
- **Tech news is RSS, not scraping** (`news.py::FEEDS`) — NYT Technology, TechCrunch, Ars Technica, The Verge, Hacker News, all official/free feeds. The Verge's feed is Atom format, not RSS 2.0 - `_parse_feed()` handles both; don't assume every feed uses `<item>`.
- **Claude Code handoff is draft-only, by explicit decision** (`handoff.py::HandoffTool`) — composes a task brief and copies it to the clipboard (`pbcopy`, macOS-only) for Duc to paste into Claude Code himself. It does not execute anything or launch a session. Don't extend this to actually spawn `claude` without checking in first — see `docs/agentic-roadmap.md`, job #1.
- **`AnthropicLLM.respond()` had the same silent-truncation gap `respond_with_tools()` was already fixed for, just never patched** - caught for real when the job-draft web endpoint's critique pass cut a cover letter off mid-word at the old 1500-token budget. `respond()` now checks `stop_reason == "max_tokens"` and appends an explicit `[cut off - ran out of room...]` marker instead of silently returning partial text that reads as complete. This applies to every `respond()` caller, not just job drafting - plain chat at the default 500-token budget could hit this on a long explanation too. The job-draft backend's budget was also bumped 1500 → 2500 (both `default_tools.py` and `webapp.py`) since a style-matched cover letter draft-plus-critique can run long.
- **Tool-calling needs a bigger `max_tokens` budget than plain chat, and this bit us once already**: `AnthropicLLM` has a separate `tool_max_tokens` (2000, vs. 500 for plain `respond()`). Sonnet 5 runs adaptive thinking by default, and thinking tokens count against `max_tokens` - deciding which tool to call burns real budget before any tool_use or text block gets emitted. With the old shared 500-token budget, a real turn got cut off `stop_reason: "max_tokens"` mid-*thinking*, before reaching the tool call, and silently returned an empty reply. `respond_with_tools()` now treats `stop_reason == "max_tokens"` as a real failure (returns an explicit "ran out of room" message) rather than returning whatever `extract_text()` finds (which can legitimately be empty). Don't shrink `tool_max_tokens` back down without re-testing a real tool-calling turn.
- **The router's classifier prompt needs concrete examples, not just a rule description** - a first version without few-shot examples missed "what's the tech news today" as a tool call entirely (correctly understood the *intent* per its own stated reason, wrong `path` field regardless). Adding examples fixed it but initially over-corrected the other way, hallucinating a tool match for "draft a cover letter" (no such tool existed in the registry *at the time*) - fixed with an explicit "only if it matches a listed tool, task-shaped isn't the same as tool-shaped" instruction plus negative examples. **That example is now stale in the opposite direction**: once `draft_application_material` was built (2026-09-03), "draft a cover letter" *should* route to `tool` - the example was updated accordingly, and re-tested against a mixed batch, not just the one case. If you touch `CLASSIFIER_PROMPT` in `router.py`, re-run a mixed batch of tool/text-claude/text-local inputs, not just the one case you're fixing - this class of prompt edit fixes one case and silently breaks another more often than not with small models, and stays stale in the other direction once a new tool is added that changes what "no matching tool" means.
- **Memory is two separate layers on purpose, not one system doing two jobs** (`memory.py`'s `ChromaMemoryStore` vs. `memory_notes.py`'s `MarkdownMemoryNotesStore`). Chroma logs every exchange automatically and retrieves the top-k *semantically similar* ones per turn - good for "what did we just talk about," but a durable fact (a preference, who someone is) can be relevant on an off-topic turn where it's not semantically similar to anything, and top-k retrieval just misses it. Memory Notes is the fix: a small set of facts Claude itself chooses to save (`save_memory_note` tool, never automatic) as dated Markdown bullets in `data/memory_notes/<category>.md`, loaded **in full, every turn** into the system prompt (`ConversationManager._build_system()`) - no query, no top-k, because the set is meant to stay small and curated. Inspired by Mem0's split between curated memory and raw logs, and by the GBrain/Sylph/DIY-Claude-git-markdown pattern Duc researched - human-readable, git-diffable, no vendor lock-in. Temporal handling is deliberately simplified vs. something like Zep/Graphiti's point-in-time graph: append-only dated lines, "most recent wins" is a reading convention, not code that resolves contradictions - documented in the module docstring so nobody "fixes" it into silently dropping history. If `ConversationManager` is constructed without a `memory_notes=` arg it builds its own `MarkdownMemoryNotesStore()`, same pattern as `default_tools.py`'s `draft_backend` - no call-site changes needed at the three front doors.
- **Full resume optimization (`material_type: "full_resume"`) is a separate path from the cover-letter/bullet drafting flow, not a variant of it** - built 2026-09-03 after direct feedback that "resume bullet" mode produced disappointing 2-liners when what was actually wanted was a complete, optimized resume as a real downloadable PDF. `resume_format.py` defines a small line-tagged text contract (`NAME:`/`SECTION:`/`ENTRY`/`HEADING:`/`BULLET:`/...) that's trivial to parse deterministically - chosen over asking the model for Markdown (ambiguous once resume content has its own "#"/inconsistent headers) or JSON (invites subtle parse failures on a long, multi-entry document). `job_applications.py::optimize_full_resume()` is one generation call, no second critique pass (resume bullets are already terse/action-verb-driven, not prose with the chatbot tells the critique pass targets; a second rewrite pass also risks corrupting the strict format). `resume_pdf.py` renders the parsed result to a real PDF via Playwright's `page.pdf()` (already a dependency, no reportlab/weasyprint needed) - a clean, professional, ATS-friendly layout built fresh from the content, not an attempt to recreate the exact typography of whatever PDF Duc originally uploaded (that would mean real PDF-editing work with its own failure modes). `webapp.py`'s `/api/job/resume-pdf/{filename}` serves the generated file - filename is validated (no path separators, must end `.pdf`) before touching the filesystem, since it comes straight from the URL. Two real bugs caught building this: (1) a 3000-token budget silently truncated a full resume mid-document - `optimize_full_resume()` now explicitly checks for `llm.TRUNCATION_MARKER` (a named constant, not a re-typed string) and raises `ResumeFormatError` rather than silently parsing a cut-off document; the actual call site (`webapp.py`'s dedicated `_resume_llm`) uses `max_tokens=6000`. (2) the model initially crammed a Project entry's tech-stack into `HEADING` instead of `SUBHEADING`, squishing the layout - fixed by adding an explicit worked Projects example to the format instructions, plus making the PDF's CSS resilient to long headings regardless (`flex: 1` heading, `flex-shrink: 0` date). Verified end-to-end with Duc's real resume and a real job context, through the actual HTTP endpoints (not just direct calls) - correct PDF downloaded, correct content, no invented facts (spot-checked numbers against the original), path-traversal/invalid-filename/not-found guards all confirmed. Test-generated PDFs cleaned up afterward each time (`data/generated_resumes/` isn't itself gitignored-vs-tracked differently from the rest of `data/`, but generated files there aren't meant to accumulate test noise any more than the other stores are).
- **A real PDF-extraction fidelity finding drove two follow-up features (2026-09-03)**: comparing pypdf's extraction of Duc's real (LaTeX-compiled) resume PDF against the visible content turned up genuine artifacts, not hallucination-prone but real - dropped underscores in inline code (`slack_sdk` extracted as `slack sdk`) and a spurious space inserted before ordinal superscripts (`27th` extracted as `27 th`). Both are characteristic of LaTeX-typeset PDFs specifically (superscript kerning, certain font/ligature encodings) - not a bug in `doc_text.py`, a structural limit of reading text back out of a compiled PDF at all. Two responses, not one: `github_profile.py` adds real supplementary project data (see two bullets below) so a resume draft has more to work with than a single, imperfectly-extracted source; and **`optimize_latex_resume()` (`job_applications.py`) edits Duc's original `.tex` source directly** rather than going anywhere near PDF extraction - `doc_text.py` now treats `.tex` as plain text (no parsing needed, it already is text), and the model is instructed to preserve structure/packages/commands exactly, touch only content, and explicitly keep each rewritten bullet roughly the original length ("this document has a fixed layout... a bullet much longer than before risks overflowing the template when compiled") - a direct response to Duc's own stated worry about alignment breaking on recompile. `material_type: "latex_resume"` is a third top-level path in `webapp.py::job_draft`, sharing a `_pick_resume_source()` helper with `full_resume` (same one-off-upload → selected-library-doc → pasted-text priority) but never touching `resume_pdf.py`. **Superseded by the one-page compile loop directly below** - `optimize_latex_resume()` (reword-in-place, fixed-length-preserving) is still in `job_applications.py` as a lighter-touch building block, but the web UI's `latex_resume` path now calls `optimize_latex_resume_one_page()` instead.
- **LaTeX one-page fitting is a real compile-measure-iterate loop, not a blind rewrite (2026-09-04)** - built after Duc gave direct negative feedback on the generic `full_resume`/`resume_pdf.py` PDF path (2 pages, skills rendered as one flat text blob - confirmed by reading the actual code: `resume_pdf.py` has no page-count target or shrink-to-fit logic at all, and `resume_format.py` explicitly treats a flat skills list as a single bare entry) and said he'd rather hand Kyra his real `.tex` and have her decide what to cut/keep to fit one page per role. The core problem: an LLM editing LaTeX text has no ground truth for whether the result compiles to one or two pages - that depends on font metrics, hyphenation, and package behavior invisible from the source alone. So this doesn't guess: `latex_compile.py` shells out to a real local LaTeX engine (`pdflatex`/`xelatex` - already installed via Homebrew/TeX Live on Duc's machine, no new Python dependency) in a scratch temp dir, reads the real page count back via `pypdf`, and `job_applications.py::optimize_latex_resume_one_page()` loops: generate → compile → if not exactly 1 page, feed the real page count back and ask for another cut (favor dropping a whole entry - an older project, a course, a weak bullet - over shrinking margins/fonts, which the prompt explicitly forbids touching) → recompile, bounded to `max_attempts` (default 4). A compile failure (bad LaTeX syntax from the model's own edit) gets its error log fed back for a fix-only pass rather than silently failing - `_extract_error_context()` pulls the actual `! ...` error block out of the `.log`, not just a blind tail, since real templates can bury the error thousands of lines into package-loading noise. Runs **fully automatically** (Duc's explicit choice over a propose-then-approve step) and picks the LaTeX engine automatically via `detect_engine()` (xelatex if the source uses `fontspec`/`setmainfont`/`polyglossia`/`unicode-math`, pdflatex otherwise) - also Duc's choice. On giving up without reaching one page, returns the closest real compiled attempt (fewest pages actually seen), never a document that was never compiled. `webapp.py::_latex_resume_draft` now returns both the edited LaTeX text *and* a compiled PDF preview (`pdf_url`, served through the same `/api/job/resume-pdf/{filename}` endpoint as `full_resume`) so Duc sees the real rendered result, not just trusts the source. Verified end-to-end with a real Claude call + real local compile on a synthetic 2-page resume (correctly cut to 1 page, correctly wove in a supplied "new coursework" fact, invented nothing) and again through the actual running HTTP endpoint (`curl` → real draft → real served PDF, inspected visually) - not just unit-tested in isolation. One real bug caught before it ever reached the live path: the initial `compile_latex()` had a leftover reference to an already-removed `log_tail` variable on the success return, which would have thrown on every single successful compile - caught by actually running the function, not by code review.
- **The one-page fit loop was rebuilt around a measured overflow signal (2026-09-04, evening audit)** after Duc's direct feedback that a resume still came back as 2 pages. Root cause wasn't the model: the loop only knew the *page count* (binary), never compiled the original for a baseline, and the shrink prompt asked for "the single least-relevant bullet" - so a large overflow never converged in 4 attempts, and a one-page original could come back longer with no budget telling the model not to grow it. Now: `latex_compile.measure_pages()` counts text lines per page from the real PDF (`PageMeasure`, `CompileResult.overflow_lines`); `optimize_latex_resume_one_page()` compiles the original first and puts a measured length budget in the first prompt, feeds "page 1 holds ~N lines, M spilled - remove at least K lines' worth" with an escalating margin into each shrink pass, picks the best candidate by (pages, overflow) not pages alone, and defaults to 5 attempts. `resume_guard.py` runs after every resume generation (Fast, Detailed, and the hidden `full_resume`) and flags any number/year/%/link in the output that isn't in the sources the model was given - the structural answer to the fabricated-entry bug two bullets down, since a prompt can't guarantee anything. `DraftOut`/`ResumeFitGenerateOut` now carry `fit`/`page_count`/`overflow_lines`/`notes` and the UI renders a red "✗ Not one page" / green "✓ Fits one page" banner plus a collapsible attempt log - a violated hard requirement must never look like success. Verified with a real Claude call on Duc's real resume + a realistic SDE posting: fit on attempt 1, guard clean, no `\resumeSubheading` added or removed. Full before/after/why in `docs/industry-standards.md`; open choices (touch layout as a last resort? make the guard blocking?) in `data/private_docs/needs-your-input.md`.
- **Resume-generation paths (`full_resume`/`latex_resume`) had a real gap: neither one looked at Memory Notes or free-text library documents at all (fixed 2026-09-04)** - Duc asked directly whether he could update resume generation "by words" (e.g. "I graduated," "I took these new classes") the way the plain chat/draft flow already lets him via `save_memory_note`. Checking the code confirmed a real gap: the plain paragraph-drafting path in `webapp.py::job_draft` already pulled in `_memory_notes.render()` and selected non-resume library documents, but `_full_resume_draft`/`_latex_resume_draft` never did - a fact saved via chat would silently never reach resume generation. - **The Memory Notes wiring above had a real, more serious follow-on bug: it fabricated a whole new resume entry (fixed same day, 2026-09-04)** - the very first real run against Duc's actual resume + a real job posting added a brand-new "Kyra | AI companion project..." ## Session workflow (this repo)

Global principles and the session-end line live in `~/.claude/CLAUDE.md`; this is the per-repo half
(`docs/templates/PROJECT-WORKFLOW.md` is the portable source for both).

1. **Plan** (Opus 5 / high): restate the goal, ask up to 5 clarifying questions, write `docs/plans/<date>-<topic>.md`
   with `[step] -> verify: [check]` lines.
2. **Build** (Sonnet 5 / medium): one plan section per session; tests first for any hard constraint.
3. **Verify**: a real run, not just `pytest` - real Claude call, real `pdflatex`, real browser.
4. **Record**: a key-decision bullet above (the *why*), an `industry-standards.md` row if a standard changed, a
   `needs-your-input.md` entry for anything that needs Duc.
5. **Close**: `ruff check` + `pytest` green, commit with what was verified.

| Task | Model | Effort |
|---|---|---|
| Design, audits, hard debugging, prompt work needing real-run verification | Opus 5 | high |
| Implementing a specified feature, wiring, docs, refactors covered by tests | Sonnet 5 | medium |
| Trivial edits, questions answerable from one file | Sonnet 5 | low |

## Working practices

- **Anything that leaves this machine for a human reader ALWAYS goes through the humanizer pass, no exceptions** (Duc's standing rule, 2026-09-07, after he caught an em-dash in material handed to him). "Outbound" means a resume, a cover letter, a job-application form answer, an outreach note, an email - and it also means *the surrounding text you hand him with it*: the file header, the summary block, the pasteable snippet in chat. The gap he caught was exactly there: the answer body had gone through `CRITIQUE_PROMPT` and was clean, while the header written by hand above it was not, and carried the em-dash. So the rule is per-artifact, not per-LLM-call - if a human other than Duc could read it, it gets the pass.
  - Run the real `job_applications.CRITIQUE_PROMPT` through a real call. Do not hand-wave "I wrote it carefully."
  - **Never an em-dash or en-dash (—, –) in outbound text, and never a spaced hyphen standing in for one** (`x - y`). `CRITIQUE_PROMPT` lists em-dashes but a single pass does not always catch the ASCII stand-in: on a take-home answer, pass 1 left `isn't one-off - it recurs` and pass 2 fixed it to `isn't a one-time gain, it recurs`. When the text is short and final, run the pass twice and diff; adopt pass 2 only where it actually improved something, since a second pass on clean text can flatten voice (see the `writing_voice` memory note).
  - **The pass is not a fact-checker, and it introduces errors of its own.** Re-verify after it, every time. Two real cases on that take-home submission: it wrote that the fabrication validator checks "against the source article" when it checks against source *documents*, and it added "run a pipeline like this against real feeds **for weeks**" when the digest was days old. Both read fluently and both were false. Check every number against sources, and reject any duration, scale, headcount or business-outcome claim the source text did not contain.
  - Check the artifact mechanically before sending, not by eye: numbers diffed against sources, no dash characters, no invented scale/duration, no greeting/sign-off on a form field, no `llm.TRUNCATION_MARKER`. A truncated draft silently poisons the pass - a 325-word answer hit a 3,000-token ceiling and the critique step then "reviewed" a stub and replied asking for the text again.
- **The repo lives at `~/Projects/kyra` (moved there 2026-09-07 from `~/Downloads/Personal assistant`), and moving it again means fixing seven things a `mv` does not.** Out of `Downloads` because that folder gets cleaned out, and no space in the name because a space needs quoting in every shell command and percent-encoding in every `file://` URI. What holds the absolute path, in the order that bites: `.venv` (`pyvenv.cfg`, `bin/activate*`, every `bin/*` shebang - patch them with `sed` on the same machine, or rebuild); `~/Library/LaunchAgents/com.kyra.daily-digest.plist` **and** its tracked copy in `deploy/` (five paths each, and a stale one fails the 05:00 digest silently); `.env`'s `KYRA_CLASSIFIER_ADAPTER` (a stale path makes `router.py` fall back to the few-shot 3B with no error - the one failure here that looks like nothing happened); `data/applicant_profile.json`'s `resume_path`; the `resume_path` column in **every** `data/*.db`, not just `job_applications.db`, since each store keeps its own file; registered git worktrees (`git worktree repair` from the new location); and `~/.claude/projects/<path-slug>/`, which is where session history and memory live - the slug is derived from the path, so skipping it silently orphans both. Verify with `pytest`, `ruff`, `daily_digest.py --dry-run`, and a real `launchctl kickstart -k gui/$(id -u)/com.kyra.daily-digest` rather than waiting for 05:00.
- **Never `cat`, `diff`, or otherwise print the full contents of `.env`.** It holds a live Anthropic API key. Two earlier sessions accidentally leaked a real key into a conversation this way (both keys were revoked after). For diagnostics, check only length/prefix/whitespace, like `scripts/debug_api_key.py` does.
- Model files and local databases (`data/`, including `data/voice_models/`) are gitignored on purpose — don't commit them, don't remove them from `.gitignore`.
- `git` identity for this repo is set locally (not global) to Minh Duc Vo / a private address — that's deliberate, leave it repo-local.
- Job-search and interview-prep working docs live under `data/private_docs/` (gitignored), not in this repo's tracked docs.
- **The "clean up test pollution" discipline covers `data/router.log` too, not just the DB stores** — a gap found 2026-09-03 while building `analyze_patterns.py`: classifier re-test scripts (`router.route(msg)` in scratchpad harnesses) log to the real `data/router.log` exactly like production does, and this had gone unnoticed across several classifier-prompt-edit sessions, leaving 193 lines of pure test noise (caught only because a pattern-analysis tool would have treated it as real usage). After any classifier re-test batch, check `data/router.log`'s recent entries the same way you'd check `data/*.db` - don't assume only the databases need this.
