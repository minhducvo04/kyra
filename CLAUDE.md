# Companion project (Kyra) — Claude Code instructions

An AI companion with persona-driven dialogue, long-term memory (RAG), and voice I/O. Built as a hands-on AI-pipeline learning project, alongside prep for a final-round interview — the project *is* the interview practice (planning, LLD, implementation, debugging, done for real).

Full design rationale: `docs/design.md`. Setup/usage: `README.md`. Don't duplicate those here — this file is for things you wouldn't get just by reading the code.

## Commands

- Setup: `python3 -m venv .venv && source .venv/bin/activate && pip install -r requirements.txt`
- Text chat: `python3 scripts/chat.py` — defaults to `--backend auto` (the `TurnRouter` decides claude/local/tool per turn). `--backend claude`/`--backend local` forces one backend for the whole session and skips the router entirely.
- Voice chat: `python3 scripts/voice_chat.py` — same `--backend auto|claude|local` (`--mode ptt` for push-to-talk, default is hands-free). Press the interrupt key while she's talking to cut her off (barge-in). Keys default to Enter for both PTT and interrupt, remap via `KYRA_PTT_KEY=space` / `KYRA_INTERRUPT_KEY=esc` (see `companion/keybindings.py`).
- Web UI: `python3 scripts/web_ui.py` → http://127.0.0.1:8420 — a HUD-style browser front end (`web/`). Three-way backend toggle (AUTO/CLAUDE/LOCAL, AUTO is default) in the header, each with its own accent color (violet/cyan/amber); in AUTO mode each Kyra reply shows a small badge with which backend/path actually answered. Same `ConversationManager`/`LLMBackend`/`TurnRouter` underneath, just a third front door alongside `chat.py`/`voice_chat.py`. **Voice now works here too** — a mic button with a PTT/hands-free switch next to the text input (`POST /api/voice`: browser recording → `faster_whisper.audio.decode_audio` → STT → router → TTS → base64 WAV back). Hands-free uses a plain `AnalyserNode` energy-threshold VAD (no external library), paused during playback for the same echo-avoidance reason the CLI is sequential.
- In auto mode on any front door: say "focus mode" / "chill mode" / "auto mode" to change the sticky session mode, or "ask claude" / "use local" in one message to override just that turn.
- Book summarization: `python3 scripts/summarize_book.py path/to/book.pdf` (or `.epub`) — reads a book you already have, saves a structured summary into the spaced-repetition learning store. Standalone script on purpose, not a conversational tool — see `docs/agentic-roadmap.md`, job #7.
- Voice model download (one-time): `python3 scripts/setup_voice_models.py`
- Voice sanity check, no mic needed: `python3 scripts/test_voice_roundtrip.py`
- API key sanity check: `python3 scripts/smoke_test.py`, or `python3 scripts/debug_api_key.py` for a detailed error if it fails
- Memory embedding migration (one-time, already run): `python3 scripts/migrate_memory_embeddings.py` — re-embeds `data/memory_db` under the BGE embedding function. Safe/idempotent to rerun; only does anything if the collection is non-empty.
- No test suite yet (no pytest). Verification so far has been targeted scripts like the ones above, plus real-pty tests (see `scratchpad/` patterns) for anything that reads raw keypresses — piped stdin doesn't exercise `termios`/`tty` cbreak mode, a real pty does. If you add real tests, use pytest under `tests/`.
- Scripts import via `sys.path.insert(0, ".../src")` rather than an editable install — keeps setup to plain `pip install -r requirements.txt`, no build step. Follow the same pattern in new scripts.

## Architecture pattern — preserve this

Every subsystem is a small ABC interface + a swappable concrete backend (Strategy pattern), specifically because this project doubles as interview practice — "how would you extend this" should always have a clean answer. Existing examples:

- `MemoryStore` → `ChromaMemoryStore` (`src/companion/memory.py`)
- `SpeechToText` → `FasterWhisperSTT`, `TextToSpeech` → `KokoroTTS` (`src/companion/voice.py`)
- `ListenMode` → `PushToTalkListener`, `VoiceActivityListener` (`src/companion/listening.py`)
- `LLMBackend` → `AnthropicLLM`, `LocalLLM` (`src/companion/llm.py`) — `ConversationManager` depends only on `LLMBackend`; `build_llm(backend)` is the factory, `LazyBackends` is a dict-like cache that only constructs a backend the first time it's actually asked for (so a session the router never sends to local doesn't pay local-model load time).
- `Tool` → `AddReminderTool`/`ListRemindersTool`/`CompleteReminderTool`/`SnoozeReminderTool` (`reminders.py`), `TechNewsTool` (`news.py`), `ScienceFactsTool` (`science.py`), `SaveLearningItemTool`/`DueReviewsTool`/`MarkReviewedTool` (`learning.py`), `HandoffTool` (`handoff.py`), `AddJobApplicationTool`/`ListJobApplicationsTool`/`UpdateJobApplicationStatusTool`/`DraftApplicationMaterialTool` (`job_applications.py`) (`src/companion/tools.py`) — `name`/`description`/`input_schema`/`run()` map 1:1 onto a Claude tool-use definition, so `ToolRegistry.schemas()` goes straight into `tools=` on a Messages API call with no translation. `default_tools.py::default_tool_registry()` is the one place all thirteen (reminders 4, learning 3, job applications 4, news 1, science 1) get assembled - `chat.py`/`voice_chat.py`/`webapp.py` all call it instead of constructing `ToolRegistry(...)` separately, so they can't drift out of sync (they briefly did, once, before this factory existed). `news.py` and `science.py` share fetch/parse code via `feeds.py` - add a new RSS-backed tool there too rather than re-implementing the Atom/RSS handling.
- `TurnRouter` (`src/companion/router.py`) — the design Duc worked through across several sessions, now built and wired into all three front doors. Layered decisions, cheapest/most-certain first: explicit override phrase ("ask claude"/"use local") > sticky session mode (`session_state.py`, file-backed, shared across front doors, focus→claude/chill→local) > a small local classifier (`Llama-3.2-3B-Instruct-4bit`, separate from the conversational `LocalLLM` default) that decides text-vs-tool and, for text, claude-vs-local. The tool path always goes to Claude as the "Agent Specialist" (`AnthropicLLM.respond_with_tools()`, the real Anthropic tool-use loop against a `ToolRegistry`) - local models weren't trusted with structured tool calls per the benchmark. `route_and_answer()`/`route_and_answer_verbose()` in the same module are what a front door actually calls per turn - one function, not reimplemented three times. Every decision is logged (`router_log.py`, JSONL, `data/router.log`) with a reason, whether or not anything went wrong.
- Long, "complex-looking" turns (word-count/multi-ask heuristic, `_looks_complex()`) get biased toward Claude rather than actually decomposed into subtasks - real subtask decomposition/execution was scoped out as a separate, bigger feature (see `docs/agentic-roadmap.md`).

When adding a new subsystem, follow the same shape: a one-or-two-method ABC, a concrete class that does the real work, callers depend only on the interface. Full context for all of the above: `docs/agentic-roadmap.md`.

## Key decisions worth knowing

- **Voice is local/open-source on purpose** (faster-whisper + Kokoro + Silero VAD), not a cloud API like ElevenLabs/OpenAI/Deepgram. Chosen for $0/turn (this gets tested a lot), privacy, and because running real local inference is more of the point of this project than calling someone else's endpoint. The interface boundary makes a cloud backend a future drop-in class, not a rewrite, if a polished demo ever wants one.
- **Voice turn-taking is sequential, with keypress barge-in** (not voice-triggered). `speak_interruptibly()` in `voice_chat.py` plays her reply via `sd.play()` and polls a raw keypress (`companion.keybindings.read_key()`, `termios`/`tty` cbreak mode — not line-buffered `input()`) instead of blocking on `sd.wait()`; the configured interrupt key stops her immediately. Deliberately *not* voice-triggered — the mic would pick up her own TTS through the speakers, and without real echo cancellation that risks her cutting herself off mid-sentence. Full concurrent listen-while-speaking stays a Backlog item; see `docs/design.md`.
- **Keybindings are configurable, not hardcoded** — `companion/keybindings.py`, env vars `KYRA_PTT_KEY`/`KYRA_INTERRUPT_KEY`, default Enter for both (unchanged behavior if you don't touch them). Both `PushToTalkListener` (`listening.py`) and `speak_interruptibly()` (`voice_chat.py`) read a single raw keypress via the same `read_key()` — this needs a real interactive terminal (`sys.stdin.isatty()`); non-tty stdin returns `None` rather than hanging or misfiring (a piped/closed stdin busy-looping here was a real bug caught during testing - see the pty-based tests this was built with).
- **Local LLM choice**: `LocalLLM`'s default is `Qwen2.5-14B-Instruct-4bit` (`llm.py::DEFAULT_LOCAL_MODEL`) — picked from `docs/model-benchmark.md`, not guessed. It's within 0.1 of the benchmark's best local model (Qwen2.5-32B) at more than 2x the tokens/sec, which matters more for voice since replies get read out loud. Local LLM weights live in `data/local_llm_models/` (its own `HF_HOME`, set in `llm.py`) — separate from `scratchpad/bench/`'s throwaway benchmark cache, which is safe to delete anytime and won't break this.
- **Memory embedding is BGE, not Chroma's default** — `memory.py::bge_embedding_function()` (`BAAI/bge-small-en-v1.5`, normalized). Chroma's built-in default is *already* MiniLM-L6 (with a 256-token truncation cap) - swapping to that would have been a no-op improvement, so don't "fix" this back to MiniLM thinking it's an upgrade. `ChromaMemoryStore` also blends in recency (`RECENCY_WEIGHT`/`RECENCY_HALFLIFE_HOURS` class attrs) since casual chat leans on "what we just talked about." **Changing the embedding function again needs `scripts/migrate_memory_embeddings.py` rerun** - old vectors don't get retroactively re-embedded, so a silent swap degrades retrieval on everything stored before the change instead of improving it.
- **Tech news is RSS, not scraping** (`news.py::FEEDS`) — NYT Technology, TechCrunch, Ars Technica, The Verge, Hacker News, all official/free feeds. The Verge's feed is Atom format, not RSS 2.0 - `_parse_feed()` handles both; don't assume every feed uses `<item>`.
- **Claude Code handoff is draft-only, by explicit decision** (`handoff.py::HandoffTool`) — composes a task brief and copies it to the clipboard (`pbcopy`, macOS-only) for Duc to paste into Claude Code himself. It does not execute anything or launch a session. Don't extend this to actually spawn `claude` without checking in first — see `docs/agentic-roadmap.md`, job #1.
- **Tool-calling needs a bigger `max_tokens` budget than plain chat, and this bit us once already**: `AnthropicLLM` has a separate `tool_max_tokens` (2000, vs. 500 for plain `respond()`). Sonnet 5 runs adaptive thinking by default, and thinking tokens count against `max_tokens` - deciding which tool to call burns real budget before any tool_use or text block gets emitted. With the old shared 500-token budget, a real turn got cut off `stop_reason: "max_tokens"` mid-*thinking*, before reaching the tool call, and silently returned an empty reply. `respond_with_tools()` now treats `stop_reason == "max_tokens"` as a real failure (returns an explicit "ran out of room" message) rather than returning whatever `extract_text()` finds (which can legitimately be empty). Don't shrink `tool_max_tokens` back down without re-testing a real tool-calling turn.
- **The router's classifier prompt needs concrete examples, not just a rule description** - a first version without few-shot examples missed "what's the tech news today" as a tool call entirely (correctly understood the *intent* per its own stated reason, wrong `path` field regardless). Adding examples fixed it but initially over-corrected the other way, hallucinating a tool match for "draft a cover letter" (no such tool existed in the registry *at the time*) - fixed with an explicit "only if it matches a listed tool, task-shaped isn't the same as tool-shaped" instruction plus negative examples. **That example is now stale in the opposite direction**: once `draft_application_material` was built (2026-09-03), "draft a cover letter" *should* route to `tool` - the example was updated accordingly, and re-tested against a mixed batch, not just the one case. If you touch `CLASSIFIER_PROMPT` in `router.py`, re-run a mixed batch of tool/text-claude/text-local inputs, not just the one case you're fixing - this class of prompt edit fixes one case and silently breaks another more often than not with small models, and stays stale in the other direction once a new tool is added that changes what "no matching tool" means.
- **Job application drafting uses a two-pass generate-then-critique technique, not a single prompt** (`job_applications.py::DraftApplicationMaterialTool`) - draft, then a separate pass that rewrites the draft against a checklist of known AI-writing tells (overused words like "delve"/"boasts", rule-of-three lists, forced parallelism, hedging), never introducing new facts. Same core idea as [github.com/blader/humanizer](https://github.com/blader/humanizer), which Duc surfaced from his own research and pointed this build at. The critique pass is explicitly bound to the same no-invention rule as the draft pass - a name/number/date/claim has to trace back to what Duc actually gave it. Uses a dedicated `AnthropicLLM(max_tokens=1500)` instance (see `default_tools.py::default_tool_registry(draft_backend=...)`) - the same tool-calling token-budget lesson two bullets up applies here: a draft plus a critique pass needs real room. The tracker/draft hard boundary (no auto-fill, no auto-submit, ever) lives in the module docstring and `docs/agentic-roadmap.md` job #4 - don't extend this tool toward actually submitting anything without checking in first.
- **The classifier only ever sees the current message, never conversation history** - a known, real limitation, not yet fixed. Context-dependent turns ("yeah I remembered that one" following Kyra asking about a review) misclassify because the classifier has no way to know what it's a reply to. Adding history would fix it but costs more tokens/latency on every single turn for a case that's relatively rare - not worth it unless it turns out to matter in practice.
- **`CLASSIFIER_MODEL` (`Llama-3.2-3B-Instruct-4bit`) is empirically justified, not just the original untested pick** - see `docs/router-model-benchmark.md`. Benchmarked against 3 smaller candidates; 3B wins on accuracy (96.6%) after a real prompt bug the benchmark caught got fixed (see `CLASSIFIER_PROMPT` two entries up). Qwen2.5-1.5B is a documented, real fallback if classifier latency ever matters more than its ~10pp accuracy gap - a one-line change, not a redesign. Separately, local models (Qwen2.5-7B+) were flawless at the Agent Specialist's job (tool selection + arguments) on an 11-case suite - promising, but the suite's small and the Agent Specialist role stays Claude's until a harder suite backs a change. Also found: Qwen/Llama/Mistral each render function-calling in a different, incompatible format from their chat templates - a real cost of ever moving tool-calling local that a single Claude API sidesteps.
- **Silero VAD requires exactly 512-sample chunks at 16kHz** (`VoiceActivityListener.CHUNK_SAMPLES` in `listening.py`) — it raises "Input audio chunk is too short" on anything else. Don't change this constant without re-verifying against the installed silero-vad version.
- **Sample rate contract**: `SpeechToText.transcribe()` always expects mono float32 audio at 16kHz (`companion.voice.SAMPLE_RATE`). Kokoro's TTS output is 24kHz — resample before feeding it back into STT (see `test_voice_roundtrip.py`'s `resample()` for the pattern used so far).
- **`ConversationManager._build_system()` includes the current local date/time, and this was a real, user-visible bug before it did**: a reminder tool call landed a due date over a year in the past because nothing ever told the model what day "today" is - "tomorrow morning" is meaningless without it. Local time (`datetime.now().astimezone()`), not UTC, so "tomorrow" means Duc's tomorrow. This affects every turn, not just tool calls - don't remove it to save a few tokens.
- **Browser audio format decoding reuses faster-whisper's own utility** (`companion.voice.decode_uploaded_audio` → `faster_whisper.audio.decode_audio`, which bundles PyAV/ffmpeg) instead of adding a new audio-decoding dependency - handles whatever `MediaRecorder` produces (webm/opus, etc.) without the web UI needing to know or care about the exact format.
- **The web UI's hands-free voice is a plain energy-threshold VAD** (`AnalyserNode.getByteTimeDomainData`, RMS against a fixed threshold, in `web/app.js`), not Silero like the CLI - no external JS library, good enough for a first version, may need real threshold tuning once actually used with real background noise. Paused during TTS playback for the same echo-avoidance reason `voice_chat.py` is sequential - don't remove that guard to make it feel more "always on."

## Verified vs. not (as of 2026-09-02 — update this section as things get confirmed)

Built and verified end-to-end, on Duc's real M5 Max: text chat on **both backends** (`chat.py --backend claude` and `--backend local`, multi-turn, memory recalled across sessions), `KokoroTTS` synthesis, live `faster-whisper` transcription (`test_voice_roundtrip.py`, real TTS→STT roundtrip), `VoiceActivityListener`'s VAD scoring on synthetic chunks. The web UI (`scripts/web_ui.py`) end-to-end through both backends, including the live backend-switch, via real browser interaction.

**Keypress mechanisms (barge-in, configurable PTT/interrupt keys) are verified with real ptys**, not just piped stdin — piped stdin can't exercise `termios`/`tty` cbreak mode, so a real `pty.openpty()` + forked child was used to actually send raw keystrokes and check the response (see `scratchpad/test_bargein_pty.py` / `test_ptt_pty.py` patterns if you need to re-verify this class of thing later). Confirmed: custom keys work (not just Enter), wrong keys are correctly ignored, non-interactive stdin doesn't hang or false-trigger.

**The `TurnRouter` is built, wired into all three front doors, and verified with real calls** - not a mock or a dry run. Verified specifically: override phrases route correctly; session mode (focus/chill) forces the right backend; the classifier correctly separates tool-path from text-path and picks claude-vs-local sensibly (9/10 on a mixed test batch across all 9 tools - the one miss is the documented context-dependent-phrase limitation above, not a prompt bug); the complexity heuristic biases long/multi-part input to Claude; a real multi-turn tool-calling session through `chat.py` genuinely added and recalled a reminder and fetched live tech news; a real Claude tool-call session correctly summarized the CAP theorem and saved it with spaced repetition, and fetched real science headlines; the same flows verified again through the actual running web UI via real browser interaction (screenshots, not just curl). `route_and_answer()` also wraps `handle_mode_command()`, so "focus mode"/"chill mode"/"auto mode" work as spoken/typed commands, not just by editing `data/session_state.json` by hand.

**`scripts/voice_chat.py` has now been run with a real human voice** (2026-09-02, Duc, hands-free/VAD mode) - real mic captured speech, real transcription, real spoken reply. The full loop (mic → VAD → STT → LLM → TTS → speaker) is confirmed working end to end, not just independently-verified pieces.

**Voice in the web UI (`POST /api/voice`, PTT + hands-free) is backend-verified but not mic-verified.** The full pipeline was proven with a real Kokoro-synthesized clip round-tripped through the actual endpoint (accurate transcript, correct tool routing, real reminder added, valid WAV reply) - but actual browser microphone capture couldn't be exercised from here: the automated browser pane explicitly blocks `getUserMedia` (confirmed directly - it rejects with `NotAllowedError` when called from devtools, and silently never resolves when triggered by an actual page click, which is why a failed mic click currently shows no error line in the transcript - not yet root-caused, needs checking in Duc's real browser where the promise should genuinely reject). This is the next thing to verify with a human, same category as the CLI was until today.

## Working practices

- **Never `cat`, `diff`, or otherwise print the full contents of `.env`.** It holds a live Anthropic API key. Two earlier sessions accidentally leaked a real key into a conversation this way (both keys were revoked after). For diagnostics, check only length/prefix/whitespace, like `scripts/debug_api_key.py` does.
- Model files and local databases (`data/`, including `data/voice_models/`) are gitignored on purpose — don't commit them, don't remove them from `.gitignore`.
- `git` identity for this repo is set locally (not global) to Minh Duc Vo / a private address — that's deliberate, leave it repo-local.
- This project also has job-search working docs under data/private_docs/ (gitignored).
