# Companion project (Kyra) — Claude Code instructions

An AI companion with persona-driven dialogue, long-term memory (RAG), and voice I/O. Built as a hands-on AI-pipeline learning project, alongside prep for a final-round interview — the project *is* the interview practice (planning, LLD, implementation, debugging, done for real).

Full design rationale: `docs/design.md`. Setup/usage: `README.md`. Don't duplicate those here — this file is for things you wouldn't get just by reading the code.

## Commands

- Setup: `python3 -m venv .venv && source .venv/bin/activate && pip install -r requirements.txt`
- Text chat: `python3 scripts/chat.py` — defaults to `--backend auto` (the `TurnRouter` decides claude/local/tool per turn). `--backend claude`/`--backend local` forces one backend for the whole session and skips the router entirely.
- Voice chat: `python3 scripts/voice_chat.py` — same `--backend auto|claude|local` (`--mode ptt` for push-to-talk, default is hands-free). Press the interrupt key while she's talking to cut her off (barge-in). Keys default to Enter for both PTT and interrupt, remap via `KYRA_PTT_KEY=space` / `KYRA_INTERRUPT_KEY=esc` (see `companion/keybindings.py`).
- Web UI: `python3 scripts/web_ui.py` → http://127.0.0.1:8420 — a HUD-style browser front end (`web/`). Three-way backend toggle (AUTO/CLAUDE/LOCAL, AUTO is default) in the header, each with its own accent color (violet/cyan/amber); in AUTO mode each Kyra reply shows a small badge with which backend/path actually answered. Same `ConversationManager`/`LLMBackend`/`TurnRouter` underneath, just a third front door alongside `chat.py`/`voice_chat.py`. **Voice now works here too** — a mic button with a PTT/hands-free switch next to the text input (`POST /api/voice`: browser recording → `faster_whisper.audio.decode_audio` → STT → router → TTS → base64 WAV back). Hands-free uses a plain `AnalyserNode` energy-threshold VAD (no external library), paused during playback for the same echo-avoidance reason the CLI is sequential.
- **JOBS panel** (2026-09-03, extended same day) — a slide-in panel (JOBS button, top right) with four tabs, hitting dedicated endpoints directly rather than the chat/router path (a UI button already knows what it wants, no intent to classify):
  - **Draft** — material type, job posting or blank for "ideal role in general", checkboxes to pull background from saved library documents, a style-sample document picker, plus a quick one-off-upload fallback (`webapp.py::job_draft`). Every draft's background also automatically includes whatever Kyra already durably knows about Duc via `memory_notes.py` - the draft tool and general chat now draw on the same "known facts" layer instead of being isolated from each other.
  - **Profile** (new) — an editable form for `profile.py::ApplicantProfile` (name/contact/links/EEO), a **document library** (`job_documents.py::JobDocumentStore` - multiple resumes, style samples, and free-text notes, persisted across sessions instead of the old one-shot-per-draft upload), and a **"View raw record" transparency toggle** showing the exact JSON that autofill/drafting will use - Duc asked for this explicitly, not a nice-to-have.
  - **Tracker** — add/list/change-status, live against the real `job_applications.db`.
  - **Autofill** — URL in, fill-only run against `GreenhouseAutofillEngine`, same fill-never-submit boundary as the chat tool.
  Built fast/functional per Duc's explicit ask ("no need to be nice... we can tweak it later") - not a polish pass, the HUD styling is minimal-but-consistent with the existing token set, not a redesign. One real HTML bug caught building this: a placeholder attribute used backslash-escaped quotes (`\"...\"`), which isn't valid HTML attribute escaping (needs `&quot;` or just avoiding the inner quotes) - the browser silently truncated the placeholder at the first backslash. Caught via a real browser screenshot, not just code review - a reminder that HTML attribute content needs the same "verify visually" discipline as anything else.
- **TOOLS panel** (2026-09-03) — a second slide-in panel (TOOLS button, top right, reuses the same `.jobs-panel`/`.jobs-tab`/`.jobs-btn` CSS classes as the JOBS panel rather than duplicating styles) surfacing reminders/news/science/learning, which existed and worked through chat/voice since early in the project but had no dedicated UI - Duc noticed the gap ("some functionality we done building but not attach to the main UI body") and asked for it connected. Four tabs, same direct-endpoint-not-router pattern as JOBS: **Reminders** (add/list/complete/+1-day-snooze, a "show completed" toggle), **News**/**Science** (fetch button → real RSS results via the existing `TechNewsTool`/`ScienceFactsTool`), **Learning** (due-review list with remembered/forgot buttons, plus a manual add-item form). Real bug caught adding a second header toggle button: `.hud-header`'s content could overflow its container and the page would scroll horizontally to compensate (`html`/`body` had no `overflow-x: hidden`) - fixed by adding that and tightening the toggle buttons' padding at the existing narrow-viewport breakpoint. Verified end-to-end against the real running server and via real browser JS-triggered interaction (not just curl) - reminder add/complete/show-done, live news/science fetches, learning add - all confirmed with no console errors; all test data cleaned from the real `reminders.db`/`learning.db` afterward.
- In auto mode on any front door: say "focus mode" / "chill mode" / "auto mode" to change the sticky session mode, or "ask claude" / "use local" in one message to override just that turn.
- Book summarization: `python3 scripts/summarize_book.py path/to/book.pdf` (or `.epub`) — reads a book you already have, saves a structured summary into the spaced-repetition learning store. Standalone script on purpose, not a conversational tool — see `docs/agentic-roadmap.md`, job #7.
- Usage-pattern check: `python3 scripts/analyze_patterns.py [--days N] [--threshold N]` — counts repeated tool usage in `data/router.log` over a rolling window (default 7 days / 3x), and on a real hit spends one Claude call turning it into an observation saved to `data/pattern_observations.md` + `memory_notes` (category `observations`). Manual for now, no cron/launchd wiring yet. See `docs/agentic-roadmap.md`, "Usage-pattern observation."
- Voice model download (one-time): `python3 scripts/setup_voice_models.py`
- Playwright browser download (one-time, needed for job-application autofill): `python3 -m playwright install chromium`
- Job application autofill: fill in `data/applicant_profile.json` (see `src/companion/profile.py::ApplicantProfile` for the fields - required: name, email, phone, resume_path pointing at a real local file), then ask Kyra to autofill a Greenhouse posting URL. Fills only - a visible browser window stays open for Duc to review and submit himself.
- Voice sanity check, no mic needed: `python3 scripts/test_voice_roundtrip.py`
- API key sanity check: `python3 scripts/smoke_test.py`, or `python3 scripts/debug_api_key.py` for a detailed error if it fails
- Memory embedding migration (one-time, already run): `python3 scripts/migrate_memory_embeddings.py` — re-embeds `data/memory_db` under the BGE embedding function. Safe/idempotent to rerun; only does anything if the collection is non-empty.
- No test suite yet (no pytest). Verification so far has been targeted scripts like the ones above, plus real-pty tests (see `scratchpad/` patterns) for anything that reads raw keypresses — piped stdin doesn't exercise `termios`/`tty` cbreak mode, a real pty does. If you add real tests, use pytest under `tests/`.
- Scripts import via `sys.path.insert(0, ".../src")` rather than an editable install — keeps setup to plain `pip install -r requirements.txt`, no build step. Follow the same pattern in new scripts.

## Architecture pattern — preserve this

Every subsystem is a small ABC interface + a swappable concrete backend (Strategy pattern), specifically because this project doubles as interview practice — "how would you extend this" should always have a clean answer. Existing examples:

- `MemoryStore` → `ChromaMemoryStore` (`src/companion/memory.py`); a separate, second memory layer, `MemoryNotesStore` → `MarkdownMemoryNotesStore` (`src/companion/memory_notes.py`) - see the key decision below, they're not the same thing
- `SpeechToText` → `FasterWhisperSTT`, `TextToSpeech` → `KokoroTTS` (`src/companion/voice.py`)
- `ListenMode` → `PushToTalkListener`, `VoiceActivityListener` (`src/companion/listening.py`)
- `LLMBackend` → `AnthropicLLM`, `LocalLLM` (`src/companion/llm.py`) — `ConversationManager` depends only on `LLMBackend`; `build_llm(backend)` is the factory, `LazyBackends` is a dict-like cache that only constructs a backend the first time it's actually asked for (so a session the router never sends to local doesn't pay local-model load time).
- `Tool` → `AddReminderTool`/`ListRemindersTool`/`CompleteReminderTool`/`SnoozeReminderTool` (`reminders.py`), `TechNewsTool` (`news.py`), `ScienceFactsTool` (`science.py`), `SaveLearningItemTool`/`DueReviewsTool`/`MarkReviewedTool` (`learning.py`), `HandoffTool` (`handoff.py`), `AddJobApplicationTool`/`ListJobApplicationsTool`/`UpdateJobApplicationStatusTool`/`DraftApplicationMaterialTool` (`job_applications.py`), `SaveMemoryNoteTool` (`memory_notes.py`), `AutofillJobApplicationTool` (`job_autofill.py`) (`src/companion/tools.py`) — `name`/`description`/`input_schema`/`run()` map 1:1 onto a Claude tool-use definition, so `ToolRegistry.schemas()` goes straight into `tools=` on a Messages API call with no translation. `default_tools.py::default_tool_registry()` is the one place all fifteen (reminders 4, learning 3, job applications 4, autofill 1, memory notes 1, news 1, science 1) get assembled - `chat.py`/`voice_chat.py`/`webapp.py` all call it instead of constructing `ToolRegistry(...)` separately, so they can't drift out of sync (they briefly did, once, before this factory existed). `news.py` and `science.py` share fetch/parse code via `feeds.py` - add a new RSS-backed tool there too rather than re-implementing the Atom/RSS handling. `job_autofill.py`'s `AutofillEngine` ABC → `GreenhouseAutofillEngine` (Playwright) is the same Strategy shape, ready for a Lever/Workday/iCIMS engine later without touching the tool.
- `TurnRouter` (`src/companion/router.py`) — the design Duc worked through across several sessions, now built and wired into all three front doors. Layered decisions, cheapest/most-certain first: explicit override phrase ("ask claude"/"use local") > sticky session mode (`session_state.py`, file-backed, shared across front doors, focus→claude/chill→local) > a small local classifier (`Llama-3.2-3B-Instruct-4bit`, separate from the conversational `LocalLLM` default) that decides text-vs-tool and, for text, claude-vs-local. The tool path always goes to Claude as the "Agent Specialist" (`AnthropicLLM.respond_with_tools()`, the real Anthropic tool-use loop against a `ToolRegistry`) - local models weren't trusted with structured tool calls per the benchmark. `route_and_answer()`/`route_and_answer_verbose()` in the same module are what a front door actually calls per turn - one function, not reimplemented three times. Every decision is logged (`router_log.py`, JSONL, `data/router.log`) with a reason, whether or not anything went wrong.
- Long, "complex-looking" turns (word-count/multi-ask heuristic, `_looks_complex()`) get biased toward Claude rather than actually decomposed into subtasks - real subtask decomposition/execution was scoped out as a separate, bigger feature (see `docs/agentic-roadmap.md`).

When adding a new subsystem, follow the same shape: a one-or-two-method ABC, a concrete class that does the real work, callers depend only on the interface. Full context for all of the above: `docs/agentic-roadmap.md`.

## Key decisions worth knowing

- **Voice is local/open-source on purpose** (faster-whisper + Kokoro + Silero VAD), not a cloud API like ElevenLabs/OpenAI/Deepgram. Chosen for $0/turn (this gets tested a lot), privacy, and because running real local inference is more of the point of this project than calling someone else's endpoint. The interface boundary makes a cloud backend a future drop-in class, not a rewrite, if a polished demo ever wants one.
- **Voice turn-taking is sequential, with keypress barge-in** (not voice-triggered). `speak_interruptibly()` in `voice_chat.py` plays her reply via `sd.play()` and polls a raw keypress (`companion.keybindings.read_key()`, `termios`/`tty` cbreak mode — not line-buffered `input()`) instead of blocking on `sd.wait()`; the configured interrupt key stops her immediately. Deliberately *not* voice-triggered — the mic would pick up her own TTS through the speakers, and without real echo cancellation that risks her cutting herself off mid-sentence. Full concurrent listen-while-speaking stays a Backlog item; see `docs/design.md`.
- **Keybindings are configurable, not hardcoded** — `companion/keybindings.py`, env vars `KYRA_PTT_KEY`/`KYRA_INTERRUPT_KEY`, default Enter for both (unchanged behavior if you don't touch them). Both `PushToTalkListener` (`listening.py`) and `speak_interruptibly()` (`voice_chat.py`) read a single raw keypress via the same `read_key()` — this needs a real interactive terminal (`sys.stdin.isatty()`); non-tty stdin returns `None` rather than hanging or misfiring (a piped/closed stdin busy-looping here was a real bug caught during testing - see the pty-based tests this was built with).
- **Local LLM choice**: `LocalLLM`'s default is `Qwen2.5-14B-Instruct-4bit` (`llm.py::DEFAULT_LOCAL_MODEL`) — picked from `docs/model-benchmark.md`, not guessed. It's within 0.1 of the benchmark's best local model (Qwen2.5-32B) at more than 2x the tokens/sec, which matters more for voice since replies get read out loud. Local LLM weights live in `data/local_llm_models/` (its own `HF_HOME`, set in `llm.py`) — separate from `scratchpad/bench/`'s throwaway benchmark cache, which is safe to delete anytime and won't break this.
- **Memory embedding is BGE, not Chroma's default** — `memory.py::bge_embedding_function()` (`BAAI/bge-small-en-v1.5`, normalized). Chroma's built-in default is *already* MiniLM-L6 (with a 256-token truncation cap) - swapping to that would have been a no-op improvement, so don't "fix" this back to MiniLM thinking it's an upgrade. `ChromaMemoryStore` also blends in recency (`RECENCY_WEIGHT`/`RECENCY_HALFLIFE_HOURS` class attrs) since casual chat leans on "what we just talked about." **Changing the embedding function again needs `scripts/migrate_memory_embeddings.py` rerun** - old vectors don't get retroactively re-embedded, so a silent swap degrades retrieval on everything stored before the change instead of improving it.
- **Tech news is RSS, not scraping** (`news.py::FEEDS`) — NYT Technology, TechCrunch, Ars Technica, The Verge, Hacker News, all official/free feeds. The Verge's feed is Atom format, not RSS 2.0 - `_parse_feed()` handles both; don't assume every feed uses `<item>`.
- **Claude Code handoff is draft-only, by explicit decision** (`handoff.py::HandoffTool`) — composes a task brief and copies it to the clipboard (`pbcopy`, macOS-only) for Duc to paste into Claude Code himself. It does not execute anything or launch a session. Don't extend this to actually spawn `claude` without checking in first — see `docs/agentic-roadmap.md`, job #1.
- **`AnthropicLLM.respond()` had the same silent-truncation gap `respond_with_tools()` was already fixed for, just never patched** - caught for real when the job-draft web endpoint's critique pass cut a cover letter off mid-word at the old 1500-token budget. `respond()` now checks `stop_reason == "max_tokens"` and appends an explicit `[cut off - ran out of room...]` marker instead of silently returning partial text that reads as complete. This applies to every `respond()` caller, not just job drafting - plain chat at the default 500-token budget could hit this on a long explanation too. The job-draft backend's budget was also bumped 1500 → 2500 (both `default_tools.py` and `webapp.py`) since a style-matched cover letter draft-plus-critique can run long.
- **Tool-calling needs a bigger `max_tokens` budget than plain chat, and this bit us once already**: `AnthropicLLM` has a separate `tool_max_tokens` (2000, vs. 500 for plain `respond()`). Sonnet 5 runs adaptive thinking by default, and thinking tokens count against `max_tokens` - deciding which tool to call burns real budget before any tool_use or text block gets emitted. With the old shared 500-token budget, a real turn got cut off `stop_reason: "max_tokens"` mid-*thinking*, before reaching the tool call, and silently returned an empty reply. `respond_with_tools()` now treats `stop_reason == "max_tokens"` as a real failure (returns an explicit "ran out of room" message) rather than returning whatever `extract_text()` finds (which can legitimately be empty). Don't shrink `tool_max_tokens` back down without re-testing a real tool-calling turn.
- **The router's classifier prompt needs concrete examples, not just a rule description** - a first version without few-shot examples missed "what's the tech news today" as a tool call entirely (correctly understood the *intent* per its own stated reason, wrong `path` field regardless). Adding examples fixed it but initially over-corrected the other way, hallucinating a tool match for "draft a cover letter" (no such tool existed in the registry *at the time*) - fixed with an explicit "only if it matches a listed tool, task-shaped isn't the same as tool-shaped" instruction plus negative examples. **That example is now stale in the opposite direction**: once `draft_application_material` was built (2026-09-03), "draft a cover letter" *should* route to `tool` - the example was updated accordingly, and re-tested against a mixed batch, not just the one case. If you touch `CLASSIFIER_PROMPT` in `router.py`, re-run a mixed batch of tool/text-claude/text-local inputs, not just the one case you're fixing - this class of prompt edit fixes one case and silently breaks another more often than not with small models, and stays stale in the other direction once a new tool is added that changes what "no matching tool" means.
- **Memory is two separate layers on purpose, not one system doing two jobs** (`memory.py`'s `ChromaMemoryStore` vs. `memory_notes.py`'s `MarkdownMemoryNotesStore`). Chroma logs every exchange automatically and retrieves the top-k *semantically similar* ones per turn - good for "what did we just talk about," but a durable fact (a preference, who someone is) can be relevant on an off-topic turn where it's not semantically similar to anything, and top-k retrieval just misses it. Memory Notes is the fix: a small set of facts Claude itself chooses to save (`save_memory_note` tool, never automatic) as dated Markdown bullets in `data/memory_notes/<category>.md`, loaded **in full, every turn** into the system prompt (`ConversationManager._build_system()`) - no query, no top-k, because the set is meant to stay small and curated. Inspired by Mem0's split between curated memory and raw logs, and by the GBrain/Sylph/DIY-Claude-git-markdown pattern Duc researched - human-readable, git-diffable, no vendor lock-in. Temporal handling is deliberately simplified vs. something like Zep/Graphiti's point-in-time graph: append-only dated lines, "most recent wins" is a reading convention, not code that resolves contradictions - documented in the module docstring so nobody "fixes" it into silently dropping history. If `ConversationManager` is constructed without a `memory_notes=` arg it builds its own `MarkdownMemoryNotesStore()`, same pattern as `default_tools.py`'s `draft_backend` - no call-site changes needed at the three front doors.
- **Full resume optimization (`material_type: "full_resume"`) is a separate path from the cover-letter/bullet drafting flow, not a variant of it** - built 2026-09-03 after direct feedback that "resume bullet" mode produced disappointing 2-liners when what was actually wanted was a complete, optimized resume as a real downloadable PDF. `resume_format.py` defines a small line-tagged text contract (`NAME:`/`SECTION:`/`ENTRY`/`HEADING:`/`BULLET:`/...) that's trivial to parse deterministically - chosen over asking the model for Markdown (ambiguous once resume content has its own "#"/inconsistent headers) or JSON (invites subtle parse failures on a long, multi-entry document). `job_applications.py::optimize_full_resume()` is one generation call, no second critique pass (resume bullets are already terse/action-verb-driven, not prose with the chatbot tells the critique pass targets; a second rewrite pass also risks corrupting the strict format). `resume_pdf.py` renders the parsed result to a real PDF via Playwright's `page.pdf()` (already a dependency, no reportlab/weasyprint needed) - a clean, professional, ATS-friendly layout built fresh from the content, not an attempt to recreate the exact typography of whatever PDF Duc originally uploaded (that would mean real PDF-editing work with its own failure modes). `webapp.py`'s `/api/job/resume-pdf/{filename}` serves the generated file - filename is validated (no path separators, must end `.pdf`) before touching the filesystem, since it comes straight from the URL. Two real bugs caught building this: (1) a 3000-token budget silently truncated a full resume mid-document - `optimize_full_resume()` now explicitly checks for `llm.TRUNCATION_MARKER` (a named constant, not a re-typed string) and raises `ResumeFormatError` rather than silently parsing a cut-off document; the actual call site (`webapp.py`'s dedicated `_resume_llm`) uses `max_tokens=6000`. (2) the model initially crammed a Project entry's tech-stack into `HEADING` instead of `SUBHEADING`, squishing the layout - fixed by adding an explicit worked Projects example to the format instructions, plus making the PDF's CSS resilient to long headings regardless (`flex: 1` heading, `flex-shrink: 0` date). Verified end-to-end with Duc's real resume and a real job context, through the actual HTTP endpoints (not just direct calls) - correct PDF downloaded, correct content, no invented facts (spot-checked numbers against the original), path-traversal/invalid-filename/not-found guards all confirmed. Test-generated PDFs cleaned up afterward each time (`data/generated_resumes/` isn't itself gitignored-vs-tracked differently from the rest of `data/`, but generated files there aren't meant to accumulate test noise any more than the other stores are).
- **A real PDF-extraction fidelity finding drove two follow-up features (2026-09-03)**: comparing pypdf's extraction of Duc's real (LaTeX-compiled) resume PDF against the visible content turned up genuine artifacts, not hallucination-prone but real - dropped underscores in inline code (`slack_sdk` extracted as `slack sdk`) and a spurious space inserted before ordinal superscripts (`27th` extracted as `27 th`). Both are characteristic of LaTeX-typeset PDFs specifically (superscript kerning, certain font/ligature encodings) - not a bug in `doc_text.py`, a structural limit of reading text back out of a compiled PDF at all. Two responses, not one: `github_profile.py` adds real supplementary project data (see two bullets below) so a resume draft has more to work with than a single, imperfectly-extracted source; and **`optimize_latex_resume()` (`job_applications.py`) edits Duc's original `.tex` source directly** rather than going anywhere near PDF extraction - `doc_text.py` now treats `.tex` as plain text (no parsing needed, it already is text), and the model is instructed to preserve structure/packages/commands exactly, touch only content, and explicitly keep each rewritten bullet roughly the original length ("this document has a fixed layout... a bullet much longer than before risks overflowing the template when compiled") - a direct response to Duc's own stated worry about alignment breaking on recompile. Output is raw LaTeX, no PDF rendering at all - Duc compiles it himself with whatever toolchain he already trusts. `material_type: "latex_resume"` is a third top-level path in `webapp.py::job_draft`, sharing a `_pick_resume_source()` helper with `full_resume` (same one-off-upload → selected-library-doc → pasted-text priority) but never touching `resume_pdf.py`.
- **GitHub is a real, live data source for drafting (`github_profile.py`); LinkedIn deliberately isn't, and that's a constraint, not a gap to fill later.** GitHub's REST API is public and needs no auth for public repo/README data, same "official API, not scraping" reasoning as `feeds.py`'s tech news (see that decision above) - `fetch_github_projects()` pulls real repo name/description/language/README excerpt (forks excluded, sorted by most-recently-pushed), never invented. LinkedIn has no equivalent for a personal script - reading a profile's real work history needs either LinkedIn's official OAuth app-approval flow (built for companies, not a personal project) or scraping the page directly, which violates their Terms of Service. Opted into "tell Duc plainly and point him at pasting his LinkedIn text into the document library himself" rather than building something fragile or ToS-risky - if this ever needs revisiting (e.g. LinkedIn ships a real personal-data export API), reconsider then, don't route around the ToS constraint now.
- **`include_github` is opt-in per draft (a checkbox), not automatic** - it's a real network call each time, and forcing it into every draft would mean every cover letter/resume silently depends on GitHub being reachable. Wired into both the paragraph-drafting path (`job_draft`) and both resume paths (`_full_resume_draft`, `_latex_resume_draft`) via a shared `_fetch_github_context()` - reads `profile.github_url`, parses the username, fetches, and returns a clearly-labeled "use if genuinely relevant, don't force it" block rather than an instruction to always incorporate it. Verified real: pulled Duc's actual repos (a CalHacks gamified-learning project, a personal LLM fine-tuning playground, a GPT-4-Vision scraper) that weren't already on his resume, produced accurate, non-fabricated draft text referencing them. Note the "don't force it" framing means a full-resume optimization won't necessarily add a new Projects entry from GitHub even when one might strengthen the resume for a given role - confirmed in testing (an ML-focused job context didn't pull in the LLM playground project) - this is the instruction working as written, not a bug, but worth knowing if "make it use GitHub more" ever comes up.
- **Job application drafting uses the actual humanizer methodology, not an improvised pattern list** (`job_applications.py::DraftApplicationMaterialTool`, `CRITIQUE_PROMPT`) - draft, then a critique-and-rewrite pass following [github.com/blader/humanizer](https://github.com/blader/humanizer) (MIT), which Duc surfaced from his own research: 35 AI-writing patterns compiled from Wikipedia's WikiProject AI Cleanup, grouped into content/language-grammar/chatbot-hedging categories, plus a four-step process ending in an explicit self-check ("does this still sound AI? did any fact change?"). Reworded for job-application material, not copied verbatim - an earlier version used a short improvised list ("delve"/"boasts"/rule-of-three) before this upgrade; if you touch `CRITIQUE_PROMPT` again, keep it grounded in the actual repo's categories rather than drifting back to an ad hoc list. The critique pass is explicitly bound to the same no-invention rule as the draft pass - a name/number/date/claim has to trace back to what Duc actually gave it. Uses a dedicated `AnthropicLLM(max_tokens=1500)` instance (see `default_tools.py::default_tool_registry(draft_backend=...)`) - the same tool-calling token-budget lesson two bullets up applies here: a draft plus a critique pass needs real room.
- **Job application autofill stops at fill, never submit - a boundary Duc set explicitly, not one to expand without asking again** (`job_autofill.py`, `profile.py`). Built with Playwright against a real live Greenhouse posting (a public Affirm job, inspected and fill-tested with fake placeholder data, nothing entered/submitted) rather than guessed DOM structure. `ApplicantProfile` is a single local JSON record (`data/applicant_profile.json`) - the most sensitive data Kyra touches, so it stays local like everything else (see the voice/memory decisions above) and is never logged or sent anywhere except into a form field on a page Duc asked to fill. EEO/voluntary self-identification fields default to "Decline to self-identify" - never guessed. Custom per-posting questions (referral source, "worked here before?", etc.) are never guessed either - unmatched fields are explicitly reported as skipped in a saved Markdown summary (`data/job_autofill_logs/`) listing exactly what was filled and what wasn't, which is the "easily checked" requirement Duc asked for directly, not a nice-to-have. **Real bug caught during build**: Greenhouse renders purely numeric HTML `id`s (e.g. `id="4028768003"`) - invalid as a bare CSS `#id` selector since a CSS identifier can't start with a digit - fixed by matching `[id="..."]` as an attribute selector instead. Don't extend this tool toward clicking Submit without checking in first - same standing rule as the tracker/draft boundary, now applied to the fill boundary too.
- **`ApplicantProfile.resume_path` needs an actual file on disk, and the PROFILE tab was shipped without any way to set it** - a real gap Duc hit directly (filled out the whole profile form, got blocked on `resume_path` with no field for it). Fixed by connecting it to the document library instead of asking for a hand-typed filesystem path: `JobDocumentStore.add()` gained an optional `file_bytes` param that saves the original uploaded file to `data/job_documents/files/<id><ext>` (not just its extracted text) and records the path on the `JobDocument.file_path` field; `JobDocumentStore.delete()` removes that file too, best-effort. The PROFILE tab has a dropdown listing resume-kind documents that have a real file, which fills the (still-editable, still-manual-override-capable) `resume_path` text field on selection. Old `JobDocument` records from before this field existed tolerate it via `dict.setdefault("file_path", None)` on read.
- **`webapp.py::_get_or_add_document()` dedups library saves by exact text content, regardless of kind** - a real bug Duc hit directly: the DRAFT tab's "Quick one-off upload" shows a Resume slot and a Style-sample slot together, and dropping the same file into both in one request silently created two separate library entries for identical content. Every save path (one-off resume upload, one-off style-sample upload, the explicit Document Library "add" form) now goes through this helper - if a document with the exact same text already exists, it's reused and the response says so ("matches something already in your library - reused it, not duplicated") instead of silently duplicating.
- **The classifier only ever sees the current message, never conversation history** - a known, real limitation, not yet fixed. Context-dependent turns ("yeah I remembered that one" following Kyra asking about a review) misclassify because the classifier has no way to know what it's a reply to. Adding history would fix it but costs more tokens/latency on every single turn for a case that's relatively rare - not worth it unless it turns out to matter in practice.
- **`CLASSIFIER_MODEL` (`Llama-3.2-3B-Instruct-4bit`) is empirically justified, not just the original untested pick** - see `docs/router-model-benchmark.md`. Benchmarked against 3 smaller candidates; 3B wins on accuracy (96.6%) after a real prompt bug the benchmark caught got fixed (see `CLASSIFIER_PROMPT` two entries up). Qwen2.5-1.5B is a documented, real fallback if classifier latency ever matters more than its ~10pp accuracy gap - a one-line change, not a redesign. Separately, local models (Qwen2.5-7B+) were flawless at the Agent Specialist's job (tool selection + arguments) on an 11-case suite - promising, but the suite's small and the Agent Specialist role stays Claude's until a harder suite backs a change. Also found: Qwen/Llama/Mistral each render function-calling in a different, incompatible format from their chat templates - a real cost of ever moving tool-calling local that a single Claude API sidesteps.
- **Silero VAD requires exactly 512-sample chunks at 16kHz** (`VoiceActivityListener.CHUNK_SAMPLES` in `listening.py`) — it raises "Input audio chunk is too short" on anything else. Don't change this constant without re-verifying against the installed silero-vad version.
- **Sample rate contract**: `SpeechToText.transcribe()` always expects mono float32 audio at 16kHz (`companion.voice.SAMPLE_RATE`). Kokoro's TTS output is 24kHz — resample before feeding it back into STT (see `test_voice_roundtrip.py`'s `resample()` for the pattern used so far).
- **`ConversationManager._build_system()` includes the current local date/time, and this was a real, user-visible bug before it did**: a reminder tool call landed a due date over a year in the past because nothing ever told the model what day "today" is - "tomorrow morning" is meaningless without it. Local time (`datetime.now().astimezone()`), not UTC, so "tomorrow" means Duc's tomorrow. This affects every turn, not just tool calls - don't remove it to save a few tokens.
- **Browser audio format decoding reuses faster-whisper's own utility** (`companion.voice.decode_uploaded_audio` → `faster_whisper.audio.decode_audio`, which bundles PyAV/ffmpeg) instead of adding a new audio-decoding dependency - handles whatever `MediaRecorder` produces (webm/opus, etc.) without the web UI needing to know or care about the exact format.
- **The web UI's hands-free voice is a plain energy-threshold VAD** (`AnalyserNode.getByteTimeDomainData`, RMS against a fixed threshold, in `web/app.js`), not Silero like the CLI - no external JS library, good enough for a first version, may need real threshold tuning once actually used with real background noise. Paused during TTS playback for the same echo-avoidance reason `voice_chat.py` is sequential - don't remove that guard to make it feel more "always on."

## Working practices

- **Never `cat`, `diff`, or otherwise print the full contents of `.env`.** It holds a live Anthropic API key. Two earlier sessions accidentally leaked a real key into a conversation this way (both keys were revoked after). For diagnostics, check only length/prefix/whitespace, like `scripts/debug_api_key.py` does.
- Model files and local databases (`data/`, including `data/voice_models/`) are gitignored on purpose — don't commit them, don't remove them from `.gitignore`.
- `git` identity for this repo is set locally (not global) to Minh Duc Vo / a private address — that's deliberate, leave it repo-local.
- This project also has job-search working docs under data/private_docs/ (gitignored).
- **The "clean up test pollution" discipline covers `data/router.log` too, not just the DB stores** — a gap found 2026-09-03 while building `analyze_patterns.py`: classifier re-test scripts (`router.route(msg)` in scratchpad harnesses) log to the real `data/router.log` exactly like production does, and this had gone unnoticed across several classifier-prompt-edit sessions, leaving 193 lines of pure test noise (caught only because a pattern-analysis tool would have treated it as real usage). After any classifier re-test batch, check `data/router.log`'s recent entries the same way you'd check `data/*.db` - don't assume only the databases need this.
