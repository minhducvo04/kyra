## Entries

- **Repo is being prepared to go public** - private job-search docs moved to `data/private_docs/` (gitignored); tracked docs scrubbed of employer/interview specifics; the history rewrite recipe lives in `data/private_docs/publish-checklist.md` (v4) + `data/private_docs/history-replacements.txt`, both gitignored (they were in `deploy/` until 2026-09-05, when the rewrite purged them from the tree). **A force-push is not enough and never was**: GitHub keeps `refs/pull/*` (13 of them here, and `refs/pull/1/head` is not an ancestor of `origin/master`), so the repo has to be deleted and recreated. The rewrite and the recreation are Duc's actions, not automated. **The audit that blocks publication is third-party PII, not secrets** - see the next bullet.
- **The rewrite is rehearsed on a throwaway clone before it touches the real repo, and that is the only honest way to hand over a destructive step (2026-09-08)** - `git-filter-repo` was run against a `--mirror` clone in a scratch directory with the existing 20-rule replacement file: **246 commits preserved, 0 hits for all five identifiers in blobs, 0 in commit messages, 493 passed and ruff clean on the rewritten tree**. So the procedure in the checklist is measured rather than plausible, and the only thing the real run adds is the repo it happens to. Two things the rehearsal established that reading the rules could not: the replacements actually land (`Alex Rivera` and `alex-example` are present in the rewritten blobs, so a rule cannot have silently no-opped), and **a blob rewrite touches test fixtures, so the suite is part of the verification, not a formality**. Also re-measured rather than trusted: the only words in the entire history containing any of the three given names are the identifiers themselves, so the substring rules cannot mangle an innocent word - v3 flagged that as a thing to skim for by eye afterwards, and it is now a fact checked up front. **Duc still runs step 1 and the delete-and-recreate**; what changed is that he is no longer running them for the first time.
- **Three things a public repo needed that a private one never did (2026-09-08)** - none of them privacy, all of them the first thing a stranger meets. (1) **`.gitignore` grew a second line for personal documents.** `/data/` already covered the college essays, the CS169A notes, the resumes and the private job-search docs, so nothing personal was ever exposed and the answer to "hide my essays" was that they already were. The patterns (`*.docx`, `*.pdf`, `*.tex`, `*.pages`, `*.key`, `*.numbers`, plus the Office and OpenDocument extensions) exist because the *next* personal file might land outside `data/`, and the check that made them safe to add is that the repo tracks **zero** files of those types - so nothing meant to ship is now hidden, and `git add -f` is the escape hatch. (2) **There was no `LICENSE`**, which means all rights reserved by default: a reader of a portfolio project cannot legally copy the thing it exists to demonstrate. MIT, matching the vendored skills. (3) **The README still said "56 tests" and "Phase 1 done"** against 493 today, was written for Duc rather than a reader ("run in your own Terminal, not through Claude"), and mentioned none of the measured work - not the router fine-tune, the search evaluation, the distillation result, the apply pipeline or the visionOS client. **The resume link lands on that page**, which made it the weakest surface in the repo while the repo was the strongest thing on the resume. Rewritten to lead with what was measured, including the tool-calling distillation that was measured and deliberately **not** shipped, since a negative result honestly reported is a stronger signal than a feature list. Every link and number in it was checked against the file it points at, and it went through the real `CRITIQUE_PROMPT` humanizer pass per the standing outbound rule - which returned it **unchanged**, so the pass is evidence here rather than a step performed.
- **A real person's details were in the test fixtures, and that is what a pre-publication audit is actually for (2026-09-07)** - `tests/test_outreach.py` plus five other tracked files carried a real outreach contact's full name, real LinkedIn URL, employer, role, school and career move, and two more real first names as "mutual connections". He never consented to appearing in a public repo, least of all in the file demonstrating automated outreach drafting *to him*. Replaced throughout with a fictional contact (Alex Rivera at Northwind, `linkedin.com/in/alex-example`); every engineering lesson in the outreach bullet above is preserved, only the identifying facts are gone. The working tree greps clean; **history does not** - 79 commits carry the identifiers in blob content and 6 in commit *message bodies*, which needs `--replace-message` as well as `--replace-text` (the v2 checklist covered neither). Everything else audited clean: no API key ever committed, `data/` never committed, no phone numbers, no real account ids. Two lessons worth keeping: (1) a pre-publication audit that only greps for secrets and employer names misses PII entirely, because the danger was a *person*, not a credential; (2) v2's verify grep returned 792 hits and looked alarming, but 495 were `amazonaws.com`/`AmazonECSTaskExecutionRolePolicy` introduced by the AWS slice one day *after* the grep was written - a scrub check that is not maintained alongside the code turns into noise that hides the real signal. (3) **removing it once was not enough**: the name came back twice within a day - once in a `relation` field comment that arrived with outreach slice 2, once in a new CLAUDE.md bullet describing a real follow-up - both written in good faith, because the real contact is still in `data/outreach.db` and still part of the actual workflow. (The literals are deliberately not quoted here; writing this bullet the obvious way tripped the guard on its first run, which is the shortest possible demonstration of why the guard is not paranoia.) `tests/test_no_third_party_pii.py` now scans every tracked file and fails with the file:line if an identifier reappears (needles spelled backwards so the guard does not reintroduce what it keeps out; `git ls-files` already excludes gitignored `data/`, where the real record belongs). Verified both directions, including a planted regression. **The history rewrite should therefore run when the tree is quiescent** - a rewrite while another session is writing the name back leaves a clean history under a dirty tip.
