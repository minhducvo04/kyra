# The daily digest

`digest.py` and `scripts/daily_digest.py`: the 05:00 page, the JSON archive, the notification, the Applications section.

Entries below were moved verbatim from `CLAUDE.md` on 2026-09-09 (original order kept, newest work is usually nearer the top of each section). Add new entries at the top of this file, dated, with the *why*.

## Entries

- **The digest has an Applications section, because the pipeline's whole end state was invisible (2026-09-08)** - mass apply finishes at `ready_to_submit` (filled, waiting on Duc's click) or `needs_attention`, and nothing surfaced either until he next opened the JOBS panel, so a batch queued overnight could sit for days. `DigestData` carries `waiting`/`needs_attention` from `JobApplicationStore`, both count toward `action_count`, and the HTML gives each its own card: the waiting one shows the **resume filename it will attach** (what an employer receives, which Duc asked to be able to check every time) and a link straight to the form; the attention one pulls the reason out of the row's last `[apply ...]` note line. `summary_line` mentions applications **only when there are some** - the line is already five numbers long and "0 to submit" every morning would train him to stop reading it, but a filled application is the most actionable thing the digest ever holds, so when there is one it leads. Verified against the real tracker: the real `needs_attention` rows rendered with their real links and reasons, and `--dry-run` left `seen.json` byte-identical.
- Daily digest: `python3 scripts/daily_digest.py [--dry-run|--no-notify|--open|--index|--date YYYY-MM-DD|--search TERM|--rebuild]` — due reminders, outreach follow-ups, due reviews, new board postings, top news → `data/digests/<date>.md` (archive) **+ `<date>.html` and `latest.html` (the page you actually read)** + a macOS notification. Scheduled at 05:00 by launchd (`deploy/com.kyra.daily-digest.plist`, installed in `~/Library/LaunchAgents/`; `launchctl unload` it to stop). Logic lives in `src/companion/digest.py` (`build_digest` → `DigestData` → `render_markdown`/`render_html`/`render_index`), the script is the thin CLI — same shape as `watch_boards.py` over `job_boards.py`. **`<date>.json` is the canonical record** (`to_json`/`from_json`); `--rebuild` regenerates every page from it, `--index` opens the archive front page, `--date` opens one past day, `--search` finds a headline across every archived day.
- **The digest archive is JSON-canonical, because the Markdown was quietly lossy (2026-09-07)** - Duc asked whether past days were kept or only temporary, and whether he could go back to a day he missed. Days *were* kept forever, but `render_markdown` writes only headline + link and **drops each item's `summary`** - exactly the "is this worth my time" signal the page exists for - so going back to 2026-09-05 lost the thing that made it readable. Fixed by writing `<date>.json` (`to_json`/`from_json`, full `DigestData` round-trip including the `WatchReport.reposted` set) as the record that must never be deleted; `.md` stays the grep-able log and `.html` became a *rendering* that `--rebuild` redoes from JSON. That is also the storage answer: ~27KB/day all-in (~10MB/year), and deleting every `.html` drops it to ~11KB/day with `--rebuild` restoring them. Navigation is plain links - each page carries `← older / All days / newer →`, `write_archive()` rewrites the newest two days each run (a new day gives the previous day a "later" link it didn't have) plus any day whose page is missing, so the archive self-heals and `--date` always has something to open. **A real mistake worth keeping**: the CSS was first split into a shared `digest.css` to save ~5KB/day, which broke self-containment - the index rendered completely unstyled in the browser preview because a relative `href` can't resolve against a page with no base URL. 5KB/day is 1.8MB/year, so the trade bought nothing and cost robustness; reverted to inline `<style>`, with a test (`test_pages_are_self_contained`) pinning it so nobody re-optimizes it back. Two days (09-05, 09-06) predate the JSON and can't be rendered as pages, but omitting them would make the index lie about how many days exist, so they get a muted, still-clickable cell linking to their `.md`. **The index is a calendar (2026-09-07, Duc's ask)** - `render_index` builds a Sunday-first month grid per month present in the archive, months newest-first so the current one is what you land on, days inside a month in natural 1..31 order. A day with a digest is a link carrying a dot (red if that morning had something to do) and a `title` with its counts; a day without one is a dim, unclickable number, which is itself the answer to "did Kyra run that morning?". Built on stdlib `calendar.Calendar(firstweekday=6).monthdatescalendar()` rather than hand-rolled date maths - the alignment is pinned by a test (1 September 2026 is a Tuesday, so exactly two pad cells precede it), since an off-by-one there would file every archived day under the wrong weekday and be easy to miss by eye.
- **The digest is a page, not a Markdown file, and the notification click was landing on Script Editor (2026-09-07)** - Duc could not find a way to read what the 05:00 digest produced, and clicking the notification opened an empty Script Editor window. Root cause of the click: macOS attributes a notification to the app that posted it, and `osascript` has no bundle of its own, so `display notification` is credited to Script Editor and clicking one activates *that*. Two fixes, both in `scripts/daily_digest.py`: the digest now also writes `data/digests/<date>.html` plus a stable `latest.html` (self-contained page - inline CSS, no JS, no server, so it opens whether or not `web_ui.py` happens to be running, which at 05:00 it isn't), and `notify()` uses `terminal-notifier -open <file uri>` when it is on PATH, falling back to the osascript notification otherwise. **`terminal-notifier` is installed now (3.1.0, Homebrew) and posting cleanly** - but getting there found the real macOS 26 constraint: the Homebrew bottle is only **ad-hoc signed** (`codesign -dv` -> `Signature=adhoc`, `TeamIdentifier=not set`), and macOS 26.6.2 refused it notification permission three times (`Requested authorization [ didGrant: 0 hasError: 1 ]` in `log show --predicate 'process == "terminal-notifier"'`, and on stdout `Could not request notification permission: Notifications are not allowed for this application`) before granting it after an `lsregister -f` on the `.app`. So the permission is real but was not automatic, and can be revoked in System Settings at any time. **`notify()` therefore treats terminal-notifier as best-effort**: it reads the command's *output*, not just its return code - the binary exits 0 even when it fails to post - and falls back to the osascript notification on either "not allowed" or a non-zero exit. All three paths were verified for real (works / not on PATH / present-but-refused via a stub on PATH). Without that fallback, installing terminal-notifier would have silently *removed* Duc's morning notification instead of improving it. An unsigned `osacompile` applet was built and tested as the zero-dependency alternative and rejected for exactly the signing reason that then bit terminal-notifier too. Three real content findings while building: (1) `FeedItem.summary` was already being fetched and thrown away by the digest - it is the whole "which of these do I want to read in full" signal, now rendered under each headline; (2) **Hacker News' RSS `description` is not prose**, it is `Article URL: ... / Comments URL: ... / Points: N / # Comments: N`, so `_news_item()` parses it into real fields - the headline now links to the *article* and the discussion is a separate link, instead of printing the metadata blob as a summary; (3) `fetch_feeds` collects per-feed errors and the digest discarded them, so a dead feed looked like a quiet news day - they are a Warnings section now. Separately fixed: `--dry-run` was **not** read-only - `check_boards` records every posting it sees, so previewing the digest consumed tomorrow's genuinely-new postings; it now runs against a temp *copy* of `seen.json` (a copy, not an empty file, or every one of the 389 open postings reads as new). Verified with a real run: both files written, notification fired, page opened and read in a real browser, `seen.json` byte-identical (md5) across a dry run.
