# Autofill, job boards, posting fetch, mass apply

`job_autofill.py` and its three engines, `job_boards.py` (Greenhouse/Lever/Ashby/Workday), `job_posting_fetch.py`, `posting_signals.py`, `apply_pipeline.py`, `profile.py`, `job_documents.py`. The fill-never-submit boundary lives here.

Entries below were moved verbatim from `CLAUDE.md` on 2026-09-09 (original order kept, newest work is usually nearer the top of each section). Add new entries at the top of this file, dated, with the *why*.

## Entries

- **Posting signals + target-this-posting (2026-09-06 overnight, from Duc's notes in `data/private_docs/job-search-notes-2026-09-06.md`)**: `analyze_job_posting` (`posting_signals.py`, deterministic: age/repost/salary spread/requirement count/problem language → interview questions/mandatory conditions/team named) and `target_job_posting` (`job_posting_fetch.py`: Greenhouse/Lever/Ashby URL → text via the public APIs, signals, tracker entry as `targeting`; other URLs need pasted text). The board watch marks `REPOSTED` and prints posting age; the digest has an Outreach section. Plan: `docs/plans/2026-09-06-overnight-notes.md`.
- **What the form marks required decides whether an application stops, not what kind of field it is (2026-09-08)** - `apply_pipeline` treated every skipped custom question as expected and every empty profile field as attention, and both halves were wrong. Duc has no portfolio site or Twitter, so an *optional* Portfolio box turned a finished application into `needs_attention`, and a status that cries wolf is one he stops reading. The dangerous half was the reverse: a **required** custom question was filed under "expected", so the real Netic form's two required free-text questions never surfaced and he would have opened a `ready_to_submit` form to find required boxes empty. `SkippedField.required` now carries the form's own marking and `hard = [s for s in report.skipped if s.required]`. **No two boards mark it the same way**, checked on real live forms: **Ashby** sets the DOM `required` property with nothing in the label, while **Greenhouse** leaves `required` false and marks it with `aria-required="true"` plus an asterisk - so `_is_required()` is the union of the three, and reading any one alone would call every field on one board optional. Lever's `cards[...]` group is treated as required, since a real form (Palantir, 60 questions) routinely includes required ones. Expect **fewer** `ready_to_submit` results and better reasons: a posting with a required "Why this company?" essay genuinely is not ready to submit. Verified by filling both real live forms headless with obviously fake data, nothing submitted.
- **Adding a board checks it immediately, so day one does not flood day two (2026-09-08)** - `watch_boards.py add` now calls `seed_entry()` (one `check_boards` over just that entry) and prints what is open. A board Duc has only just started watching has no "since I last looked", so without this its entire current list lands in the next morning's digest as if it appeared overnight - really 57 postings for NVIDIA, 120 for Anthropic - burying whatever genuinely did. Nothing is hidden: the openings are printed at the moment he asks, which is where he is looking, and the digest goes back to meaning "what changed". A fetch failure is reported rather than raised, because the watchlist entry is what he asked for and losing it to a momentary network problem would be worse than losing the preview. Verified against the live NVIDIA board: the add printed all 57 and the next run reported 0 new.
- **Workday boards can be watched, but only by searching them (2026-09-08)** - `WorkdayBoard` joins Greenhouse/Lever/Ashby behind `JobBoardSource`, with a token that carries all three parts it needs, `"<tenant>.<pod>/<site>"` (e.g. `nvidia.wd5/NVIDIAExternalCareerSite`), which `slug_from_url()` builds from any Workday URL. It is unlike the other three in two ways, both measured on NVIDIA's real board: **it cannot be enumerated** (2,000 open postings, a page caps at 20, and asking for 100 returns an empty response, so a full crawl is 100 requests per company per run), so the watch entry's own `title_keywords` are sent as the board's search text, one request per keyword, bounded to 5 pages each - the ordinary local filter still decides what counts, the search only narrows what must be fetched, and a keywordless Workday entry is **refused** rather than crawled. And **the list is a POST** (hence `_post_json`) whose dates are relative phrases, so `_workday_posted_on()` turns "Posted Today" / "Posted 5 Days Ago" into a real date, treating "30+ Days Ago" as exactly 30 - a floor, since reporting an older age would invent precision the board never gave, and posting age is a signal Duc actually reads. **The trap to know**: Workday's search is token-based while `_matches` is a substring test, so an entry keyworded `new grad` fetches "Software Engineer, New College Grad" and then discards it. The filter was deliberately left alone (every watch entry Duc has already written assumes substring matching, and changing it would silently change what the other three boards report); a test pins both halves of that behaviour, and the fix is to keyword `grad`. Verified against the live board: 63 postings for "new college grad", 57 matching, 0 new on a second run, and one of those URLs carried straight through fetch, the tracker and the signals.
- **Workday is fetched and tailored for but will never be autofilled, and that is a boundary not a backlog item (2026-09-08)** - it is the most common ATS at large companies and was the last big gap in mass apply. Checked on a real live NVIDIA posting: the manual apply route is a **seven-step wizard whose step 1 is Sign In** (Google / LinkedIn / email), so an engine would have to sign in or create an account, which Kyra never does. What does work is everything before the form: `parse_posting_url` recognizes Workday URLs in the shapes Duc actually pastes (tenant in the subdomain, optional locale, any `wdN` pod, and the `/apply` or `/apply/applyManually` suffix stripped, because he pastes them after clicking Apply), and `fetch_posting` reads the posting from `/wday/cxs/<tenant>/<site>/job/<path>`, the site's own unauthenticated JSON endpoint - the same "official API, not scraping" line as the other three boards. So a Workday URL gets a tracker entry, signals, a tailored one-page resume and a cover letter, and then `apply_pipeline.CANNOT_FILL` says *why* the form is his to fill, with the link and the resume filename. **"No engine yet" would have been a lie**: it reads as "coming soon" and would cost him attention on every single run. Two things worth keeping: Workday's `hiringOrganization` is the **legal entity** ("2100 NVIDIA USA"), so the company still comes from `_company_name` (watchlist, else title-cased tenant) for the reason recorded on 2026-09-07; and the invariant test that every parseable source has an engine now distinguishes "unfillable by decision" from "unknown site".
- **Mass apply slice 3 (2026-09-08): the LinkedIn hand-off is two fields and no reads** - Duc finds a job on LinkedIn and applies through the company's own link, so `target_job_posting` and the apply pipeline take a `source_url` beside `url`: the URL is what the pipeline acts on, the source is where he found it, recorded on the tracker row as `[found via] <link>` (written once, not once per run) and never fetched. It is also the exact dedup key, because the row he made while browsing carries the LinkedIn link and LinkedIn's title need not match the ATS's. A LinkedIn URL with no pasted text now says how to hand over the company link rather than the generic "not a board URL" message, and `POST /api/jobs/apply` refuses a `source_url` with more than one posting, since "where I found it" describes one job. **Greenhouse's embed URL is recognized now** (`boards.greenhouse.io/embed/job_app?for=<co>&token=<id>`, either host, params in either order) because that is where "Apply on company website" usually lands - checked against a real live Anthropic embed form, whose labels and single file input are exactly the shape `LabeledFormEngine` already fills, so the Greenhouse engine needed no change.
- **A URL that identifies a posting only in its query string broke resume attachment, and the fix is to key on identity not spelling (2026-09-08)** - `job_autofill._normalize_url` reduced a URL to host + path so a `?gh_src=` tracking parameter could not defeat a match. A Greenhouse **embed** URL keeps the company and the job id *only* in the query, so every embed application in the tracker normalized to the same `.../embed/job_app`: two of them collided, no single URL match survived, and the company-slug fallback could not see "anthropic" either because it read the stripped key. The result would have been the **general** resume silently attached to a form an employer reads, which is the exact failure the one-resume-per-company rule exists to prevent. `_normalize_url` now returns `parse_posting_url`'s `(board, token, job id)` triple when the URL is a board posting, and falls back to host+path otherwise - so the boards, job-boards and embed spellings of one job all match each other, which was already the intent. The company fallback reads the raw URL, since the key no longer carries a slug. This was found by verifying against real data rather than by the tests, which had only ever seen one embed row.
- **Mass apply (2026-09-07, slice 1)**: JOBS → **APPLY** tab, or `POST /api/jobs/apply` with `urls` - one queued `apply` job per posting URL (`apply_pipeline.py::run_apply_pipeline`): target the posting (tracker entry), tailor the resume from `Settings.resume_base_tex` (`KYRA_RESUME_BASE_TEX`, default the General `.tex`) with the one-page loop and save `Duc_Vo_Resume_<Company>_<Role>.{tex,pdf}` under `data/resumes/` (set on the application, so autofill attaches it), draft a cover letter only when the posting mentions one (`cover_letter` auto/always/never → `data/cover_letters/`), fill the form when an engine exists for the URL's ATS (Greenhouse only today), then set `ready_to_submit` or `needs_attention`. Never `applied` - that is Duc's click. Plan: `docs/plans/2026-09-07-mass-apply.md`.
- **Autofill says why it cannot run instead of raising a Playwright traceback (2026-09-08)** - `requirements-web.txt` installs the `playwright` package but the Dockerfile never runs `playwright install`, so in any container `/api/job/autofill` died opaquely. Chromium stays **out** of the image on purpose: autofill opens a *visible* window for Duc to review and submit himself, so it is a laptop activity by design, and shipping a browser to run it headless on a server would defeat the fill-never-submit boundary rather than serve it. `BrowserUnavailable` names the fix instead.

- **Autofill now covers all three boards the fetcher supports, and each ATS matches fields its own way (2026-09-07)** - `AutofillEngine` gained `AshbyAutofillEngine` and `LeverAutofillEngine` beside Greenhouse, each built by reading a real live form (Composio and Netic for Ashby, Palantir for Lever) rather than guessing the DOM, and each verified headless with obviously fake placeholder data. The generic behaviour is now `LabeledFormEngine`: Greenhouse is that base with no overrides at all. What each board taught: **Ashby** serves the form at `<posting>/application`, has ONE `_systemfield_name` field instead of first/last (hence `single_name_labels`), and renders client-side - at `domcontentloaded` the first real run filled nothing and reported "no file input found", so the base gained a `ready_selector` wait. **Lever** has no `<label for>` on its core fields at all: they are `name` attributes (`name`, `email`, `phone`, `location`, `org`, `urls[LinkedIn]`), which is why the field walk became the overridable `_form_fields()` hook; everything else is a `cards[<uuid>][fieldN]` custom question, 60 of them on the Palantir form including a checkbox per language, all reported and none ticked. A required numeric question ("years of industry experience") was being *silently* ignored because the type filter allowed only text/tel/email/textarea - `number` and `url` are walked now, because a field missing from the summary Duc checks is worse than one listed as needing him. Boundaries unchanged: never a checkbox, never a CAPTCHA, never a free-text answer, never Submit.
- **Ashby and Lever hand back only a board slug where Greenhouse returns a company name (2026-09-07)** - and that slug became the tracker's company AND the tailored resume's filename, so the first real pipeline run produced `..._Resume_composio_...` and `..._Resume_retell_ai_...` on files an employer receives. `job_boards.company_for_token()` reads the display name out of the watchlist Duc already curates (matched per board, slug case ignored), and `titleize_token()` is the fallback for an unwatched board ("retell-ai" -> "Retell AI"). Rule this generalises: any identifier that reaches a filename or a form has to be checked against what a human would call it.
- **Mass apply is a pipeline over the existing pieces, and its end state is never `applied` (2026-09-07)** - Duc asked for "get the jobs, click apply, autofill, tailored resume and cover letter, note the status." Everything but discovery and the Submit click was already built as separate buttons; `apply_pipeline.py` strings them into one job per URL so a batch is N queued jobs the worker runs in order (one browser window each). Two statuses were added for the honest end states: `ready_to_submit` (form filled, review and click) and `needs_attention` (not one page, a guard warning, an empty profile field the form wanted, no engine for this ATS, a step failed - each reason listed, and the pipeline refuses to re-run a posting already past `applied`). A custom question autofill cannot answer is listed but is not an attention reason: nearly every form has one and Duc reviews the window anyway. LinkedIn stays out (standing decision); a LinkedIn URL needs pasted text and hand filling, and the next slices are Ashby/Lever engines and the "apply on company site" hand-off. **Found on the first real run**: the overnight bump of `_resume_llm` to 32000 tokens made every resume job fail with the SDK's "Streaming is required for operations that may take longer than 10 minutes" (the SDK refuses non-streaming calls above ~21k `max_tokens`) - `AnthropicLLM.respond()` now streams and takes the final message, same object as before. Also: the SSE terminal `event: error` shares its name with EventSource's native error, so the APPLY card guards against the native handler overwriting a verdict that already landed.
- **A LinkedIn posting reaches the pipeline by being looked up on the company's own board, not by being read (2026-09-08)** - the mass-apply slice-1 bullet above ends "a LinkedIn URL needs pasted text and hand filling"; that is now stale. `job_boards.find_posting(company, role)` searches the same public Greenhouse/Lever/Ashby APIs the watch already polls, and both front doors use it: `apply_pipeline.resolve_apply_url` puts the resolved URL in front of every later step (so autofill fills the real form and the tracker row's link is upgraded by the existing dedup), and `target_job_posting` does the same for a chat turn rather than answering "paste the posting text". LinkedIn itself is never opened, so the standing decision is untouched - what changed is that Duc's own recorded company and role are enough to find the req. **The refusal is the feature, and a real run against Anthropic's live board is what set its shape**: the role "AI Engineer" scores 0.80 against "Applied AI Engineer" and 0.67 against the posting actually meant, so an F1 over title tokens picks a *different* req with confidence - a generic title simply does not identify one posting. A leader is therefore trusted only when it is essentially exact (>= 0.95) or leads the runner-up by >= 0.25, on top of the existing rule that two matches within 0.05 (one req per office) refuse outright. Sending a resume tailored for one job to another is the failure that matters, so every refusal names the fallback: use the posting's own "Apply on company website" link, or paste the text. **What it does not reach**: a company that is not on those three boards under a watched or guessable slug. Measured on the real tracker, none of the stuck tracker rows resolve, because those companies are not on the three boards - so this pays off on the watchlist companies and on future postings, not retroactively.
- **The digest hands its postings to APPLY as one paste (2026-09-08)** - the 05:00 digest already does the "get the jobs" half of Duc's ask, and every posting in it came off a watched Greenhouse/Lever/Ashby board, so every URL is one `apply_pipeline` can fetch, tailor for and fill. They left the page one card at a time, so acting on a dozen meant a dozen copies. The jobs section now ends with a readonly `<textarea>` of the URLs. **A textarea rather than a copy button because the page is deliberately JavaScript-free and self-contained** (`test_pages_are_self_contained` pins that, after an earlier attempt to share a `digest.css` broke styling entirely) - click inside and select-all is the whole interaction, and no copy button can exist without script.
- **Scout slice 1 - board watch (2026-09-05)**: `job_boards.py` (`JobBoardSource` → `GreenhouseBoard`, `LeverBoard`) polls official public board APIs and diffs against `seen.json`; a fetch failure is an error, never "all postings closed." - **Job application autofill stops at fill, never submit - a boundary Duc set explicitly, not one to expand without asking again** (`job_autofill.py`, `profile.py`). Built with Playwright against a real live Greenhouse posting (a public Affirm job, inspected and fill-tested with fake placeholder data, nothing entered/submitted) rather than guessed DOM structure. `ApplicantProfile` is a single local JSON record (`data/applicant_profile.json`) - the most sensitive data Kyra touches, so it stays local like everything else (see the voice/memory decisions above) and is never logged or sent anywhere except into a form field on a page Duc asked to fill. EEO/voluntary self-identification fields default to "Decline to self-identify" - never guessed. Custom per-posting questions (referral source, "worked here before?", etc.) are never guessed either - unmatched fields are explicitly reported as skipped in a saved Markdown summary (`data/job_autofill_logs/`) listing exactly what was filled and what wasn't, which is the "easily checked" requirement Duc asked for directly, not a nice-to-have. **Real bug caught during build**: Greenhouse renders purely numeric HTML `id`s (e.g. `id="4028768003"`) - invalid as a bare CSS `#id` selector since a CSS identifier can't start with a digit - fixed by matching `[id="..."]` as an attribute selector instead. Don't extend this tool toward clicking Submit without checking in first - same standing rule as the tracker/draft boundary, now applied to the fill boundary too.
- **`ApplicantProfile.resume_path` needs an actual file on disk, and the PROFILE tab was shipped without any way to set it** - a real gap Duc hit directly (filled out the whole profile form, got blocked on `resume_path` with no field for it). Fixed by connecting it to the document library instead of asking for a hand-typed filesystem path: `JobDocumentStore.add()` gained an optional `file_bytes` param that saves the original uploaded file to `data/job_documents/files/<id><ext>` (not just its extracted text) and records the path on the `JobDocument.file_path` field; `JobDocumentStore.delete()` removes that file too, best-effort. The PROFILE tab has a dropdown listing resume-kind documents that have a real file, which fills the (still-editable, still-manual-override-capable) `resume_path` text field on selection. Old `JobDocument` records from before this field existed tolerate it via `dict.setdefault("file_path", None)` on read.
- **`webapp.py::_get_or_add_document()` dedups library saves by exact text content, regardless of kind** - a real bug Duc hit directly: the DRAFT tab's "Quick one-off upload" shows a Resume slot and a Style-sample slot together, and dropping the same file into both in one request silently created two separate library entries for identical content. Every save path (one-off resume upload, one-off style-sample upload, the explicit Document Library "add" form) now goes through this helper - if a document with the exact same text already exists, it's reused and the response says so ("matches something already in your library - reused it, not duplicated") instead of silently duplicating.
