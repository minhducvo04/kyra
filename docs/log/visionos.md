# The visionOS client

`apple/KyraVision/`: transport, presence orb, Today tab, the SSE parsing bug, the launch-argument seam.

Entries below were moved verbatim from `CLAUDE.md` on 2026-09-09 (original order kept, newest work is usually nearer the top of each section). Add new entries at the top of this file, dated, with the *why*.

## Entries

- **Workspace checkpoints and a spatial learning lab (2026-09-09)**: Duc asked Codex to build both brainstorming ideas. Workspace persists an explicitly edited task, last result, next action and inert reference text on the Mac. Resume restores context without executing it. The Learn tab runs a deterministic ten-tick shared-queue experiment with three optional servers, a committed numerical prediction, measured explanation and an editable takeaway saved into existing spaced repetition. A RealityKit volume in Shared Space shows enabled servers, completions and waiting work; it opens beside the main window. No LLM, room sensing or new permission is required to simulate.

- **Retries and destination changes are tested state, not view assumptions (2026-09-09)**: independent review found that late responses and failed connection changes could reassign old-Mac checkpoint rows to a new server, and that a lost save followed by a rejected retry could create a duplicate lesson. `WorkspaceState` and `LearningLab` now preserve uncertain payloads, request identity and destination, discard foreign lists before reassignment, and only unlock after definitive first-attempt failures. Unsaved lessons block experiment changes until saved or explicitly discarded. The original failures were reproduced in Swift tests before fixing them. Thirteen native tests cover those transitions plus all eight server masks and eleven arrival rates, conservation at every tick, deterministic routing and invalid configurations. The Debug-only `kyra.lab.demo` fixture renders a local result and opens the volume without any save or API call. Unsaved drafts are session state, not crash recovery.

- **A Today tab on the headset: the part of the digest you act on (2026-09-08)** - the 05:00 digest already assembles reminders, outreach follow-ups, due reviews, postings and news into a page Duc reads in a browser. `TodayView.swift` takes only the two halves he *acts on* - reminders to tick and reviews to answer - because those are what is worth having in front of him while wearing it; the rest is reading matter and stays where reading happens. Profile, documents, autofill and the tracker are deliberately absent: desk work on a headset is interface for its own sake. A `TabView` (Talk / Today) rather than anything spatial, per Apple's guidance to start with what people recognise. The saved summary sits behind a disclosure, since a review you can read the answer to is not a review, and a tick removes the row immediately rather than after a refetch - on a headset a tap that does nothing for half a second reads as a tap that missed. **Verified against the real stores** with a throwaway reminder and a backdated review beside Duc's real outreach follow-up, then both removed.
- **The visionOS client has a presence now, and it is an orb rather than a face (2026-09-08)** - `PresenceOrb.swift` carries the same six states as the web HUD (`idle/listening/thinking/speaking/interrupted/failed`) with the same vocabulary on screen (STANDBY / PROCESSING / SPEAKING / FAULT), so both front doors describe her identically. Drawn with plain SwiftUI shapes in a `TimelineView`, not RealityKit: this lives in a window, and a particle system belongs in a volume later if it earns one. Abstract on purpose - the research says an abstract shape reads calmer and more trustworthy than a face that can be slightly wrong. `ContentView` no longer keeps a `thinking` Bool; presence is the single state, which is the same consolidation the web HUD needed after its core ring knew two states and its mic button five. Reduce-motion pauses the whole timeline rather than just slowing it. **Verified with a real turn in the simulator**: PROCESSING with the Stop button red mid-flight, then the reply with a `claude` badge and the orb back to STANDBY.
- **`--args -kyra.ask "..."` hands the client a question at launch (2026-09-08)** - `xcrun simctl launch booted com.kyra.KyraVision --args -kyra.ask "hello"` lands in `UserDefaults` (the argument domain) with no Info.plist work, and `ContentView.onAppear` sends it. It exists because the visionOS simulator has no way to type into the app from a script, so without it nothing past the first screen can be verified unattended; it is also the seam a Shortcut or spatial Siri would use later, which is why it is a real affordance and not a test-only hook.
- **There is a visionOS client now, and it builds and talks to the Mac (2026-09-08)** - `apple/KyraVision/`, a SwiftUI window (not a volume, not immersive - Apple's guidance is to start with what people recognise, and the presence is the last thing to build). `KyraClient.swift` is the whole transport: `URLSession` with `waitsForConnectivity`, an optional `Authorization: Bearer` from `KYRA_API_TOKEN`, `/api/backend`, `/api/chat/stream` as SSE, and `/api/chat/cancel`. The backend badge is a top ornament; SEND becomes STOP mid-reply exactly as on the web. The `.xcodeproj` is hand-written (no XcodeGen dependency) and builds against visionOS 26.5 for the simulator. **Verified for real**: installed and launched in the Apple Vision Pro simulator, where the ornament went from `NOT CONNECTED` to `AUTO` - a real request to the real server, decoded and rendered - and the same `KyraClient.swift` compiled for macOS and run against the live server completed turns on both the streamed Claude path and the tool path.
- **`AsyncLineSequence` does not hand back the blank lines that separate SSE blocks (found 2026-09-08)** - and the bug it caused was invisible on exactly the turns most likely to be tried first. The Swift client flushed a block when it saw an empty line, so every token's JSON was concatenated onto the following `done` object and the object no longer parsed. A **tool** turn sends no tokens at all, so it worked perfectly; every streamed Claude turn failed with "the data couldn't be read". Flush when the next `event:` line arrives, and again at EOF, rather than waiting for a blank line. Found by compiling the real client for macOS and running it against the real server - reading the code would not have shown it, and the simulator UI would have shown only a generic failure.
