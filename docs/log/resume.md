# Resume tailoring

The LaTeX one-page loop (`job_applications.py`, `latex_compile.py`, `resume_latex.py`, `resume_guard.py`), Detailed mode, the guard, token budgets, the fabrication bugs and what fixed them.

Entries below were moved verbatim from `CLAUDE.md` on 2026-09-09 (original order kept, newest work is usually nearer the top of each section). Add new entries at the top of this file, dated, with the *why*.

## Entries

- LaTeX distribution (one-time, needed for one-page LaTeX resume fitting): `pdflatex`/`xelatex` on PATH — a real local LaTeX toolchain (e.g. MacTeX/TeX Live via Homebrew), not a Python package. `src/companion/latex_compile.py` shells out to whichever engine `detect_engine()` picks (xelatex if the source uses `fontspec`/`setmainfont`/`polyglossia`/`unicode-math`, pdflatex otherwise).
- **Full resume optimization (`material_type: "full_resume"`) is a separate path from the cover-letter/bullet drafting flow, not a variant of it** - built 2026-09-03 after direct feedback that "resume bullet" mode produced disappointing 2-liners when what was actually wanted was a complete, optimized resume as a real downloadable PDF. `resume_format.py` defines a small line-tagged text contract (`NAME:`/`SECTION:`/`ENTRY`/`HEADING:`/`BULLET:`/...) that's trivial to parse deterministically - chosen over asking the model for Markdown (ambiguous once resume content has its own "#"/inconsistent headers) or JSON (invites subtle parse failures on a long, multi-entry document). `job_applications.py::optimize_full_resume()` is one generation call, no second critique pass (resume bullets are already terse/action-verb-driven, not prose with the chatbot tells the critique pass targets; a second rewrite pass also risks corrupting the strict format). `resume_pdf.py` renders the parsed result to a real PDF via Playwright's `page.pdf()` (already a dependency, no reportlab/weasyprint needed) - a clean, professional, ATS-friendly layout built fresh from the content, not an attempt to recreate the exact typography of whatever PDF Duc originally uploaded (that would mean real PDF-editing work with its own failure modes). `webapp.py`'s `/api/job/resume-pdf/{filename}` serves the generated file - filename is validated (no path separators, must end `.pdf`) before touching the filesystem, since it comes straight from the URL. Two real bugs caught building this: (1) a 3000-token budget silently truncated a full resume mid-document - `optimize_full_resume()` now explicitly checks for `llm.TRUNCATION_MARKER` (a named constant, not a re-typed string) and raises `ResumeFormatError` rather than silently parsing a cut-off document; the actual call site (`webapp.py`'s dedicated `_resume_llm`) uses `max_tokens=6000`. (2) the model initially crammed a Project entry's tech-stack into `HEADING` instead of `SUBHEADING`, squishing the layout - fixed by adding an explicit worked Projects example to the format instructions, plus making the PDF's CSS resilient to long headings regardless (`flex: 1` heading, `flex-shrink: 0` date). Verified end-to-end with Duc's real resume and a real job context, through the actual HTTP endpoints (not just direct calls) - correct PDF downloaded, correct content, no invented facts (spot-checked numbers against the original), path-traversal/invalid-filename/not-found guards all confirmed. Test-generated PDFs cleaned up afterward each time (`data/generated_resumes/` isn't itself gitignored-vs-tracked differently from the rest of `data/`, but generated files there aren't meant to accumulate test noise any more than the other stores are).
- **A real PDF-extraction fidelity finding drove two follow-up features (2026-09-03)**: comparing pypdf's extraction of Duc's real (LaTeX-compiled) resume PDF against the visible content turned up genuine artifacts, not hallucination-prone but real - dropped underscores in inline code (`slack_sdk` extracted as `slack sdk`) and a spurious space inserted before ordinal superscripts (`27th` extracted as `27 th`). Both are characteristic of LaTeX-typeset PDFs specifically (superscript kerning, certain font/ligature encodings) - not a bug in `doc_text.py`, a structural limit of reading text back out of a compiled PDF at all. Two responses, not one: `github_profile.py` adds real supplementary project data (see two bullets below) so a resume draft has more to work with than a single, imperfectly-extracted source; and **`optimize_latex_resume()` (`job_applications.py`) edits Duc's original `.tex` source directly** rather than going anywhere near PDF extraction - `doc_text.py` now treats `.tex` as plain text (no parsing needed, it already is text), and the model is instructed to preserve structure/packages/commands exactly, touch only content, and explicitly keep each rewritten bullet roughly the original length ("this document has a fixed layout... a bullet much longer than before risks overflowing the template when compiled") - a direct response to Duc's own stated worry about alignment breaking on recompile. `material_type: "latex_resume"` is a third top-level path in `webapp.py::job_draft`, sharing a `_pick_resume_source()` helper with `full_resume` (same one-off-upload → selected-library-doc → pasted-text priority) but never touching `resume_pdf.py`. **Superseded by the one-page compile loop directly below** - `optimize_latex_resume()` (reword-in-place, fixed-length-preserving) is still in `job_applications.py` as a lighter-touch building block, but the web UI's `latex_resume` path now calls `optimize_latex_resume_one_page()` instead.
- **LaTeX one-page fitting is a real compile-measure-iterate loop, not a blind rewrite (2026-09-04)** - built after Duc gave direct negative feedback on the generic `full_resume`/`resume_pdf.py` PDF path (2 pages, skills rendered as one flat text blob - confirmed by reading the actual code: `resume_pdf.py` has no page-count target or shrink-to-fit logic at all, and `resume_format.py` explicitly treats a flat skills list as a single bare entry) and said he'd rather hand Kyra his real `.tex` and have her decide what to cut/keep to fit one page per role. The core problem: an LLM editing LaTeX text has no ground truth for whether the result compiles to one or two pages - that depends on font metrics, hyphenation, and package behavior invisible from the source alone. So this doesn't guess: `latex_compile.py` shells out to a real local LaTeX engine (`pdflatex`/`xelatex` - already installed via Homebrew/TeX Live on Duc's machine, no new Python dependency) in a scratch temp dir, reads the real page count back via `pypdf`, and `job_applications.py::optimize_latex_resume_one_page()` loops: generate → compile → if not exactly 1 page, feed the real page count back and ask for another cut (favor dropping a whole entry - an older project, a course, a weak bullet - over shrinking margins/fonts, which the prompt explicitly forbids touching) → recompile, bounded to `max_attempts` (default 4). A compile failure (bad LaTeX syntax from the model's own edit) gets its error log fed back for a fix-only pass rather than silently failing - `_extract_error_context()` pulls the actual `! ...` error block out of the `.log`, not just a blind tail, since real templates can bury the error thousands of lines into package-loading noise. Runs **fully automatically** (Duc's explicit choice over a propose-then-approve step) and picks the LaTeX engine automatically via `detect_engine()` (xelatex if the source uses `fontspec`/`setmainfont`/`polyglossia`/`unicode-math`, pdflatex otherwise) - also Duc's choice. On giving up without reaching one page, returns the closest real compiled attempt (fewest pages actually seen), never a document that was never compiled. `webapp.py::_latex_resume_draft` now returns both the edited LaTeX text *and* a compiled PDF preview (`pdf_url`, served through the same `/api/job/resume-pdf/{filename}` endpoint as `full_resume`) so Duc sees the real rendered result, not just trusts the source. Verified end-to-end with a real Claude call + real local compile on a synthetic 2-page resume (correctly cut to 1 page, correctly wove in a supplied "new coursework" fact, invented nothing) and again through the actual running HTTP endpoint (`curl` → real draft → real served PDF, inspected visually) - not just unit-tested in isolation. One real bug caught before it ever reached the live path: the initial `compile_latex()` had a leftover reference to an already-removed `log_tail` variable on the success return, which would have thrown on every single successful compile - caught by actually running the function, not by code review.
- **The one-page fit loop was rebuilt around a measured overflow signal (2026-09-04, evening audit)** after Duc's direct feedback that a resume still came back as 2 pages. Root cause wasn't the model: the loop only knew the *page count* (binary), never compiled the original for a baseline, and the shrink prompt asked for "the single least-relevant bullet" - so a large overflow never converged in 4 attempts, and a one-page original could come back longer with no budget telling the model not to grow it. Now: `latex_compile.measure_pages()` counts text lines per page from the real PDF (`PageMeasure`, `CompileResult.overflow_lines`); `optimize_latex_resume_one_page()` compiles the original first and puts a measured length budget in the first prompt, feeds "page 1 holds ~N lines, M spilled - remove at least K lines' worth" with an escalating margin into each shrink pass, picks the best candidate by (pages, overflow) not pages alone, and defaults to 5 attempts. `resume_guard.py` runs after every resume generation (Fast, Detailed, and the hidden `full_resume`) and flags any number/year/%/link in the output that isn't in the sources the model was given - the structural answer to the fabricated-entry bug two bullets down, since a prompt can't guarantee anything. `DraftOut`/`ResumeFitGenerateOut` now carry `fit`/`page_count`/`overflow_lines`/`notes` and the UI renders a red "✗ Not one page" / green "✓ Fits one page" banner plus a collapsible attempt log - a violated hard requirement must never look like success. Verified with a real Claude call on Duc's real resume + a realistic SDE posting: fit on attempt 1, guard clean, no `\resumeSubheading` added or removed. Full before/after/why in `docs/industry-standards.md`; open choices (touch layout as a last resort? make the guard blocking?) in `data/private_docs/needs-your-input.md`.
- **Resume-generation paths (`full_resume`/`latex_resume`) had a real gap: neither one looked at Memory Notes or free-text library documents at all (fixed 2026-09-04)** - Duc asked directly whether he could update resume generation "by words" (e.g. "I graduated," "I took these new classes") the way the plain chat/draft flow already lets him via `save_memory_note`. Checking the code confirmed a real gap: the plain paragraph-drafting path in `webapp.py::job_draft` already pulled in `_memory_notes.render()` and selected non-resume library documents, but `_full_resume_draft`/`_latex_resume_draft` never did - a fact saved via chat would silently never reach resume generation. Fixed by folding that gathering into `_pick_resume_source()` itself (now returns `(resume_text, extra_facts_text, warnings)` instead of just `(resume_text, warnings)`), so Memory Notes + any selected non-resume documents + pasted "Extra background" text all flow into both resume paths the same way they already did for the paragraph path. Verified for real: a synthetic resume draft correctly wove in a supplied "completed Advanced Cloud Computing" fact into the Education section, and correctly *ignored* Kyra's own seeded, resume-irrelevant memory notes (about building Kyra, about the interview) rather than forcing them in - confirming "use if genuinely relevant, don't force it" holds even when the facts are real and available.
- **The Memory Notes wiring above had a real, more serious follow-on bug: it fabricated a whole new resume entry (fixed same day, 2026-09-04)** - the very first real run against Duc's actual resume + a real job posting added a brand-new "Kyra | AI companion project..." Projects entry that was never in his original `.tex`, sourced from Kyra's own seeded memory note about herself ("Duc is building Kyra as an AI-pipeline learning project"). The fact was true, but it was never meant to become resume content, and it landed on a document meant for a real employer, unreviewed - "use if genuinely relevant, don't force it" wasn't a strong enough instruction once "genuinely relevant" is a real-sounding true fact. Root cause: extra facts were only told to "trace back to something true," never told they couldn't spawn a *new standalone entry*. Fixed in both `LATEX_ONE_PAGE_SYSTEM`/`PROMPT` and `FULL_RESUME_SYSTEM`/`PROMPT` (`job_applications.py`) with an explicit carve-out: extra facts may correct/extend a detail **inside an entry that already exists** (a graduation date, a GPA, one more course on an existing coursework line) but must never create a new job/project/certification/section, even true and relevant - that's Duc's call to add by hand, not something to infer automatically. Also stopped blending extra facts into the "original resume" text itself (`optimize_full_resume` now takes `extra_facts` as its own explicit parameter, matching how the LaTeX path already did it) - concatenating them into one blob was part of why the boundary blurred. Re-verified against the same real resume + real job posting that produced the bug: no fabricated entry, same real content, still one page.
- **`_resume_llm`'s token budget was raised 6000 → 16000 (2026-09-04)** after the LaTeX one-page path hit "the optimized LaTeX got cut off before finishing" repeatedly on Duc's real resume + a real job posting, even though the exact same 6000 budget had passed isolated testing earlier that day. Same root cause documented elsewhere in this file: Sonnet 5's adaptive thinking eats into `max_tokens` unpredictably, and every iteration of the one-page fit loop must return a **complete** document, not a diff - thinking plus a full multi-KB LaTeX output can together exceed a budget that looked generous in isolated testing but wasn't safe against real, larger inputs. `max_tokens` is a ceiling, not a reservation, so raising it costs nothing unless actually used - 16000 leaves large headroom over any real resume's output size.
- **The DRAFT tab's material-type dropdown was trimmed from 5 options to 4, then to 5 again with "Detailed" added (2026-09-04)**, removing `full_resume` ("Full resume, optimized (PDF)") - Duc's direct feedback ("I chose PDF and got the same PDF... others are kinda distracting") plus the already-known, undated formatting problems in that path (`resume_pdf.py` has no page-count target/shrink-to-fit logic, `resume_format.py` renders skills as one flat text blob - see the PDF-extraction-fidelity bullet above) meant it wasn't worth keeping as a visible option once the LaTeX one-page path existed and actually works on Duc's real template. The backing code (`optimize_full_resume`, `resume_pdf.py`, `_full_resume_draft`) is **not deleted** - still reachable by posting `material_type: "full_resume"` directly - just no longer surfaced in the UI, in case a future resume source isn't LaTeX and needs a fallback. The remaining/added resume options are labeled "Resume — Fast" (`latex_resume`) and "Resume — Detailed (pick & choose)" (`resume_detailed`, see below) - Duc's explicit ask: a fast automatic mode for mass-applying, and a slower reviewable mode, "others are kinda distracting" for that use case.
- **Fast mode's objective is now *tailor*, not *fit* (2026-09-05)** - a real diff showed the loop returning Duc's resume unchanged except for deleting every `%`-commented line (his stash of alternate bullets), and calling it a success because the original already fit. `LATEX_ONE_PAGE_PROMPT` now demands RE-RANK / REWORD / CUT toward the job; `resume_latex.restore_comments()` deterministically puts back any comment line the model drops (anchored after the nearest surviving line), and `content_diff()` measures bullet/heading changes so an unchanged pass-through is flagged as a `tailoring check` warning instead of reported as done. Both are post-conditions in code, per the standing rule.
- **`resume_guard.py` checks proper nouns too (2026-09-05)** - entry headings, course codes, and capitalized terms are diffed against sources, after a draft gained an "Operating Systems concepts" coursework line the number-only check couldn't see. Source comments count as evidence (a commented bullet in Duc's own `.tex` is real); output comments are stripped. Still warn-only by decision; the Kyra heading is *expected* to flag against the original resume. **Inflation qualifiers too (2026-09-06)**: after the Northwind run added `high-performance`/`large-scale`/`scalable`/`high-throughput` with no source, `INFLATION_QUALIFIERS` (a short module-level list) is diffed against sources case-insensitively and hyphen/space-insensitively - the one class of fabrication the capitalized-term check can't see. Still warn-only.
- **Fast mode needs a diff review before a resume goes out, and two of its failure modes are known (2026-09-06, Northwind new-grad SWE run)** - (1) **the library's LaTeX source went stale**: the `Resume (LaTeX source)` document (id `23dcbcdb8e42`, added 2026-09-04) predates the Kyra project entry, CS 169A and the reorganized skills block that every tailored resume since 2026-09-05 was built from; tailoring from it produced a one-page PDF with the bottom third empty. The current base is `data/resumes/Duc_Vo_Resume_General_AI_Engineer.tex`, passed as `background_text`, until Duc replaces the library entry. (2) **The loop cut the whole ICPC block** for a role where competitive programming in C++ is the strongest signal on the page, and dropped the Slack evaluation-loop bullet (calibration, decile analysis) that maps onto a probability/statistics ask - its relevance ranking is the model's, so read `content_diff`'s removed list against the posting and restore by hand. (3) **It added qualifiers not in any source** - `high-performance`, `large-scale`, `scalable`, `high-throughput`, `probabilistic modeling` - which `resume_guard.py` cannot see: it checks numbers, URLs, headings, course codes and capitalized terms, and these are lowercase adjectives. Stripped by hand; the guard gap is logged in `data/private_docs/needs-your-input.md`. The humanizer critique pass (`CRITIQUE_PROMPT`) run over the final bullets found only one hedge word, so the base bullets are clean and the drift comes from the tailoring pass, not the source. Final file: `data/resumes/Duc_Vo_Resume_Northwind_SWE_University_Graduate.{tex,pdf}` - one page, 45 lines, guard clean.
- **The resume fit loop's token ceiling has to grow with the base resume, and it silently failed again (2026-09-07)** - `_resume_llm` was raised 16000 → 32000 after every tailoring attempt on the current base died with `ValueError: the optimized LaTeX got cut off before finishing`. Same root cause as the 6000 → 16000 raise: each iteration must return a COMPLETE document rather than a diff, Sonnet's adaptive thinking is charged against the same ceiling, and the base `.tex` has grown to ~4.5k tokens (15,927 chars). Anything that calls `optimize_latex_resume_one_page` on the real base - the JOBS panel, the apply pipeline - hits this, so the budget is not a per-caller detail. `max_tokens` is a ceiling and not a reservation, so headroom costs nothing until used; when the base resume grows again, raise it again rather than shortening the source.
- **One resume per company: the tailored file travels with the tracked application (2026-09-07, Duc's rule)** - autofill used to attach `ApplicantProfile.resume_path` for every posting. `job_applications.resume_path` (Alembic `8f4f8496ae73`) now holds the company-tailored PDF, `SetApplicationResumeTool` sets it, and `job_autofill.resume_for_url()` resolves which file to attach: exact posting URL first (scheme/query/trailing slash normalized), then exactly one tracked company whose name appears in the URL slug, since Greenhouse and Ashby both put the company in the path. Ambiguity attaches nothing and says so - sending another company's resume is worse than sending the general one - and a company name under four characters must match by URL, because "AI" is a substring of "openai". A tailored path that doesn't exist yet is allowed (Duc may write it later); autofill falls back to the profile default and reports why. The response carries `resume_attached` and `resume_choice` so the choice is visible before he presses Submit. Two real defects fixed on the way: (1) `resume_path` pointed at `data/job_documents/files/52a3b69f225c.pdf`, and Playwright uploads under the basename, so every autofilled application sent a file named `52a3b69f225c.pdf` to an employer - it now points at a human-named file in `data/resumes/`, which is the rule going forward; (2) that PDF was the 2026-09-03 copy with no Kyra, CS 169A, LoRA or router content, as was the document library's LaTeX source that every JOBS-panel draft started from - both replaced from `Duc_Vo_Resume_General_AI_Engineer.tex` (compiles to one page, verified through `_pick_resume_source` itself).
- **Re-running an application reuses its resume, and renames it on the way out (2026-09-08)** - a tracked row is one company and one role, and the standing rule is one resume per company, so the file on the row already *is* that posting's resume; re-tailoring spent a multi-minute loop and a real bill to rebuild it. `apply_pipeline` reuses it unless `retailor` is passed, and a reused file **carries no fit verdict** (`resume_fit` stays None, `change_summary` says reused) because nothing was compiled or guard-checked on that run - reporting one page for a document this run never measured is exactly the kind of unearned check the guard work exists to prevent. This matters immediately: the stale Ashby rows sit at `needs_attention` only because no Ashby engine existed when they ran, and all four already have both `.pdf` and `.tex` on disk, so re-running them is now nearly free. **The reuse also exposed a real interaction bug**: those four files predate the same day's `Duc_Vo_` naming decision, so reuse would have attached the `Minh_Duc_Vo_` prefix that decision removed - to an employer, silently, on precisely the applications it was meant to fix. `_rename_to_convention()` renames the pair to the current `resume_stem` at reuse time rather than as a one-off cleanup, so it stays true the next time the convention moves; a correctly-named file that already exists wins and the stale copy is left alone rather than overwritten. **Reviewing that rename found a destructive bug in it**: `set_application_resume` accepts any path and `Settings.resume_base_tex` lives in the same directory, so a row pointed at the general resume would have had `Duc_Vo_Resume_General_AI_Engineer.{pdf,tex}` renamed to a company name - taking the `.tex` every future tailoring reads with it and breaking mass apply silently until the next run failed. Renaming is now confined to a file that is *this application's* under an older prefix, which is what sharing a `_Resume_<company>_<role>` tail means. The general lesson: a convenience that renames a file has to prove the file is the one it thinks it is, because the directory also holds inputs.
- **Invented numbers are removed, not just flagged (2026-09-06, Duc's rule: never a number that is not his without asking)** - `_finalize_fit` now runs `_remove_invented_numbers`: any number the guard finds outside the sources triggers one fix pass (`LATEX_NUMBER_FIX_PROMPT`), recompiled for real and kept only if it compiles to no more pages; if the pass fails the original stays and the guard warning stands, so nothing is hidden. Alongside it `metric_questions()` asks the model to list bullets without a measured result and the question Duc should answer - the parser accepts only `BULLET: … | ASK: …` lines, so a suggested value cannot slip through as a question. The tailoring prompt carries the formula from Duc's note (strong verb + what + measured result) with 'no new numbers, ever'. `resume_guard.py` itself was not touched (a separate session was extending it at the time). Verified with a real Claude run on the Northwind posting: fit on attempt 2, no invented numbers, one honest question back (the OpenRouter routing bullet has no measured result). Also from the notes: the board watch treats a re-listed title as a `REPOSTED` high-priority signal and uses Greenhouse `first_published` so age means what the note means; Greenhouse `updated_at` is a last-edit date and would hide a stale post.
- **The `full_resume` HTML/Playwright path was deleted (2026-09-05, Duc's decision)** - `resume_pdf.py`, `resume_format.py`, `optimize_full_resume`, `_full_resume_draft` and their tests are gone; `paths.GENERATED_RESUMES_DIR` now owns the PDF output directory. It was the only non-LaTeX resume source; if one is ever needed again, build it on the compile-measure loop, not the old renderer.
- **Resume "Detailed" mode - fit-scored, section-grouped content selection, built and verified 2026-09-04** (`docs/agentic-roadmap.md` had the design sketch; this is the real build). Two new stateless JSON endpoints, `POST /api/job/resume-fit/analyze` and `POST /api/job/resume-fit/generate` (`webapp.py`), backed by `job_applications.py::analyze_latex_resume_fit()` and `generate_latex_from_selection()`:
  - **Analyze**: one Claude call rates every real bullet/entry/skills-line/coursework-line in the LaTeX source against a job context as strict JSON (`FitBlock`: id, section, entry, kind, label, score 0-100, priority High/Medium/Low, reason, recommended_keep). Every Education/Experience/Projects/award **entry** gets its own whole-entry row *in addition to* its individual **bullet** rows (all sharing one `entry` label) - a parent-plus-children shape, not a flat list, so the UI can render "drop this whole job" and "keep the job but trim these bullets" as two different, obvious actions. A **detail** row (a coursework line, a skills category line) has no separate parent.
  - **UI**: the checklist groups by section (Education/Experience/Projects/...) then by entry within it, each row a checkbox pre-checked per `recommended_keep` plus a colored pill badge (`--fit-high`/`--fit-medium`/`--fit-low` CSS tokens: green/amber/muted-grey, not the theme accent) reading "N% fit — Priority" and a one-line reason - Duc's own answer when asked how to convey "how necessary" a part is, with an explicit ask to keep sections visually separate so it doesn't turn into one confusing flat list.
  - **Generate**: edits the LaTeX to match exactly what's checked, hierarchically (an entry marked CUT removes the whole thing regardless of its bullets' own marks; an entry marked KEEP keeps its heading but only the bullets also marked KEEP), compiles for real, and **never cuts more than what Duc unchecked** even if the result doesn't fit one page - Duc's explicit answer to "what happens on overflow" was "tell me what to cut next," not auto-trim. Overflow instead resurfaces the still-kept blocks sorted by their own analysis score (lowest first) as `cut_suggestions` - free, no extra LLM call, since the scores are already known from analysis.
  - **Real bugs caught building this, not just theoretical**: (1) the analyzer initially only rated bullets/whole-entries with no shared grouping key, so the UI couldn't tell which bullets belonged to which job - fixed by requiring every entry row and its bullet rows to share one `entry` label. (2) the very first real generate-from-selection run on Duc's actual template failed to compile ("missing \item") - root cause: the analyzer had misclassified an intro sentence that precedes Escaype's bulleted list (real content in this template, but not wrapped in `\resumeItem`) as a "bullet," and the generator inserted a bare `\item` to represent keeping it, which doesn't belong in this template's structure at all. Fixed two ways: the analyze prompt now explicitly excludes non-bullet-wrapped intro text from bullet rows (it stays attached to its entry, not independently selectable), and the generate prompt now forbids inserting any structural command that doesn't already appear in the original for that kind of content - copy the original's own LaTeX verbatim when unsure. (3) cutting every entry within a section (e.g. dropping the only Project) left an empty `\section{Projects}` heading with nothing under it in the compiled PDF - fixed with an explicit instruction to also remove a section's heading when every entry within it is cut. All three re-verified with real Claude calls, a real local compile, and a real browser click-through (not just curl) after each fix.
  - **A real browser-caching bug was found and fixed while verifying this in the browser** (unrelated to the feature itself, but real): editing `web/app.js`/`web/style.css` and reloading - even a hard reload - didn't reliably pick up the changes; the browser (this held for the automated test browser, and would hold for a real one too) kept serving a stale cached copy despite `StaticFiles`' ETag/Last-Modified conditional-GET machinery. `webapp.py::index()` now reads `index.html` per-request and injects each static asset's real file mtime as a `?v=<mtime>` cache-busting query string, rather than a hand-maintained version string that would just go stale the next time someone edits those files and forgets to bump it.
- **GitHub is a real, live data source for drafting (`github_profile.py`); LinkedIn deliberately isn't, and that's a constraint, not a gap to fill later.** GitHub's REST API is public and needs no auth for public repo/README data, same "official API, not scraping" reasoning as `feeds.py`'s tech news (see that decision above) - `fetch_github_projects()` pulls real repo name/description/language/README excerpt (forks excluded, sorted by most-recently-pushed), never invented. LinkedIn has no equivalent for a personal script - reading a profile's real work history needs either LinkedIn's official OAuth app-approval flow (built for companies, not a personal project) or scraping the page directly, which violates their Terms of Service. Opted into "tell Duc plainly and point him at pasting his LinkedIn text into the document library himself" rather than building something fragile or ToS-risky - if this ever needs revisiting (e.g. LinkedIn ships a real personal-data export API), reconsider then, don't route around the ToS constraint now.
- **`include_github` is opt-in per draft (a checkbox), not automatic** - it's a real network call each time, and forcing it into every draft would mean every cover letter/resume silently depends on GitHub being reachable.
