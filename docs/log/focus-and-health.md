# Focus blocks and the health arc

`focus.py`, the FOCUS panel, the blinded n=1 experiment, and the two health/attention plans.

Entries below were moved verbatim from `CLAUDE.md` on 2026-09-09 (original order kept, newest work is usually nearer the top of each section). Add new entries at the top of this file, dated, with the *why*.

## Entries

- **FOCUS panel + focus blocks (2026-09-08, slices 0-4 of `docs/plans/2026-09-08-attention-environment.md`)**: a fourth slide-in panel (FOCUS button, top right, reusing the JOBS panel's classes) plus `start_focus_block`/`end_focus_block`/`focus_status` in `default_tools.py`, over `POST /api/focus/start|end|probe` and `GET /api/focus/active|history`. A block is a timed stretch with one of four sound conditions, break cues, and a 60-second reaction-time probe at each end; `python3 scripts/focus_report.py [--min-blocks N] [--json]` reads them back per condition. All audio is synthesised in `web/app.js` from oscillators and filters (pink noise by Paul Kellett's filter, a 16 Hz amplitude-modulated pad, a two-carrier binaural pair) - there is no track list, which is how "no lyrics" is a property rather than a rule.
- **Focus blocks: the defaults are removals, the additions are an experiment (2026-09-08)** - built from the evidence review in `docs/plans/2026-09-08-attention-environment.md`, whose finding is that almost everything that reliably helps attention is a *removal* (no lyrics, no speech, no evening blue, no 30 minutes without a break) while every addition is small, vendor-adjacent or single-study, and broadband noise **flips sign** between listeners with and without attention difficulties. So `focus.py` does two separate things. The removals are post-conditions with tests: `CONDITIONS` holds synthesis specs rather than file paths (`test_no_condition_can_reference_a_file_or_url`), `FocusPlan.__post_init__` refuses a gain over `GAIN_CEILING`, a break gap over `MAX_MINUTES_WITHOUT_BREAK` or a missing fade, and the browser's gain comes from the server rather than a slider. The additions are a blinded n=1 experiment: `ScheduledPlanner` block-randomises four arms (each cycle of four holds each arm once, shuffled per cycle from the completed count alone, so the arm cannot track the time of day and the schedule needs no stored state), a PVT probe runs at both ends, and `build_report`'s `verdict()` refuses to rank until every arm has 8 blocks **and** the best-to-second gap exceeds the widest within-arm spread - the same lesson already paid for twice here (router round 4's 4-point seed swing, the search eval's 3.8-points-per-query). **The blind is structural at the HTTP boundary and conventional beyond it**: `_focus_payload` strips `condition` from both the plan and the session while a block runs and `/api/focus/end` returns it, so the panel cannot print the arm by accident, but the synthesis spec has to travel (the browser makes the sound) so devtools would still unblind - `render_report` says exactly that beside its numbers. `FocusPlanner` is the usual Strategy shape so "Kyra learned what works" can replace "Kyra is running an experiment" without touching the tools, the endpoints or the browser.
- **Two front doors disagreeing about whether Duc is working (2026-09-08)** - `start_focus_block` on the tool path is reachable by voice and by typing, and the browser had no way to learn about it: the server would have a block running while the HUD sat idle with no sound, no clock and no break cue, and the reverse after an `end_focus_block`. `focusSync()` re-reads `GET /api/focus/active` after every chat and voice turn and adopts or drops the block to match, which is cheap because a turn has just happened and the server is the source of truth either way. Verified through the real UI with a real Claude turn: typing "start a 25 minute focus block on testing the sync" routed to the tool path and the header chip started ticking with the pink-noise layer playing, having done nothing in the browser. **The break cue also had to survive a hidden tab** - it is the best-supported intervention in the whole review, and a cue Duc cannot see because he is in another tab is not a cue, so it also fires a `Notification` when permission exists. Permission is requested when he starts a block, never on page load, and the whole path is guarded: in a browser that denies it (the automated one does) the in-page cue still stands. The same guarded helper fires when the block *ends*, which is the cue that actually needs him. **And wind-down has to arrive on its own**: the evening theme was only applied on a turn, so an evening spent reading would have stayed on the daytime palette, which is the single thing the evening rule exists to prevent. A slow `setInterval(focusSync, 5 min)` asks the server rather than duplicating `WIND_DOWN_HOUR` in the browser, and keeps the block state in step with the other front doors for free. Verified by faking the server's answer both ways through that same path and reading the painted accent back: 150.7 against 157.2.
- **Three real defects the browser found that no unit test would have (2026-09-08)** - (1) **the probe hung forever on an unanswered dot**: `finish()` was gated on `&& !lit`, so a dot still lit when the 60 s timer expired blocked the end of the run, and since the end-of-block probe precedes `POST /api/focus/end`, *the block was never recorded at all*. Fixed as real PVT behaviour - an unanswered trial times out at `PROBE_TIMEOUT_MS` and counts as a lapse - which also stops a mid-run stall when Duc simply misses one. (2) **the evening palette was brighter than the day palette.** `--accent: #ff9d4d` looked warmer and measured 172.1 relative luminance against the AUTO backend's violet at 157.2; orange carries more luminance than cyan or violet at the same apparent vividness. `tests/test_evening_theme.py` parses the real stylesheet and asserts it, on two metrics because they answer different questions: relative luminance ("is the screen dimmer") and blue channel (the melanopic proxy, which is what actually suppresses melatonin). **The first version of that test was vacuous** - it compared only against `:root`'s cyan (181.6), which the defect passes, and it took reintroducing the defect to notice; `--accent` is redefined per backend, so the evening accent is now compared against the dimmest accent any backend can be showing. (3) **a tool promised a break that would never fire**: `start_focus_block` returned `break_every_minutes: 25`, and on a 25-minute block `break_offsets` is empty (a cue never lands on the end), so a real Claude turn told Duc "I'll cue a break". It returns `break_cues_at_minutes` now, and a real turn says the cues for a 90-minute block and promises nothing for a 25.
- **A measurement is only as good as the environment it was taken in (2026-09-08)** - the probe's first real run stored a 2,000 ms median against a scripted 250 ms response, which read exactly like an arithmetic bug in the RT maths. It was not: a `setTimeout` nested inside a `setInterval` is clamped to ~1000 ms in a hidden tab, while a top-level awaited `setTimeout` is not, so the first diagnostic ("timers are accurate") was measuring the wrong kind of timer. A MutationObserver on the target gave ground truth and the stored median matched it to 0.1 ms. The fix is not in the maths but in the guard: `runProbe` refuses to start while `document.hidden` and says so in the transcript, and a `visibilitychange` mid-probe discards the run rather than saving a number about the browser as though it were a number about Duc.
- **Attention through the environment (2026-09-08, plan only)**: `docs/plans/2026-09-08-attention-environment.md` - the daytime half of the health arc, researched paper by paper. What holds up is mostly removal (no lyrics or speech in focus audio, no evening blue, a break every 25-30 min); the additions (broadband noise, 16 Hz amplitude modulation, binaural beats, 40 Hz) are small, vendor-adjacent or single-study, and broadband noise flips sign between attention-difficulty and typical listeners. So the defaults are post-conditions and the additions are a blinded n = 1 experiment: focus blocks with a procedural audio layer under a gain ceiling, a 60 s reaction-time probe at both ends, one self-report, and a per-condition report with the noise floor stated. The headset can only darken or tint passthrough, never brighten it, so the alertness half of the light evidence needs a bulb (Duc's call, #24). Nothing built; `apple/KyraVision` builds for the visionOS 26.5 simulator (Xcode 26.6 is installed now, the day-one plan's "not installed" line is stale).
- **Health companion (2026-09-07, plan only)**: `docs/plans/2026-09-07-health-companion.md` - hydration/activity/sleep with light and sound, headset-first (the Vision Pro dims the room, the AirPods carry a faded-out sleep sound, the iPhone runs the night; no bedroom hardware). The one architectural fact it rests on: Apple Health is the integration point (every bottle, ring, watch and AirPods writes there; HealthKit and HomeKit are both on visionOS 1.0+), and HealthKit data never leaves the device, so the health half lives in the Apple app and the Mac server only receives consented summaries as memory notes. Nothing built yet; slices 2, 3 and 6 need no purchase. **Band decided 2026-09-08: Garmin vívosmart 5** ($150, no subscription) - and checking the vendors' own support pages to write the arrival checklist corrected a real error in the plan's own table: **no third-party band puts HRV into Apple Health.** HealthKit's only HRV type is `heartRateVariabilitySDNN` and every recovery wearable except the Apple Watch computes RMSSD, so writing it would misstate it and the vendors decline - the exact reason WHOOP was rejected, which the table had then failed to apply to Garmin and Polar. Garmin sends sleep analysis (stages since Connect 4.71), all-day heart rate, steps, distance, energy, **water** and workouts, and nothing else; Polar sends less still (no stages, no continuous HR). Two operational traps from Garmin's page: **Connect must be open in the foreground to push**, and Health shows only the highest-priority source per type. Rule this generalises: a sync table built from reviews is a guess - read the vendor's own support page before a criterion decides a purchase.
