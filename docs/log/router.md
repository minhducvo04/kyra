# The per-turn router

`router.py`, the classifier, the LoRA fine-tune rounds (`router_ft.py`), the tool-calling distillation (`agent_ft.py`, `local_tools.py`), and the rule for when a retrain is needed.

Entries below were moved verbatim from `CLAUDE.md` on 2026-09-09 (original order kept, newest work is usually nearer the top of each section). Add new entries at the top of this file, dated, with the *why*.

## Entries

- **Initiatives tool, measured before it exists (2026-09-09)**: per the rule from round 5, the production adapter (`qwen1.5b-v4-s13`) was run on ten handwritten cases for a planned `suggest_initiatives` tool (`tests/data/router_testset_initiatives.jsonl`, committed before any data was generated): five asks for a suggestion, three text near-misses, two other-tool near-misses. **70% overall, 80% path-only.** It already sends three of the five asks to the tool path with no such tool in the registry; it misses "if you were me what would you pick up next" and "what's worth doing next on the project" (both text/claude), and sends the D&D "initiative" near-miss to claude instead of local. Decision: **no retrain now**. Ship the tool, watch real turns, and fold the two misses into the next adapter round with two seeds; a two-case gain is inside the noise round 5 measured. Run against the real `data/`, `router.log` stayed at zero lines because `evaluate()` calls the classifier directly. Output: `data/router_ft/eval-initiatives-2026-09-09.json` (gitignored).
- Text chat: `python3 scripts/chat.py` — defaults to `--backend auto` (the `TurnRouter` decides claude/local/tool per turn). `--backend claude`/`--backend local` forces one backend for the whole session and skips the router entirely.
- In auto mode on any front door: say "focus mode" / "chill mode" / "auto mode" to change the sticky session mode, or "ask claude" / "use local" in one message to override just that turn.
- Usage-pattern check: `python3 scripts/analyze_patterns.py [--days N] [--threshold N]` — counts repeated tool usage in `data/router.log` over a rolling window (default 7 days / 3x), and on a real hit spends one Claude call turning it into an observation saved to `data/pattern_observations.md` + `memory_notes` (category `observations`). Manual for now, no cron/launchd wiring yet. See `docs/agentic-roadmap.md`, "Usage-pattern observation."
- **Router round 5 (2026-09-08) measured that the retrain was not needed, and qualified the standing rule**: `search_kyra_data` and `set_application_resume` had no training data, so per the rule they got a round - four new categories (tool ×2 plus lookup bait, claude and local), 18 more handwritten held-out cases committed before any data was generated, 1,699/188 rows, two seeds. **The adapter that had never seen either tool already scored 11/13 on the new cases**; round 5 moved that to 12/13, one case. And it is a trade, not a gain: v4-s13 and v5-s13 make exactly five path errors each on 85 cases, with v5 fixing one new case while breaking two advice-bait cases v4 got right ("what does a good STAR answer for Ownership look like", "what does a reposted job usually mean") - the very cases round 4's advice bucket existed for. **Adding categories has a budget.** So the rule "when a tool is added, the adapter has to be retrained" is too strong; the honest version is **measure the current adapter on handwritten cases for the new tool first, and retrain only if it actually fails them**. **Not activated** - `KYRA_CLASSIFIER_ADAPTER` still points at `qwen1.5b-v4-s13`, since path accuracy (the metric that decides whether a tool loop runs at all) is identical at 94.1% and a wash does not justify the two regressions; `qwen1.5b-v5`/`-s13` are on disk and the switch is one line in `.env`. One phrasing no adapter of any round gets right: "what does CLAUDE.md say about the resume token budget" goes to text - it wants its own seeds next round. Numbers and the full trade: `docs/router-finetune.md`, round 5.
- **The classifier now loads at server startup, not on the first thing Duc says (2026-09-08)** - `TurnRouter.warm()` on a background thread from the FastAPI startup event (`KYRA_WARM_UP_ROUTER`, default on, forced off in `conftest.py` because starting the app in a test must never load a model). Measured 2.4s on a real start with the server answering throughout; a genuinely cold page cache made it 44s once, which is why it must not be paid mid-conversation. It calls `_classify`, **not** `route`: route() files the decision into `data/router.log`, and `analyze_patterns.py` reads that log as real usage, so a warm-up nobody asked for must not appear there. Pinned by a test.
- **A generator that returns nothing must fail, not shrug (2026-09-08)**: `router_ft.generate_synthetic()` retries twice and then raises. `parse_json_array()` returns `[]` for any reply it cannot read, and on the first round-5 run two of four new categories came back `got=0` where the next run gave 60 - a category that silently contributes nothing is exactly how a tool ends up untrained while the run still looks like it worked, which is the gap round 3 existed to close.
- **The router did not need retraining, measured before assuming (2026-09-08)** - per the corrected round-5 rule, `qwen1.5b-v4-s13` (which has never seen these tools) was measured on 14 handwritten cases first: **9/9 on the tool phrasings** for all three focus tools and 4/5 on bait, **13/14 = 92.9%**, so no round 6. The one miss is `"I can't focus today"` -> tool, which is arguably the more useful answer and is exactly the kind of ambiguous bait round 5 showed costs two advice cases to fix. Measured through `_classify`, not `route()`, so the batch left `data/router.log` empty.
- Tool-calling distillation (`src/companion/agent_ft.py`, `scripts/tool_ft.py`): `gen` (Claude writes messages per category) → `trace` (Claude's real tool loop against a `FakeRegistry`, recorded) → `build --name X` (mlx-lm rows, one per assistant turn, with a row-token report) → `train --name A --model <repo> --data X --iters N` → `eval [--teacher] [--zero-shot <repo>] [--adapter A:<repo>] [--prompt specialist|production]`. The held-out suite is `tests/data/tool_testset.jsonl` (70 handwritten cases). Results and the verdict: `docs/tool-calling-distill.md`.
- Router fine-tune (`src/companion/router_ft.py`, `scripts/router_ft.py`): `gen` (Claude → `data/router_ft/synthetic.jsonl`, deduped and scrubbed against the held-out set) → `build [--limit N --name X]` (mlx_lm chat-format `data-X/{train,valid,test}.jsonl`) → `train --name A --model <mlx repo> --data X --iters N` (`python -m mlx_lm.lora`, LoRA adapter under `data/router_ft/adapters/A`) → `eval --baseline --adapter A:<repo> [--zero-shot <repo>]` (accuracy / path-accuracy / latency / prompt tokens on `tests/data/router_testset.jsonl`, results → `data/router_ft/eval.json`). Activate an adapter in production with `KYRA_CLASSIFIER_ADAPTER="<repo>:<adapter dir>"` (router.py reads it; compact prompt replaces the few-shot one).
- **The router's classifier prompt needs concrete examples, not just a rule description** - a first version without few-shot examples missed "what's the tech news today" as a tool call entirely (correctly understood the *intent* per its own stated reason, wrong `path` field regardless). Adding examples fixed it but initially over-corrected the other way, hallucinating a tool match for "draft a cover letter" (no such tool existed in the registry *at the time*) - fixed with an explicit "only if it matches a listed tool, task-shaped isn't the same as tool-shaped" instruction plus negative examples. **That example is now stale in the opposite direction**: once `draft_application_material` was built (2026-09-03), "draft a cover letter" *should* route to `tool` - the example was updated accordingly, and re-tested against a mixed batch, not just the one case. If you touch `CLASSIFIER_PROMPT` in `router.py`, re-run a mixed batch of tool/text-claude/text-local inputs, not just the one case you're fixing - this class of prompt edit fixes one case and silently breaks another more often than not with small models, and stays stale in the other direction once a new tool is added that changes what "no matching tool" means.
- **A local model was trained to take over tool-calling and the answer was still no (2026-09-06, `docs/tool-calling-distill.md`)** - the 2026-09-02 benchmark left "could Qwen2.5-7B be the Agent Specialist?" open on an 11-case suite. This settled it properly: a 70-case handwritten held-out suite (50 tool incl. 13 multi-call find-then-act/two-tool, 20 that must call nothing), a `FakeRegistry` over the real schemas that records calls and rejects bad arguments exactly as the real one does, ~1,650 Sonnet 5 traces through the production tool loop, and a LoRA on Qwen2.5-7B. **Teacher 90.0% / best student 80.0% on the same prompt**, with the student still over-triggering on 1 no-tool case in 20 - short of the bar set beforehand (≥95% of the teacher, zero over-triggers), so **Claude stays the Agent Specialist and nothing was wired into the router**. `local_tools.py::LocalToolLLM` exists and implements the same `respond_with_tools` contract over Qwen's `<tool_call>` format, ready behind the interface if a later round clears the bar. What the training *did* fix is real: multi-call misses 10 → 4, no more invented ids, no duplicate calls. Three findings worth keeping: (1) **the specialist training prompt biased the student toward calling** - the same adapter over-triggers 20% under it and 5% under the production prompt, and scores *higher* in production, the opposite of the usual over-fits-its-prompt worry; (2) **expanding a trace into one row per assistant turn silently skewed class balance** (a 2-call trace makes 3 rows, a no-tool trace makes 1), so the first decision said "call a tool" 80% of the time - rebalancing to 49% was worth 8.6 points and killed the duplicate-call behaviour; (3) **in mlx-lm one `--iters` step is one batch and `--grad-accumulation-steps` only delays the update**, so at batch 1 iters == rows and an epoch here is ~2,350 iters, not ~590. Batch 1 itself is forced by memory: a tool row with a listing result is ~3.4k tokens vs the router fine-tune's ~100, and batch 2 ran the GPU out of memory on step 1 (fixed with `--grad-checkpoint`, ~10.6 GB peak). Also shipped from this work: `cache_control` on the last tool schema in `respond_with_tools()`, so the ~2,020-token schema block is cached on every production tool turn.
- **The router classifier is being replaced by a LoRA fine-tune, measured against a handwritten held-out set (2026-09-05)** - the few-shot `CLASSIFIER_PROMPT` costs ~900 tokens on every turn; a 0.5B-1.5B model trained on the same decision should reach the same accuracy from `router_ft.COMPACT_SYSTEM` (~60 tokens) faster. `tests/data/router_testset.jsonl` (61 cases incl. keyword-bait hard negatives like "remind me how quicksort works") is handwritten, never generated, never trained on, and never used to pick a checkpoint - `generate_synthetic()` drops any synthetic message that normalizes to a test message. Training data is Claude-generated per category (`CATEGORIES`), deduped. `LocalLLM(adapter_path=...)` and `TurnRouter(adapter_spec=...)` keep the Strategy shape: the adapter is a config value, not a code path. **Measured 2026-09-05 (`docs/router-finetune.md`):** production few-shot 3B = 73.8% / 85.2% path-only / 0.58 s / 2,051 prompt tokens; best adapter `qwen1.5b-hn` (LoRA on Qwen2.5-1.5B-4bit, 1,035 train examples incl. 151 keyword-bait negatives) = **88.5% / 93.4% / 0.15 s / 122 tokens**; zero-shot control on the same model + prompt = 27.9%, so the gain is the adapter. Round 1 without bait data scored 86.9% with 7 of 8 misses being keyword-bait over-triggers - the data fix, not model size, was the lever. **Activated in production** via `KYRA_CLASSIFIER_ADAPTER` in `.env`; the adapter lives in gitignored `data/router_ft/adapters/` and is reproducible with the four `router_ft.py` commands (~10 min on the M5 Max). Verified through the real `TurnRouter` path (env-driven, no `adapter_spec` arg): 54/61 = 88.5%, identical to the harness. `router.py` now reads the env var at construction and imports `companion.config` first so `.env` ordering can't hide it. Unset the variable to fall back to the few-shot path. **Round 3 (2026-09-07):** the seven tools added 2026-09-06/07 (outreach ×5, `analyze_job_posting`, `target_job_posting`) were never in the adapter's data, and the salary question "what's a good salary range for a new grad SWE in NYC?" over-triggered to the tool path. Added 9 `CATEGORIES` buckets (7 tool + 2 bait), 11 handwritten test cases (72 total), one clause to `COMPACT_SYSTEM`, retrained as `qwen1.5b-v3`: **93.1% on 72** vs the old adapter's 87.5% under its own prompt (91.7% under the new one); 11/11 on the new-tool cases, salary question fixed, but two old cases regressed ("note for later: I hate early morning meetings" -> text; "what does a good STAR answer..." -> tool) and "what does a reposted job mean" still goes to tool through the real router. Activated in `.env`; `qwen1.5b-hn` is the rollback. **When a tool is added, the adapter has to be retrained** - add a category + bait bucket, extend the test set by hand, `gen --categories ... --out X.jsonl`, `build --sources synthetic.jsonl,hard_negatives.jsonl,X.jsonl`, train, eval against the previous adapter. Details: `docs/router-finetune.md`, round 3. **Round 4 (2026-09-07) corrects that headline**: retraining the *same* round-3 data under a second seed scores 88.9%, so the 93.1-vs-91.7 margin was noise and the real noise floor here is ~±4 points on 72 cases - round 3's tool *coverage* (11/11 new tools) was the real reason to ship it, not the accuracy. Round 4 added a `text_hard_negative_jobsearch_advice` bucket (the STAR/repost/salary advice class), widened `save_memory_note` seeds to the "note for later: ..." shape, and a **second held-out set** (`tests/data/router_testset_holdout2.jsonl`, 17 cases, written and committed before the data was generated; the generator blocks both sets and a test asserts they are disjoint). Result: `qwen1.5b-v4-s13` is **seed-stable** (91.7% at both seeds vs v3's 93.1/88.9 swing) and 100% at both seeds on holdout2 vs v3's 100/82.4. Shipped it on a stated tie-break (equal accuracy -> higher path-only, 95.8%), which is itself checkpoint selection and therefore optimistic - the honest number is 91.7%. Verified 13/13 through the real `TurnRouter`. **When adding a tool, train two seeds and read both** - a single-seed comparison on 72 cases cannot see a 4-point effect.
- **The classifier only ever sees the current message, never conversation history** - a known, real limitation, not yet fixed. Context-dependent turns ("yeah I remembered that one" following Kyra asking about a review) misclassify because the classifier has no way to know what it's a reply to. Adding history would fix it but costs more tokens/latency on every single turn for a case that's relatively rare - not worth it unless it turns out to matter in practice.
- **`CLASSIFIER_MODEL` (`Llama-3.2-3B-Instruct-4bit`) is empirically justified, not just the original untested pick** - see `docs/router-model-benchmark.md`. Benchmarked against 3 smaller candidates; 3B wins on accuracy (96.6%) after a real prompt bug the benchmark caught got fixed (see `CLASSIFIER_PROMPT` two entries up). Qwen2.5-1.5B is a documented, real fallback if classifier latency ever matters more than its ~10pp accuracy gap - a one-line change, not a redesign. Separately, local models (Qwen2.5-7B+) were flawless at the Agent Specialist's job (tool selection + arguments) on an 11-case suite - promising, but the suite's small and the Agent Specialist role stays Claude's until a harder suite backs a change. Also found: Qwen/Llama/Mistral each render function-calling in a different, incompatible format from their chat templates - a real cost of ever moving tool-calling local that a single Claude API sidesteps.
