## Entries

- **Outreach assist (2026-09-06, slice 1 - chat tools only)**: five tools in `default_tools.py` from `src/companion/outreach.py` - `add_outreach_contact`, `draft_outreach_note` (connection note ≤200 chars + follow-up, in Duc's voice via the `writing_voice` memory notes, through the same humanizer `CRITIQUE_PROMPT` as cover letters), `copy_outreach_note` (pbcopy + `open` the profile - Duc pastes and presses Send), `update_outreach_status` (`sent` schedules a follow-up reminder 4 days out in the shared `RemindersStore`), `list_outreach` (`due_only` for overdue follow-ups). Store: `data/outreach.db` (`outreach_contacts`, Alembic `5e0d66b61880`). The tracker gained `targeting` (outreach before applying) and `referral_pending` (applied, referral in flight) statuses; `add_job_application` accepts `status`. Slice 2 (JOBS-panel Outreach tab, digest section) is in `docs/plans/2026-09-06-outreach-assist.md`.
- **Outreach slice 2 (2026-09-08): the JOBS panel's OUTREACH tab, over the same tool objects the chat path uses** - `GET/POST /api/outreach`, plus `/{id}/draft`, `/{id}/copy` and `/{id}/status`, each a `_registry.run(...)` rather than a fresh `OutreachStore` call. That matters because the logic lives in the tools: drafting reads the linked application's status so a note can never claim Duc applied when he is only targeting, and `sent` schedules the follow-up reminder the digest surfaces. Two front doors, one implementation - the same reason `default_tool_registry()` exists after the three front doors really did drift. The one adaptation at the HTTP boundary is the error convention: a tool returns `{"error": ...}` because that is what a model reads, so `_outreach()` turns "no outreach contact with id N" into a 404 and everything else into a 400 rather than answering 200 with an error body. The tab reuses the tracker's item classes, like the TOOLS panel reuses the JOBS panel's; the only new shapes are the note blocks and a 3-line clamp on the role line, because a real outreach `role` often holds a paragraph of context that would otherwise bury every other contact.
- **The dash rule is a post-condition now, not a prompt request (2026-09-08)** - the first real draft through the new tab came back with `cutting deploy times - what turned out to be the bottleneck` *after* the humanizer critique pass had already run, which is exactly the ASCII stand-in CLAUDE.md warns a single pass misses. `outreach.py::has_dash()` catches em-dash, en-dash and a spaced hyphen (a hyphenated word like "new-grad" is not one), and `draft_outreach_note` does one `DEDASH_PROMPT` rewrite after the length check. It never raises - a usable draft with a flagged dash beats no draft - so a dash that survives comes back in `OutreachDraft.warnings`, which the tool returns and the panel prints as an error line. Verified on a real redraft: both note and follow-up clean, the personal angle still used. **If another outbound path grows its own drafting call, it needs this check too**; today only outreach has it.
- **Outreach assist never touches LinkedIn, by decision (2026-09-06)** - Duc asked for automated "connect + add note" and automated people discovery. Both were declined as features: LinkedIn's User Agreement bans automation that interacts with the site, the project already refused to scrape it for profile data on the same ground, and an automated browser on Duc's real account is the one thing here that could get a real asset restricted mid job-search. What is automated is the writing, the tracking and the follow-up timing; delivery is `OutreachChannel` → `ClipboardChannel` (Strategy shape), with a Playwright fill-never-send channel possible behind the same interface only if Duc accepts the account risk in writing. Who to contact is Duc's pasted list. Three things the first real run (a real contact, anonymized here and in the tests) taught, all now in code or prompt with tests: (1) the note said "I just applied" when the tracker said `targeting` - the draft tool now reads the linked application's status and the prompt carries an explicit applied/not-applied line; (2) it turned mutual connections into "Sam and Jordan connected us" - the prompt now says mutuals are people both know, not an introduction; (3) the follow-up called Kyra "C++/Python-heavy" to match the posting - the system prompt now forbids reshaping Duc's projects toward the job. (4) after the contact's real profile was read through Duc's own Chrome (one page view, by Duc's request - not a Kyra feature) and their role/degrees went into the contact's `role`/`relation` fields, the draft wrote "Berkeley EECS alum here (MS+BS)" - the contact's degrees, attributed to Duc - and, one run earlier, "I took 61B when you were TAing" from a relation note that mentioned their TA years; the prompt now separates "About {recipient} - their facts, never Duc's" from "About Duc - the sender", the relation text states no-overlap facts as prohibitions ("never imply they crossed paths"), and Duc's own degree is a `background` memory note so the sender side has a source. Rule of thumb from this: any fact you put in a prompt about the *other* person will be re-attributed to Duc unless the prompt labels whose it is. The 200-character note limit is a post-condition in `draft_outreach_note` (one shorten retry, then `OutreachNoteTooLong`), not a prompt request. Also found and fixed: `ToolRegistry.run(name, **kwargs)` could not call any tool whose input schema has its own `name` field - the production tool loop would have raised `TypeError` on `add_outreach_contact`; `name` is positional-only now, with a test. Verified: 121 tests, real Claude draft through the real registry, real `pbcopy`/`open`, router sends 5/5 outreach phrasings to the tool path (router.log test noise cleared afterward).
