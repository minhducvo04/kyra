# Rules history: the standing rules and the architecture section as first written

`AGENTS.md` carries the current, condensed form of the working practices and the architecture pattern. This file keeps the **original wording** of both blocks as they stood in `CLAUDE.md` on 2026-09-09, because each rule there was written right after the failure that earned it and names the evidence (the leaked key, the em-dash in a handed-over header, the merge that dropped a whole entry, the 193 lines of router-log noise). When a rule in `AGENTS.md` seems too strict, the reason is here.

## Architecture pattern (verbatim)

Every subsystem is a small ABC interface + a swappable concrete backend (Strategy pattern), specifically so that "how would you extend this" always has a clean answer. Existing examples:

- `MemoryStore` → `ChromaMemoryStore` (`src/companion/memory.py`); a separate, second memory layer, `MemoryNotesStore` → `MarkdownMemoryNotesStore` (`src/companion/memory_notes.py`) - see the key decision below, they're not the same thing
- `SpeechToText` → `FasterWhisperSTT`, `TextToSpeech` → `KokoroTTS` (`src/companion/voice.py`)
- `ListenMode` → `PushToTalkListener`, `VoiceActivityListener` (`src/companion/listening.py`)
- `LLMBackend` → `AnthropicLLM`, `LocalLLM` (`src/companion/llm.py`) — `ConversationManager` depends only on `LLMBackend`; `build_llm(backend)` is the factory, `LazyBackends` is a dict-like cache that only constructs a backend the first time it's actually asked for (so a session the router never sends to local doesn't pay local-model load time).
- `Tool` → `AddReminderTool`/`ListRemindersTool`/`CompleteReminderTool`/`SnoozeReminderTool` (`reminders.py`), `TechNewsTool` (`news.py`), `ScienceFactsTool` (`science.py`), `SaveLearningItemTool`/`DueReviewsTool`/`MarkReviewedTool` (`learning.py`), `HandoffTool` (`handoff.py`), `AddJobApplicationTool`/`ListJobApplicationsTool`/`UpdateJobApplicationStatusTool`/`DraftApplicationMaterialTool` (`job_applications.py`), `SaveMemoryNoteTool` (`memory_notes.py`), `AutofillJobApplicationTool` (`job_autofill.py`) (`src/companion/tools.py`) — `name`/`description`/`input_schema`/`run()` map 1:1 onto a Claude tool-use definition, so `ToolRegistry.schemas()` goes straight into `tools=` on a Messages API call with no translation. `default_tools.py::default_tool_registry()` is the one place all fifteen (reminders 4, learning 3, job applications 4, autofill 1, memory notes 1, news 1, science 1) get assembled - `chat.py`/`voice_chat.py`/`webapp.py` all call it instead of constructing `ToolRegistry(...)` separately, so they can't drift out of sync (they briefly did, once, before this factory existed). `news.py` and `science.py` share fetch/parse code via `feeds.py` - add a new RSS-backed tool there too rather than re-implementing the Atom/RSS handling. `job_autofill.py`'s `AutofillEngine` ABC → `GreenhouseAutofillEngine` (Playwright) is the same Strategy shape, ready for a Lever/Workday/iCIMS engine later without touching the tool.
- `TurnRouter` (`src/companion/router.py`) — the design Duc worked through across several sessions, now built and wired into all three front doors. Layered decisions, cheapest/most-certain first: explicit override phrase ("ask claude"/"use local") > sticky session mode (`session_state.py`, file-backed, shared across front doors, focus→claude/chill→local) > a small local classifier (`Llama-3.2-3B-Instruct-4bit`, separate from the conversational `LocalLLM` default) that decides text-vs-tool and, for text, claude-vs-local. The tool path always goes to Claude as the "Agent Specialist" (`AnthropicLLM.respond_with_tools()`, the real Anthropic tool-use loop against a `ToolRegistry`) - local models weren't trusted with structured tool calls per the benchmark. `route_and_answer()`/`route_and_answer_verbose()` in the same module are what a front door actually calls per turn - one function, not reimplemented three times. Every decision is logged (`router_log.py`, JSONL, `data/router.log`) with a reason, whether or not anything went wrong.
- Long, "complex-looking" turns (word-count/multi-ask heuristic, `_looks_complex()`) get biased toward Claude rather than actually decomposed into subtasks - real subtask decomposition/execution was scoped out as a separate, bigger feature (see `docs/agentic-roadmap.md`).

When adding a new subsystem, follow the same shape: a one-or-two-method ABC, a concrete class that does the real work, callers depend only on the interface. Full context for all of the above: `docs/agentic-roadmap.md`.

## Working practices (verbatim)

- **"I am going to sleep" / "work as much as you can before I am needed" means: do not stop at the first thing that needs Duc** (his standing instruction, 2026-09-08). He wants work finished early so he can adopt and test features, not a list of blockers waiting for him. So:
  - Keep going until input is *genuinely* required to make progress, not until it is merely convenient to ask. A decision with an obvious default is made, stated, and moved past.
  - When something really does need him - an API key, an account, a purchase, a signed agreement, a recording only his microphone can make, a device that has not arrived - **build everything around it anyway**, so that the moment he supplies his half it runs. Prepare the config, the wiring, the tests, the docs and the exact command he types; leave a single obvious seam where his thing plugs in.
  - **That preparation goes on its own branch**, named so it is obvious what it is waiting for, so he can throw it away cheaply if he decides it was not worth doing. Say in the report which branch, what it is waiting for, and what happens when he supplies it.
  - Report at the end with what is done, what is on a prep branch, and the shortest possible list of things only he can do.


- **Anything that leaves this machine for a human reader ALWAYS goes through the humanizer pass, no exceptions** (Duc's standing rule, 2026-09-07, after he caught an em-dash in material handed to him). "Outbound" means a resume, a cover letter, a job-application form answer, an outreach note, an email - and it also means *the surrounding text you hand him with it*: the file header, the summary block, the pasteable snippet in chat. The gap he caught was exactly there: the answer body had gone through `CRITIQUE_PROMPT` and was clean, while the header written by hand above it was not, and carried the em-dash. So the rule is per-artifact, not per-LLM-call - if a human other than Duc could read it, it gets the pass.
  - Run the real `job_applications.CRITIQUE_PROMPT` through a real call. Do not hand-wave "I wrote it carefully."
  - **Never an em-dash or en-dash (—, –) in outbound text, and never a spaced hyphen standing in for one** (`x - y`). `CRITIQUE_PROMPT` lists em-dashes but a single pass does not always catch the ASCII stand-in: on a take-home answer, pass 1 left `isn't one-off - it recurs` and pass 2 fixed it to `isn't a one-time gain, it recurs`. When the text is short and final, run the pass twice and diff; adopt pass 2 only where it actually improved something, since a second pass on clean text can flatten voice (see the `writing_voice` memory note).
  - **The pass is not a fact-checker, and it introduces errors of its own.** Re-verify after it, every time. Two real cases on that take-home submission: it wrote that the fabrication validator checks "against the source article" when it checks against source *documents*, and it added "run a pipeline like this against real feeds **for weeks**" when the digest was days old. Both read fluently and both were false. Check every number against sources, and reject any duration, scale, headcount or business-outcome claim the source text did not contain.
  - Check the artifact mechanically before sending, not by eye: numbers diffed against sources, no dash characters, no invented scale/duration, no greeting/sign-off on a form field, no `llm.TRUNCATION_MARKER`. A truncated draft silently poisons the pass - a 325-word answer hit a 3,000-token ceiling and the critique step then "reviewed" a stub and replied asking for the text again.
- **The repo lives at `~/Projects/kyra` (moved there 2026-09-07 from `~/Downloads/Personal assistant`), and moving it again means fixing seven things a `mv` does not.** Out of `Downloads` because that folder gets cleaned out, and no space in the name because a space needs quoting in every shell command and percent-encoding in every `file://` URI. What holds the absolute path, in the order that bites: `.venv` (`pyvenv.cfg`, `bin/activate*`, every `bin/*` shebang - patch them with `sed` on the same machine, or rebuild); `~/Library/LaunchAgents/com.kyra.daily-digest.plist` **and** its tracked copy in `deploy/` (five paths each, and a stale one fails the 05:00 digest silently); `.env`'s `KYRA_CLASSIFIER_ADAPTER` (a stale path makes `router.py` fall back to the few-shot 3B with no error - the one failure here that looks like nothing happened); `data/applicant_profile.json`'s `resume_path`; the `resume_path` column in **every** `data/*.db`, not just `job_applications.db`, since each store keeps its own file; registered git worktrees (`git worktree repair` from the new location); and `~/.claude/projects/<path-slug>/`, which is where session history and memory live - the slug is derived from the path, so skipping it silently orphans both. Verify with `pytest`, `ruff`, `daily_digest.py --dry-run`, and a real `launchctl kickstart -k gui/$(id -u)/com.kyra.daily-digest` rather than waiting for 05:00.
- **Never `cat`, `diff`, or otherwise print the full contents of `.env`.** It holds a live Anthropic API key. Two earlier sessions accidentally leaked a real key into a conversation this way (both keys were revoked after). For diagnostics, check only length/prefix/whitespace, like `scripts/debug_api_key.py` does.
- Model files and local databases (`data/`, including `data/voice_models/`) are gitignored on purpose — don't commit them, don't remove them from `.gitignore`.
- `git` identity for this repo is set locally (not global) to Minh Duc Vo / a private address — that's deliberate, leave it repo-local.
- Job-search and interview-prep working docs live under `data/private_docs/` (gitignored), not in this repo's tracked docs.
- **To check that a merge lost nothing, enumerate what disappeared - never confirm what you expected to survive (2026-09-08)** - resolving the two parallel slice-3 branches dropped a whole CLAUDE.md verification entry, and the session that resolved it then grepped for three markers, saw all three, and called it verified. Three of the four entries were present, and the three had been chosen from the same wrong mental model that caused the bug: the resolver dropped the first "ours" line in every hunk on a rule that held in the decisions list (where it was a stale copy of an anchor master had rewritten) and was false in the verification section (where it was a distinct new entry). **A spot check written by the author of a change tests the author's assumptions, not the change.** The method that works is mechanical and takes a minute: `diff <(git show <pre-merge tip>:<file>) <file>`, then for every removed line ask whether the other side ever had it - a line gone because the other side rewrote it looks identical to a line that was lost, until you check. Run it over every file the merge touched, not the one you suspect. This is the same failure this file already records three times without naming it - the evening-theme test that compared against the wrong baseline and passed the defect, the self-containment test that had quietly stopped testing its own name, and the scrub grep whose 792 hits were mostly noise it had never been updated to exclude.
- **The "clean up test pollution" discipline covers `data/router.log` too, not just the DB stores** — a gap found 2026-09-03 while building `analyze_patterns.py`: classifier re-test scripts (`router.route(msg)` in scratchpad harnesses) log to the real `data/router.log` exactly like production does, and this had gone unnoticed across several classifier-prompt-edit sessions, leaving 193 lines of pure test noise (caught only because a pattern-analysis tool would have treated it as real usage). After any classifier re-test batch, check `data/router.log`'s recent entries the same way you'd check `data/*.db` - don't assume only the databases need this. **And `data/memory_db` needs a safe recipe, not just the habit (2026-09-08)**: verification turns against the running app write real memories, and the WAL shows every session cleaning them by deleting "the ids I wrote" - which, under the old counter ids, handed the same ids to the next real exchange and, because a live process's counter keeps advancing after the delete, let the last test turn escape (ids 38/39 are exactly that). Snapshot `collection.get()["ids"]` before the run and delete the set difference after, or run the server with `KYRA_DATA_DIR` pointed at a scratch copy of `data/`. Never delete by the ids you think you wrote.
