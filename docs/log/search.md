- **`search_kyra_data` is the chat front door to search, and its safety property is an absence (2026-09-08)**: `SearchKyraDataTool` (`search.py`, registered in `default_tools.py`) has **no `include_sensitive` parameter**. Asking for the `private` kind is refused, not answered with an empty list, because empty reads as "nothing there" instead of "not yours to read". Held-out set `tests/data/search_testset.jsonl`, numbers in `docs/search-eval.md`, plan in `docs/plans/2026-09-07-semantic-search.md`. **The index writes with `upsert`, not `add` (2026-09-08)** - a chunk id is deterministic (`source_id#i`), so re-indexing an edited document writes ids that already exist, and Chroma ignores an add whose id is taken. `_drop_source` frees them first, but its vector delete is deliberately swallowed (an empty collection can raise), so a delete that ever missed would leave the OLD embedding under a fresh FTS row: hybrid search keeps answering and nothing surfaces that half the index is stale. Stale results are still stale; they just no longer look current.
- **Search is hybrid because vector-only measurably is not enough, and the reranker result was the opposite of the prior (2026-09-07)** - Duc asked for semantic search over the project's and Kyra's data, run through the local model. Built as `search.py`: SQLite **FTS5** (BM25) for exact terms and Chroma+BGE for meaning over the same chunks, fused by **Reciprocal Rank Fusion** (k=60) rather than a weighted score blend - BM25 scores and cosine distances are not on comparable scales, and any blend needs normalisation constants that drift, while RRF only reads ranks. FTS5 ships inside `sqlite3`, so the half that usually wins cost no new dependency. Measured on 26 handwritten held-out queries (`docs/search-eval.md`): vector-only **69.2%** Recall@5 vs lexical **88.5%** - embeddings miss every identifier (`RECENCY_WEIGHT`, `write18`, `ICPC`), which is a large share of how Duc searches his own material, so "just do semantic search" would have been a downgrade. The finding that justifies hybrid is not the top-5 score but the depth curve: **hybrid reaches 100% recall by rank 20 while lexical plateaus at 96.2% even at rank 40** - BM25 can never find "the resume I tailored for the hedge fund new grad role" because the Northwind resume never says "hedge fund". Retrieval and ordering therefore fail differently, which is why RRF weights were left alone (tuning them against 26 queries is fitting the test set) and a reranker was built instead. **The reranker measurement contradicted the design note written before it ran**: both cross-encoders scored 84.6%, the local Qwen2.5-14B scored **92.3%** (the only config above 90%, best MRR too) - a cross-encoder trained on MS MARCO web relevance has no notion of whose files these are, and the three queries it misses are all intent-shaped ("which decisions are still waiting on me"). Duc's instinct to route it through the local model was right; the code comments were corrected. Cost is 3.13s/query vs 0.01s, so rerank is opt-in and retrieval stays instant. **Caveat that must not be dropped**: 26 queries means one query is 3.8 points, so the top rows are not separated - same lesson as router round 4, where a 4-point gap was seed noise. Two real bugs found by building it: (1) FTS5's `unicode61` splits on `_`, so `RECENCY_WEIGHT` indexed as two words and matched the prose "recency weighting" - fixed with `tokenize = "porter unicode61 tokenchars '_'"` (`-` still splits, so "one page" finds "one-page"), and a `SCHEMA_VERSION` + `PRAGMA user_version` guard drops and rebuilds an index built under different tokenization instead of letting it answer with the old rules; (2) a `zip(..., strict=True)` on a deliberately-offset pair list, caught by the first chunking test rather than in production. **Sensitivity is a default argument, not a prompt**: everything under `data/private_docs/` is tagged `sensitive=True` and `search()`/`answer()` refuse to return or show it unless the caller passes `include_sensitive=True`, with tests asserting a private chunk never surfaces by default in any of the three modes and never reaches the model's prompt - the structural answer to the 2026-09-04 bug where a true-but-private memory note became a fabricated resume entry. Chunks are capped at 300 words because `bge-small-en-v1.5` silently truncates past 512 tokens (the same trap `bge_embedding_function`'s docstring records for MiniLM's 256-token cap), enforced by a test rather than by trusting the splitter. Also noted, not changed: `llm.py` redirects `HF_HOME` to `data/local_llm_models` while a bare CLI run uses the default cache, so `bge-small-en-v1.5` now exists in both - same weights, duplicated on disk.
