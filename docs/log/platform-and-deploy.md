- **The image was 3.5 GB because of a wheel nobody asked for (2026-09-10)** - `sentence-transformers` depends on torch, and PyPI's torch wheel carries the CUDA libraries, so the pip layer was 6.7 GB on a Fargate task that has no GPU. Installing torch from the CPU wheel index first (Dockerfile) brings the image to 753 MB. Pip timeout and retries are set as image environment because two builds died on flaky downloads. Also: `scripts/web_ui.py` ran uvicorn at `warning`, so the container had no access log; it now follows `KYRA_LOG_LEVEL`, which the task definition sets to INFO.
- **First real deploy, and the router had no fallback for a machine without a local model (2026-09-10)** - the Terraform in `deploy/aws/` was applied for the first time (43 resources, us-west-2, budget 40 USD/month). The image needs Rosetta rather than QEMU under Colima on Apple silicon, because LaTeX's post-install pipes break under emulation. The real finding: `router.py` treated a classifier exception as "default to Claude, text path", which on a laptop is a rare hiccup and in the container, where `mlx_lm` does not exist, is every turn: the deployed Kyra could not call a tool. Now a classifier error routes to the Claude tool path and the model decides per turn; unparseable classifier output still means text. Verified by a reminder turn that reached RDS after the redeploy. Follow-ups: CPU-only torch (the pip layer is 6.7 GB because sentence-transformers pulls CUDA), HTTPS, and the CI deploy variables.

- **Two agents hand off through a file, because the alternative was Duc copying a block between two chats (2026-09-09)** - `session_log.py` + `scripts/session_log.py` write `data/sessions/<branch>.md`, append-only and gitignored. **One thread per branch**, since the branch is already the unit of work in `docs/agent-workflow.md`: the same slice appends, a different slice gets its own file, and no thread id has to be invented or remembered. - Setup: `python3 -m venv .venv && source .venv/bin/activate && pip install -r requirements.txt`
- **Two documented startup invariants are tests now, not measurements in this file (2026-09-08)** - `tests/test_startup_cost.py` asserts that importing `companion.webapp`, building `default_tool_registry()`, and importing `digest`/`job_boards`/`outreach` leave `chromadb`, `torch`, `mlx`, `sentence_transformers`, `faster_whisper` and `kokoro` out of `sys.modules`. One top-level import or a store constructed at module scope breaks that quietly: the server still works, it just takes tens of seconds to start and drags the suite with it, which is exactly what `_Runtime`'s `cached_property` and `LazyBackends` exist to prevent. Asserted as module presence in a subprocess rather than a stopwatch - a timing assertion on a shared runner is a flake, an accidental import is a fact. The detector was checked against a real `import chromadb` so the tests are not vacuous (`memory.py` already defers its own chromadb import inside `__init__`).
- **A browser could not cross the API boundary, and that is why nothing could be deployed (fixed 2026-09-08)** - `KYRA_API_TOKEN` (2026-09-07) exempts loopback only, so behind any proxy every request is non-loopback and needs `Authorization: Bearer`. `web/app.js` never sends that header from **43 `fetch` call sites** and **cannot** from its 2 `EventSource` ones, because EventSource has no header API at all. So the two available settings were "token off, the API is open to the internet" and "token on, the UI is dead" - there was no third one, which is the real reason `deploy/aws/` was never applied and why Render or anything else would have failed the same way. `webauth.py` is the third setting: an HMAC-SHA256 over its own issue time, keyed by the token, set as an HttpOnly SameSite=Lax cookie by `POST /api/login`. A cookie rides every fetch **and** every EventSource automatically, same-origin, so not one of the 43 call sites changed. Stdlib only, no session store - rotating `KYRA_API_TOKEN` invalidates every outstanding session, which is the whole revocation story and the right size of one for a single user. The bearer path is untouched, because `KyraClient.swift` speaks it. **Proven by A/B on a real server, not TestClient**: the identical `EventSource` URL returns 422 (past the gate, bad job id) logged in and 401 after `POST /api/logout`. **The gate now covers the whole app, not just `/api/`** - `test_static_and_index_are_not_gated` pinned the opposite and was correct for the LAN-headset case it was written for; a hosted Kyra serving its HUD to strangers shows them Duc's profile, outreach contacts and memory notes. That test only kept passing because TestClient follows redirects, so it was asserting 200 from `/login`, not from the HUD - a test that had quietly stopped testing its own name.
- **The loopback exemption reads the socket peer and never `X-Forwarded-For` (2026-09-08)** - reading the header would let anyone send `X-Forwarded-For: 127.0.0.1` and walk straight in, so uvicorn is deliberately **not** started with `--proxy-headers`: that flag overwrites `scope["client"]` from exactly that header. There is a test per spoofable header. The cost of the safe choice is that a reverse proxy on the *same host* makes every caller look local, which is what `KYRA_TRUST_LOOPBACK=false` exists for and what `render.yaml` sets.
- **`/healthz` is ungated because an authenticated healthcheck fails closed (2026-09-08)** - the Dockerfile `HEALTHCHECK` and CI's smoke test both hit `/api/backend`, which is under the gate, so with a token set an orchestrator would have marked every healthy task unhealthy and restarted it forever. It touches no subsystem either: it must answer while Postgres, Chroma and the model are all unavailable, or a slow dependency reads as a dead process. CI now asserts both halves - `/healthz` open, `/api/backend` 401, bearer 200 - against the real image.
- **A managed provider's `DATABASE_URL` names a driver we do not install (2026-09-08)** - Render, Heroku, Fly and the RDS console all hand out `postgres://` or `postgresql://`; SQLAlchemy resolves both to **psycopg2** while `requirements-web.txt` installs `psycopg[binary]` (psycopg **3**). A copy-pasted connection string would have died at startup with `ModuleNotFoundError: psycopg2`, which reads as a broken image rather than a URL needing one word changed. `db.normalize_db_url()` rewrites both to `postgresql+psycopg://` and leaves an explicitly chosen driver alone. Found while writing `render.yaml`, before it could cost a first deploy.
- **Hosting: `render.yaml` is the cheap path, and the disk is the scaling ceiling (2026-09-08)** - one web service with the inline worker, Postgres, and a 5GB disk at `/data`, ~$33/month against `deploy/aws/`'s ~$85 for one user. **RAM picks the plan, not CPU**: the image loads `chromadb` plus `sentence-transformers` (BGE, ~130MB) for memory and search, so a 512MB Starter OOMs on the first retrieval rather than at boot, which is worse. A Render disk pins the service to exactly **one instance** and rules out zero-downtime deploys - correct for one user, but lifting it means moving Chroma and the document library off the filesystem, not adding instances. The 171GB under `data/` is almost entirely `bench_hf` (121GB) and `local_llm_models` (49GB), which the container never loads. **The hosted Kyra is the weaker Kyra** - no local model, no voice, no classifier (already handled: `route()` falls back to Claude) - so it is remote access for Duc, not the thing to show people. Plan and the honest option comparison: `docs/plans/2026-09-08-going-public.md`.
- **Configuration** is one typed object: `companion/settings.py::get_settings()` (pydantic-settings, reads `.env`; env names unchanged: `ANTHROPIC_API_KEY`, `KYRA_DATA_DIR`, `KYRA_LOG_LEVEL`, `KYRA_CLASSIFIER_ADAPTER`, `KYRA_STT_MODEL`, `KYRA_PTT_KEY`/`KYRA_INTERRUPT_KEY`, `DATABASE_URL`, `KYRA_HOST`/`KYRA_PORT`). Don't read `os.environ` in new code - add a field. `config.require_api_key()` is a shim over it.
- **HTTP errors** raise `companion.errors.ApiError(status, code, message, details)`; the handler renders `{"error": {"code", "message", "details"}}`. Never `return {"error": ...}` with 200. In `web/app.js`, read responses through `readJson(res)` so 4xx messages surface.
- **Relational stores (v2 slice 2)**: `RemindersStore`, `LearningStore`, `JobApplicationStore` are SQLAlchemy Core over `companion/schema.py` (tables match v1's hand-written DDL column-for-column, so existing `data/*.db` files read as-is). `DATABASE_URL` unset → each store keeps its own SQLite file under `DATA_DIR` (the laptop default); set → all share that database (Postgres in the container/AWS). Constructors accept a path (SQLite), a URL, or `engine=`. Schema changes go through Alembic: `.venv/bin/alembic revision --autogenerate -m "..."` then `.venv/bin/alembic upgrade head` (URL from Settings; `ALEMBIC_URL` overrides). `engine_for_store()` still runs `create_all` (idempotent) so a fresh DB works without running migrations; production deploys should run `alembic upgrade head`. `JobDocumentStore` is still the JSON index + files (object storage is a later slice).
- **Background jobs (v2 slice 3)**: the one-page resume loop runs as a job. `POST /api/jobs/draft` (same form as `/api/job/draft`, `latex_resume` only) → `{id}`; `GET /api/jobs/{id}`; `GET /api/jobs/{id}/events` is SSE (`progress` lines as the loop's attempt notes land, then `done` with the full `DraftOut`, or `error`). `companion/jobs.py`: `JobQueue` ABC → `DbJobQueue` (a `jobs` table on the same engine as the stores; Postgres claims with `FOR UPDATE SKIP LOCKED`). On the laptop the worker is a thread inside the web process (`KYRA_INLINE_WORKER`, default true); in the container `KYRA_INLINE_WORKER=false` and `python scripts/worker.py` runs as the `worker` service. Tests drive the queue with `jobs.run_one()` (conftest turns the inline thread off). `optimize_latex_resume_one_page(..., on_progress=)` / `generate_latex_from_selection(..., on_progress=)` are the hooks. The synchronous `/api/job/draft` path still works for every material type.
- **Container (v2 slice 1)**: `docker compose up` (api + postgres) or `docker build -t kyra-api .`; the image installs `requirements-web.txt` only (no torch/mlx/voice - those stay on the Mac; the router's local classifier is unavailable in a container and `route()` falls back to Claude). Docker isn't installed on the dev Mac; the `docker` job in CI builds and smoke-tests the image.
- **Deploy (v2 slice 4)**: `deploy/aws/` is Terraform for the compose shape on AWS - `api` + `worker` on ECS Fargate from the one ECR image, RDS Postgres 16 in private subnets, one EFS volume at `/data` on both tasks, an ALB whose `allowed_cidrs` variable rejects `0.0.0.0/0` (there's no login yet), Secrets Manager (the Anthropic key is `put-secret-value`'d by hand, never in state), CloudWatch, and a GitHub OIDC role. Steps, cost (~$85/month running, ~$0 after `deploy/aws/teardown.sh`) and what's deliberately deferred are in `deploy/aws/README.md`. Neither Terraform nor the AWS CLI is installed on the dev Mac: CI's `terraform` job runs `fmt -check` + `validate`; the `deploy` job (ECR push + `update-service --force-new-deployment`) is skipped until the `AWS_ROLE_ARN`/`AWS_REGION` repository variables exist. **Never applied yet** - the first `terraform apply` is Duc's, against an account and spend ceiling he's chosen.

- **Tests: `pip install -r requirements-dev.txt` once, then `python3 -m pytest`** (56 tests, ~5 s; LaTeX-backed tests skip cleanly if `pdflatex` isn't on PATH). **Lint: `ruff check src scripts tests`.** Both run in CI (`.github/workflows/ci.yml`) once a remote exists. Real-pty tests for raw keypress handling are still ad hoc (`scratchpad/` patterns) - piped stdin doesn't exercise `termios`/`tty` cbreak mode.
- **All on-disk state lives under `companion/paths.py::DATA_DIR`** (default `data/`, override with `KYRA_DATA_DIR`). Don't compute `Path(__file__)...parent.parent.parent / "data"` in a new module - derive from `DATA_DIR`. **JSON stores write through `paths.write_json()` (2026-09-08)**, which writes a sibling temp file and `os.replace`s it, because `Path.write_text` truncates before writing and a crash in between leaves a half-written file. Every reader here fails loud on a corrupt file (`load_watchlist`, `_read_all` and `check_boards`'s `seen.json` all let `JSONDecodeError` out - the `except Exception` in `company_for_token` is a display-name lookup only, not the watchlist read), so the harm is not silent misbehaviour: it is that the file's contents are **gone**, and these are curated things - the document library index behind every drafting path, the board watchlist Duc maintains by hand, `seen.json`. Use it for a new JSON store rather than `write_text`, and leave the readers loud: silently returning an empty library is the failure being prevented, not the fix. `KYRA_LOG_LEVEL` sets logging level (`companion/logging_setup.py`); use `logging.getLogger(__name__)`, not `print`, in `src/`.
- Scripts import via `sys.path.insert(0, ".../src")` rather than an editable install — keeps setup to plain `pip install -r requirements.txt`, no build step. Follow the same pattern in new scripts.
- **The laptop's per-store SQLite files are not migrated by Alembic, and a column addition must reach them by hand (2026-09-07)** - `DATABASE_URL` is unset locally, so each store keeps its own file (`job_applications.db`, `reminders.db`, `learning.db`, `outreach.db`) while `alembic upgrade head` only ever touches `kyra.db`. Those files also carry no `alembic_version` row (their tables came from `create_all`), so `upgrade` fails with "table already exists" until they are stamped. The recipe used for `8f4f8496ae73`, after backing every file up: `alembic stamp <previous head>` then `ALEMBIC_URL="sqlite:///$(pwd)/data/<store>.db" alembic upgrade head` for each file. Without this the real tracker keeps the old table and any insert naming the new column fails. Setting `DATABASE_URL` to one shared database removes the problem entirely and is what the container already does.
- **v2 Phase 1 started 2026-09-06 (`docs/plans/2026-09-06-v2-phase1.md`)** - target AWS (ECS Fargate + RDS + S3 + SQS, Terraform), one-evening slices because the interview date is unknown, local-first so spend starts only at deploy. - **v2 slice 2 (2026-09-06): Postgres behind the store interfaces, verified in CI only** - no Postgres or Docker on the dev Mac, so `tests/test_stores_backends.py` parametrizes the store tests over SQLite (always) and Postgres (when `TEST_DATABASE_URL` is set; CI provides a `postgres:16` service container). Design choices worth knowing: timestamps stay ISO strings (v1 wrote them that way; a TIMESTAMP migration is a data migration for a later slice); the `learning_streak` single row is check-then-insert instead of SQLite's `INSERT OR IGNORE` for portability; `ORDER BY (due_at IS NULL), due_at` became `due_at.is_(None), due_at` for the same reason. The initial Alembic revision was autogenerated from the metadata and applied to a fresh DB (4 tables), not hand-written.
- **v2 slice 3 (2026-09-06): a DB-backed job queue, not Redis/SQS, on purpose** - the long tasks run for a minute or two, a few times a day, for one user; a `jobs` table on the database the stores already use gives durable state and streamable progress with zero new infrastructure (no Redis or Docker on the laptop), and the identical code runs on Postgres in the container. SQS was pencilled in as the AWS adapter behind the same `JobQueue` interface, then deliberately left out of slice 4 (see that bullet) - the API and worker don't change either way. SSE is implemented by polling the table every 0.7 s; a pub/sub channel is an optimization for later, not a correctness fix. One real bug caught by the tests before it shipped: the bulk rename that routed every `notes.append` through the new `note()` progress helper also rewrote the append *inside* the helper, making it call itself - `RecursionError` on the first attempt line.
- **v2 slice 4 (2026-09-06): the deploy is EFS + the DB queue, not S3 + SQS, on purpose** - the plan said S3 for PDFs and SQS for jobs. Reading the worker handler settled it: the worker doesn't only write the PDF the api serves, it also reads the document library, memory notes and extra facts, all under `KYRA_DATA_DIR` - so an S3 adapter for PDFs alone would still leave two containers with different libraries. One EFS mount on both tasks gives the laptop's code the shared filesystem it assumes with zero code change; per-store object storage is a later slice. SQS would only replace the worker's 1-second claim poll, since the SSE endpoint already streams progress from the `jobs` table; it goes in behind `JobQueue` when a second worker exists. Three constraints live in code, not docs: `allowed_cidrs` rejects `0.0.0.0/0` in a Terraform validation rule (no auth yet, so the allow-list is the only boundary in front of the API key); the Anthropic secret is created empty so the key never enters state; and `latex_compile.compile_argv()` passes `-no-shell-escape`, with a test that plants `\write18{touch ...}` in a source and asserts the file never appears - a model-written resume must not be able to run a command, on the laptop or in the container. No NAT gateway (tasks get public IPs, ingress only from the ALB) saves ~$32/month per AZ. Verified: CI `terraform validate` on the PR, `pytest` 87 passed with the `\write18` test under a real `pdflatex`; **not applied** - waiting on an AWS account and a spend ceiling from Duc.
