# Voice

`voice.py`, `listening.py`, `voice_text.py`, `scripts/voice_chat.py`: STT/TTS choices, barge-in, keybindings, sentence-by-sentence speech, the latency measurements.

Entries below were moved verbatim from `CLAUDE.md` on 2026-09-09 (original order kept, newest work is usually nearer the top of each section). Add new entries at the top of this file, dated, with the *why*.

## Entries

- Voice chat: `python3 scripts/voice_chat.py` — same `--backend auto|claude|local` (`--mode ptt` for push-to-talk, default is hands-free). Press the interrupt key while she's talking to cut her off (barge-in). Keys default to Enter for both PTT and interrupt, remap via `KYRA_PTT_KEY=space` / `KYRA_INTERRUPT_KEY=esc` (see `companion/keybindings.py`).
- **A smaller STT model is not the free second it looks like (measured 2026-09-08)** - `scripts/measure_stt.py`, numbers in `docs/voice-latency.md`. On clean speech `base` is **3.6x faster than `small` at identical 0% WER**, and `KYRA_STT_MODEL` already exists to switch - but clean speech cannot rank the models, because nearly every configuration scores 0%. With calibrated noise added (averaged over three draws) `small` wins at every level, and at 10 dB - an ordinary room - `base` makes **2.8x the errors** (11.5% vs 4.1%). Mishearing is worse for a companion than a second of waiting, so **`small` stays**. Two cautions that travel with the table: with one noise draw the 0 dB row flipped the ranking between runs, so it is averaged and the decision rests on the stable 5-10 dB columns; and the speed column moves with the model cache while the ratio holds. The remaining ~1.2s therefore has to come from overlapping transcription with speech, which needs a real streaming approach and a baseline recorded through Duc's own microphone - synthetic speech cannot stand in for the thing being optimised.
- **`POST /api/speak` says text that is already written, and the visionOS client uses it (2026-09-08)** - `/api/voice/stream` takes a microphone recording and runs a whole turn, so a client that typed its turn through `/api/chat/stream` cannot use it: it has the reply and only needs a voice. Same events (`audio` per sentence, then `done`) so one player serves both, and the same `_audio_event()` helper does the synthesis for both so they cannot drift - markdown is stripped per sentence before the synthesiser sees it either way. Synchronous rather than threaded: there is no model call to overlap with. On the headset this means her Kokoro voice rather than `AVSpeechSynthesizer` - the same voice at every front door, and the round trip is a LAN hop. `SpeechPlayer.swift` is the queue; `stop()` drops what has not been said yet as well as what is playing, because clearing only the current clip makes her carry on a moment after being cut off. **Verified**: real Kokoro through the endpoint (two sentences, two real WAVs at 24 kHz) and the simulator showing SPEAKING / "tap to interrupt" during a real turn.
- **She starts speaking before she has finished thinking (2026-09-08)**: `POST /api/voice/stream` is `/api/voice` as SSE - `transcript` first (so he sees what she heard before she says anything), then one `audio` event per **sentence** as it is synthesised, then `done` with the written reply. Measured against the same utterance on the same server: first word at **3.61s versus 4.45s**, and the gap widens with reply length because the first sentence still lands at ~3.6s however long the rest turns out to be. `voice_text.take_sentences()` splits the streamed text; it deliberately runs on the **raw** text (the boundary regex tolerates trailing markdown, `**Sure.** `) because stripping markdown first would mangle a link still being written - `spoken_text()` then cleans each whole sentence. Each chunk is a complete WAV, not a slice of one stream, so the browser plays them from a queue with a plain `<audio>` element; interrupting clears the queue as well as the clip, or she carries on with the next sentence a moment after being cut off. **Only a streamed Claude text turn benefits**: a tool turn has no `on_token` and `LocalLLM.supports_streaming` is False, so both fall back to synthesising the whole reply at the end - correct, but no faster. Both of the first two utterances tried during verification took those paths, which is a useful reminder of how often the fast path is not the one taken.
- **The voice loop is 5.3s of silence, and the measurement says where to spend the next hour (2026-09-08)** - `scripts/measure_voice_latency.py`, numbers and caveats in `docs/voice-latency.md`. Warm: STT 1.56s / route 0.17s / Claude 1.93s / Kokoro 1.12s. The only number on record before this was "first token at 5.3s of 7.1s" for a **text** turn, which measures the wrong thing for a companion - what matters is the gap between Duc finishing his sentence and hearing her start. Two findings drive everything: **synthesising just the first sentence costs 0.48s against 1.12s for the whole reply**, so speaking it while the rest is still being written puts the first word near 3.6s; and **STT is all paid after he stops talking** (1.56s for 3.0s of speech), so transcribing incrementally is worth another ~1.2s. Together that is ~2.4s, which is the range where a reply stops feeling like a request. One turn costs 2,386 input / 176 output tokens, and **the memory notes are ~65% of that prompt and grow without bound** - the layer is rendered in full every turn by a design that assumed it stays small. Caveat that must travel with these numbers: this is the *text* path; a tool turn does not stream at all, so it cannot benefit from the first-sentence trick.
- Voice model download (one-time): `python3 scripts/setup_voice_models.py`
- Voice sanity check, no mic needed: `python3 scripts/test_voice_roundtrip.py`
- **Voice is local/open-source on purpose** (faster-whisper + Kokoro + Silero VAD), not a cloud API like ElevenLabs/OpenAI/Deepgram. Chosen for $0/turn (this gets tested a lot), privacy, and because running real local inference is more of the point of this project than calling someone else's endpoint. The interface boundary makes a cloud backend a future drop-in class, not a rewrite, if a polished demo ever wants one.
- **Voice turn-taking is sequential, with keypress barge-in** (not voice-triggered). `speak_interruptibly()` in `voice_chat.py` plays her reply via `sd.play()` and polls a raw keypress (`companion.keybindings.read_key()`, `termios`/`tty` cbreak mode — not line-buffered `input()`) instead of blocking on `sd.wait()`; the configured interrupt key stops her immediately. Deliberately *not* voice-triggered — the mic would pick up her own TTS through the speakers, and without real echo cancellation that risks her cutting herself off mid-sentence. Full concurrent listen-while-speaking stays a Backlog item; see `docs/design.md`.
- **Keybindings are configurable, not hardcoded** — `companion/keybindings.py`, env vars `KYRA_PTT_KEY`/`KYRA_INTERRUPT_KEY`, default Enter for both (unchanged behavior if you don't touch them). Both `PushToTalkListener` (`listening.py`) and `speak_interruptibly()` (`voice_chat.py`) read a single raw keypress via the same `read_key()` — this needs a real interactive terminal (`sys.stdin.isatty()`); non-tty stdin returns `None` rather than hanging or misfiring (a piped/closed stdin busy-looping here was a real bug caught during testing - see the pty-based tests this was built with).
- **Silero VAD requires exactly 512-sample chunks at 16kHz** (`VoiceActivityListener.CHUNK_SAMPLES` in `listening.py`) — it raises "Input audio chunk is too short" on anything else. Don't change this constant without re-verifying against the installed silero-vad version.
- **Sample rate contract**: `SpeechToText.transcribe()` always expects mono float32 audio at 16kHz (`companion.voice.SAMPLE_RATE`). Kokoro's TTS output is 24kHz — resample before feeding it back into STT (see `test_voice_roundtrip.py`'s `resample()` for the pattern used so far).
