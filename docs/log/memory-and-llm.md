# Memory layers and the LLM client

`memory.py`, `memory_notes.py`, `llm.py`, `conversation.py`: the two memory layers, the Chroma id defect, token budgets, streaming, prompt caching, the date in the system prompt.

Entries below were moved verbatim from `CLAUDE.md` on 2026-09-09 (original order kept, newest work is usually nearer the top of each section). Add new entries at the top of this file, dated, with the *why*.

## Entries

- **The system prompt is cached, which is where the money actually was (2026-09-08)** - `respond()` sends `system` as a block with `cache_control: ephemeral` rather than a bare string. It is identical on every turn of a session (persona, today's date, the memory notes rendered in full) and it is the biggest thing in the request - 2,386 input tokens measured, ~65% of it notes, growing as more are saved. `respond_with_tools()` had cached its tool schemas since the distillation work; the larger block was never covered. Verified against the real API: first turn writes 2,344 cache tokens, every turn after **reads** 2,344, so the input side of a turn falls about 90% after the first. The TTL is roughly five minutes, so this pays for a conversation, not for one question an hour. An empty system prompt is still sent as a bare string, because an empty block is rejected and there is nothing to cache.
- **`ChromaMemoryStore.add()` dropped a record whose id already existed (found 2026-09-07, FIXED the same day)** - ids came from `str(self._next_id)`, seeded from `count()` at construction, and Chroma ignores a duplicate-id add with no exception and no warning: the record is simply gone and `count()` never moves. Any drift in that counter therefore lost memories with no error anywhere - a second store over the same collection (the web app and a CLI session at once), a store constructed while another was writing, a deleted row moving `count()` backwards. `add()` now writes `uuid.uuid4().hex`. Nothing ever read those ids as numbers, which is why the counter bought nothing: `retrieve()` ranks by the `timestamp` metadata, `search.py::ConversationSource` only echoes the id into a `source_id`, and `migrate_memory_embeddings.py` round-trips whatever it dumps - so existing rows keep their numeric ids, Chroma takes the mixed formats, and **no migration is needed**. The post-condition is `tests/test_memory.py`: a write must be retrievable, covering the two-instances-over-one-collection repro and the reopen-after-a-delete case; both failed red against the counter before the fix, which is the only reason to trust them. Verified past the suite with a real run under real BGE embeddings against a **copy** of the real `data/memory_db` (the original never opened): the repro that used to lose a write keeps all four, the existing numeric-id rows still retrieve, and new uuid rows land beside them. **The real store has a hole in it** - ids 30-37, four exchanges between 09-02 and 09-07, are absent, and Chroma's own write-ahead log (`embeddings_queue`) records ids 30 and 31 added twice, which is this defect's fingerprint. The log's DELETEs of 30-37 turned out to be deliberate (traced 2026-09-08 on a copy of the store): two Claude sessions - the streaming check at 05:38 local, the cancel check at 20:33 - each cleared the verification turns they had written, one to two minutes after the last one, and the deleted documents are the verification prompts themselves ("In two sentences, what does the router do?", "Explain in detail how RRF works... be thorough"). So nothing of Duc's was lost, and the one write the counter actually dropped (WAL seq 79/80, a second instance re-using ids 30/31) was a verification exchange that session would have deleted anyway. Two test rows escaped that cleanup - ids 38/39, written *after* the delete by the same process, whose in-memory counter had already moved past the deleted block - and a later session removed them on 2026-09-08; the real store is back to exactly Duc's 30 rows (`needs-your-input.md` #27). **Correction (2026-09-08): the deletes were this session's own cleanup, not an unknown actor.** Ids 30-37 were verification turns made against the running web UI on 2026-09-07 evening and removed afterwards under the standing clean-up-test-pollution rule; the store is contiguous 0-29 and its newest real exchange is dated 2026-09-02, so none of Duc's conversations are missing. The duplicate adds of 30 and 31 are still the defect's real fingerprint - one of those verification turns streamed a reply to the browser, raised nothing and left no record, which is what started this investigation.
- Memory embedding migration (one-time, already run): `python3 scripts/migrate_memory_embeddings.py` — re-embeds `data/memory_db` under the BGE embedding function. Safe/idempotent to rerun; only does anything if the collection is non-empty.
- **Local LLM choice**: `LocalLLM`'s default is `Qwen2.5-14B-Instruct-4bit` (`llm.py::DEFAULT_LOCAL_MODEL`) — picked from `docs/model-benchmark.md`, not guessed. It's within 0.1 of the benchmark's best local model (Qwen2.5-32B) at more than 2x the tokens/sec, which matters more for voice since replies get read out loud. Local LLM weights live in `data/local_llm_models/` (its own `HF_HOME`, set in `llm.py`) — separate from `scratchpad/bench/`'s throwaway benchmark cache, which is safe to delete anytime and won't break this.
- **Memory embedding is BGE, not Chroma's default** — `memory.py::bge_embedding_function()` (`BAAI/bge-small-en-v1.5`, normalized). Chroma's built-in default is *already* MiniLM-L6 (with a 256-token truncation cap) - swapping to that would have been a no-op improvement, so don't "fix" this back to MiniLM thinking it's an upgrade. `ChromaMemoryStore` also blends in recency (`RECENCY_WEIGHT`/`RECENCY_HALFLIFE_HOURS` class attrs) since casual chat leans on "what we just talked about." **Changing the embedding function again needs `scripts/migrate_memory_embeddings.py` rerun** - old vectors don't get retroactively re-embedded, so a silent swap degrades retrieval on everything stored before the change instead of improving it.
- **`AnthropicLLM.respond()` had the same silent-truncation gap `respond_with_tools()` was already fixed for, just never patched** - caught for real when the job-draft web endpoint's critique pass cut a cover letter off mid-word at the old 1500-token budget. `respond()` now checks `stop_reason == "max_tokens"` and appends an explicit `[cut off - ran out of room...]` marker instead of silently returning partial text that reads as complete. This applies to every `respond()` caller, not just job drafting - plain chat at the default 500-token budget could hit this on a long explanation too. The job-draft backend's budget was also bumped 1500 → 2500 (both `default_tools.py` and `webapp.py`) since a style-matched cover letter draft-plus-critique can run long.
- **Tool-calling needs a bigger `max_tokens` budget than plain chat, and this bit us once already**: `AnthropicLLM` has a separate `tool_max_tokens` (2000, vs. 500 for plain `respond()`). Sonnet 5 runs adaptive thinking by default, and thinking tokens count against `max_tokens` - deciding which tool to call burns real budget before any tool_use or text block gets emitted. With the old shared 500-token budget, a real turn got cut off `stop_reason: "max_tokens"` mid-*thinking*, before reaching the tool call, and silently returned an empty reply. `respond_with_tools()` now treats `stop_reason == "max_tokens"` as a real failure (returns an explicit "ran out of room" message) rather than returning whatever `extract_text()` finds (which can legitimately be empty). Don't shrink `tool_max_tokens` back down without re-testing a real tool-calling turn.
- **Memory is two separate layers on purpose, not one system doing two jobs** (`memory.py`'s `ChromaMemoryStore` vs. `memory_notes.py`'s `MarkdownMemoryNotesStore`). Chroma logs every exchange automatically and retrieves the top-k *semantically similar* ones per turn - good for "what did we just talk about," but a durable fact (a preference, who someone is) can be relevant on an off-topic turn where it's not semantically similar to anything, and top-k retrieval just misses it. Memory Notes is the fix: a small set of facts Claude itself chooses to save (`save_memory_note` tool, never automatic) as dated Markdown bullets in `data/memory_notes/<category>.md`, loaded **in full, every turn** into the system prompt (`ConversationManager._build_system()`) - no query, no top-k, because the set is meant to stay small and curated. Inspired by Mem0's split between curated memory and raw logs, and by the GBrain/Sylph/DIY-Claude-git-markdown pattern Duc researched - human-readable, git-diffable, no vendor lock-in. Temporal handling is deliberately simplified vs. something like Zep/Graphiti's point-in-time graph: append-only dated lines, "most recent wins" is a reading convention, not code that resolves contradictions - documented in the module docstring so nobody "fixes" it into silently dropping history. If `ConversationManager` is constructed without a `memory_notes=` arg it builds its own `MarkdownMemoryNotesStore()`, same pattern as `default_tools.py`'s `draft_backend` - no call-site changes needed at the three front doors.
- **Streaming was already happening and being thrown away (2026-09-07)** - `AnthropicLLM.respond()` iterated `messages.stream()` for the SDK's ten-minute rule and only kept the final message. `on_token` now threads through `respond()` → `ConversationManager.handle_turn()` → `route_and_answer_verbose()`, guarded by `LLMBackend.supports_streaming` so the local MLX backend never receives an argument it rejects, and tool turns yield only `done`. Measured on a real Claude turn: first token at 5.3 s of 7.1 s - adaptive thinking precedes the first text delta, so streaming shortens the visible tail rather than the wait; don't sell it as sub-second. The message goes by POST so it never lands in the uvicorn access log. Research behind both this and the presence-state work is in `docs/plans/2026-09-07-human-interface.md`: a companion's first job is to show its state (idle/listening/thinking/speaking/interrupted/failed), cancellation is core logic, and spoken replies need a different register from written ones.
- **`AnthropicLLM.respond()` streams because the resume budget crossed the SDK's non-streaming cap (2026-09-07)** - the 32000 raise above never ran: the Anthropic SDK computes an expected duration from `max_tokens` and refuses a plain `messages.create()` above roughly 21k tokens with `ValueError: Streaming is required for operations that may take longer than 10 minutes`. The failing calls were real (input ~10k tokens, output hit the full 16000 budget with `stop_reason=max_tokens`, content blocks `['thinking', 'text']` - adaptive thinking ate the budget before the document finished), so the ceiling had to go up, and going up meant streaming. `respond()` now uses `messages.stream()` + `get_final_message()`, which returns the same message object `create()` did - the `stop_reason == "max_tokens"` check, `TRUNCATION_MARKER` and `extract_text` are unchanged, and no caller notices. `_resume_llm` is at 40000 (a ceiling, not a reservation; the largest real reply so far was ~13.8k output tokens), and the worker shares it by importing `HANDLERS` from `webapp`. `respond_with_tools()` still calls `create()` - its 2000-token budget is far below the cap, and its loop was left alone on purpose. `tests/test_llm.py` pins both halves with a fake client: `respond()` must go through `stream()` and never `create()`, and the marker must still land on `max_tokens`.
- **`ConversationManager._build_system()` includes the current local date/time, and this was a real, user-visible bug before it did**: a reminder tool call landed a due date over a year in the past because nothing ever told the model what day "today" is - "tomorrow morning" is meaningless without it. Local time (`datetime.now().astimezone()`), not UTC, so "tomorrow" means Duc's tomorrow. This affects every turn, not just tool calls - don't remove it to save a few tokens.
