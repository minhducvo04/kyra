# Plan: the CONSOLE, one place for every tool and every agent (2026-09-13)

Goal: Duc asked for "a nice interface to centralize the tools and agents". Today the HUD has four
slide-in panels (JOBS, TOOLS, SEARCH, FOCUS) that expose some tools through hand-built forms, while
the rest of the registry is reachable only by asking Kyra in chat, the two coding agents' hand-off
threads are readable only with `scripts/session_log.py`, and what Kyra actually ran (tool calls,
background jobs) is visible nowhere. The CONSOLE is a fifth panel with three tabs that closes those
three gaps without moving anything that already works:

- **TOOLS**: the whole `default_tool_registry()`, listed from the registry itself, each with a
  generated run form and, where a dedicated UI already exists, a link that opens that panel.
- **AGENTS**: every hand-off thread under `data/sessions/`, newest first, with who wrote last, what it
  is open for, and what comes next; the repo's branch and tree state beside it.
- **RUNS**: what Kyra did, as a list: every tool run (chat, voice, digest, console) and every
  background job, with status and time.

Background: `docs/plans/Kyra_Project_Conversation_Handoff.docx` (on disk only, gitignored by
extension). Its "Memory and workflow system" section asks for approval before external action, an
audit event per action, and a small number of clear actions that hide the plumbing. This plan takes
the two pieces that fit the existing HUD (a confirmation gate and a tool-run audit) and leaves the
rest (workflow versions, approval queue, OpenClaw, cloud, Vision Pro, audio) for later plans. The
father's system is a separate product with separate data and is not touched here.

## Assumptions (state them, then build)

1. "Agents" means the two coding agents (Claude Code, Codex) and Kyra's own tool-calling loop, as
   the repo already models them: hand-off threads in `data/sessions/`, `ToolRegistry`, `JobQueue`.
   Not the father's assistant, not OpenClaw.
2. The CONSOLE sits beside the existing panels rather than replacing them. Every tool that already
   has a form (reminders, learning, tracker, outreach, autofill, memory, focus, search, initiatives,
   news, science) keeps it; the CONSOLE links to it. Folding the old TOOLS grab-bag into the CONSOLE
   is a later cleanup once the CONSOLE has been used for a week.
3. The AGENTS tab is read-only in this slice. Hand-off blocks are written by the agents with
   `session_log.py --write`, which records git facts the browser cannot vouch for.
4. Same privacy line as every `/api/*` route: loopback is open, the LAN needs `KYRA_API_TOKEN`.
   Thread text and tool arguments live under `data/` and never reach a tracked file. `GET /api/jobs`
   returns status and timestamps, never the payload (a draft job's payload carries resume text).
5. No new dependency, no markdown renderer: thread text is shown with `textContent` in a `<pre>`,
   the rule every other panel follows.

## Two hard constraints, in code not prose

- **A tool that leaves the machine, spends model tokens, or opens a browser is never run from a
  button without confirmation.** `Tool.needs_confirmation` (class attribute, default False, next to
  `terminal`). `POST /api/tools/{name}/run` refuses with 409 `confirmation_required` unless the body
  says `confirmed: true`. The browser asks with a confirm dialog; the server is the guard.
  Pinned by test for: `autofill_job_application`, `draft_application_material`,
  `draft_outreach_note`, `copy_outreach_note`, `suggest_initiatives`. Codex applies the same rule
  to any other tool that fits it and says which in the hand-off.
- **Every tool run is recorded, whoever asked for it.** `ToolRegistry.run()` records to a
  `ToolRunStore` when one is attached; `default_tool_registry()` attaches one, so chat, voice, the
  digest and the console all land in the same `data/tool_runs.db`. A failed record never fails the
  tool (log a warning). Arguments are stored as JSON; the result is summarised to 300 characters.

## Contracts (what the red tests pin)

Backend, `src/companion/`:

- `tools.py`: `Tool.needs_confirmation = False`; `ToolRegistry(tools, audit: ToolRunStore | None = None)`;
  `run()` records `tool, args, ok, summary, error, duration_ms`.
- `tool_runs.py` (new): `ToolRun` dataclass (`id, tool, args, ok, summary, error, started_at,
  duration_ms`); `ToolRunStore(engine=None)` over `engine_for_store(DATA_DIR / "tool_runs.db")`
  with `record(...) -> int` and `list(limit=50)` newest first. Table `tool_runs` in `schema.py`
  plus an Alembic revision. Lazy: nothing heavy at import.
- `jobs.py`: `JobQueue.list(limit=20) -> list[Job]` on the ABC and `DbJobQueue`, newest first.
- `session_log.py`: `summarize(text) -> dict` reads the last block: `agent, stamp, open_for, next,
  suggested`; `threads()` is unchanged.
- `webapp.py`:
  - `GET /api/tools` -> `{"tools": [{name, description, input_schema, needs_confirmation, group,
    panel}]}`. `group` is the tool's module name (`reminders`, `outreach`, ...). `panel` is
    `"<panel>/<tab>"` from a `CONSOLE_PANELS` dict in `webapp.py` (for example `add_reminder` ->
    `tools/reminders`, `add_job_application` -> `jobs/tracker`) or null.
  - `POST /api/tools/{name}/run` body `{"input": {}, "confirmed": false}` ->
    `{"tool", "result", "run_id"}`. 404 `unknown_tool`; 409 `confirmation_required` (details
    `{"tool": name}`); 400 `tool_input_invalid` when the tool rejects the kwargs (`TypeError`);
    400 `tool_error` when the tool returns `{"error": ...}` (the `_outreach` convention: a model
    reads an error dict, an HTTP client reads a status).
  - `GET /api/tools/runs?limit=50` -> `{"runs": [ToolRun...]}`.
  - `GET /api/jobs?limit=20` -> `{"jobs": [{id, kind, status, created_at, started_at,
    finished_at, error}]}`. No payload, no result.
  - `GET /api/agents` -> `{"repo": {branch, head, subject, tree}, "threads": [{slug, modified,
    agent, stamp, open_for, next, suggested}]}` newest first.
  - `GET /api/agents/{slug}` -> `{"slug", "text"}`; 404 `not_found`. The slug is passed through
    `session_log.slug()` so no name can reach outside `data/sessions/`.

Front end, `web/`:

- Header gets one toggle, `CONSOLE` (`#console-toggle`), first in the row. Panel `#console-panel`
  reuses `.jobs-panel`, `.jobs-tab`, `.jobs-btn`; tabs `data-console-tab` = `tools | agents |
  runs`, panels `data-console-tab-panel`. Escape closes it like the others.
- TOOLS tab: rows grouped by `group`; each row shows name, description, an OPEN button when
  `panel` is set (opens that panel and selects that tab), and a RUN button that expands a form
  generated from `input_schema` (string -> input, or textarea when the description says "text" or
  the name ends in `_text`/`_notes`; integer/number -> number; boolean -> checkbox; enum -> select;
  required fields marked). Submit posts to `/api/tools/{name}/run`; the result is pretty JSON in a
  `<pre>` via `textContent`; an error shows the server's message through `readJson`. A tool with
  `needs_confirmation` asks with `confirm()` first and sends `confirmed: true`.
- AGENTS tab: a repo line (branch, head, tree state), then one card per thread: slug, last agent
  and stamp, an "Open for" badge coloured by value (`duc` amber, `build`/`tests`/`review`/
  `critique` cyan, `nothing` grey), Next, Suggested. Clicking a card loads `/api/agents/{slug}` into
  a `<pre>`. REFRESH button.
- RUNS tab: recent tool runs (time, tool, OK/ERROR, summary) above background jobs (id, kind,
  status, created, finished). Loads when the tab opens; REFRESH button; no polling.
- Phone: at 375 px wide, `document.documentElement.scrollWidth === clientWidth`; buttons keep the
  44 px minimum height the Suggestions tab set.
