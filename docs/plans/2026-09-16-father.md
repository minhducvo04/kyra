# Plan: Father's assistant, first two slices on synthetic data (2026-09-16)

Goal: the seams that make Father's system a separate tenant, and the deterministic document check that
owns every outbound file. Nothing here touches real Father content, opens a provider account, or deploys.
Restrictions come from `docs/plans/Kyra_Project_Conversation_Handoff.docx` (on disk only). Fixtures use
Alex Rivera at Northwind.

## Restrictions, as code (F01)

- `Settings.tenant` (`KYRA_TENANT`), `personal` by default or `father`. A `father` tenant refuses to
  start when `KYRA_DATA_DIR` is unset or resolves inside the personal `data/` directory.
- `companion.tenant.policy(settings)`: for `father`, min tier `work`, no training, no local models, no
  router, direct providers only (`anthropic`, `openai`). `refuse_training(settings)` raises for `father`;
  `scripts/router_ft.py` and `scripts/tool_ft.py` call it before anything else.
- Personal behaviour is unchanged: same defaults, same tests.

## Deterministic document QA (F02)

`companion.doc_qa.inspect_docx(path, *, facts, allowed_authors, renderer) -> Report`. Scans body, headers,
footers, comments and `docProps`. Finding kinds: `dash`, `provider_name`, `placeholder`, `metadata`,
`fact_missing`, `truncation`. Rendering goes through a `Renderer` ABC (`render(path, out_dir) -> pages`);
the real ones drive Word on this Mac or `pdftoppm` on a PDF, and are verified by a real run, not a test.
`Report.ok` is true only with zero findings and at least one rendered page; a renderer that cannot run
is a recorded `render_error`, never silence.

## F03: task cards on synthetic data (added 2026-09-16, after F01 landed)

What Father sees is five things: Start a task, In progress, Review, Approve or Request changes, History.
Everything else (provider, prompt, file conversion, metadata cleanup) stays behind those. This slice has
no model call at all: the document comes from an approved workflow version plus a facts table through a
deterministic python-docx builder, then F02's `inspect_docx`. The model drafting stage arrives in F04 with
the approved provider and its dated terms record, and slots in between "facts" and "builder".

Shapes (`companion/father.py`):
- `WorkflowVersion(slug, version, title, template_path, required_facts, approved_at)`; workflows are JSON
  files under `<father data>/workflows/<slug>/v<N>.json`; `active(slug)` is the highest approved version.
  A new version is a new file; nothing edits an approved one.
- `FatherTaskStore` (SQLite `father.db`): `tasks(id, slug, version, status, facts_json, document_path,
  report_json, note, created_at, decided_at)`; statuses `review | approved | changes_requested`.
- `start_task(slug, facts) -> Task`: builds the DOCX, runs `inspect_docx` with the configured renderer,
  stores the report, status `review`.
- `decide(task_id, decision, note)`: `approve` refused while the report has a `dash`, `provider_name`,
  `fact_missing` or `truncation` finding, or a `render_error`; the refusal names the findings. Approval
  never sends anything; delivery is a later slice with its own gate.
- Routes `/father` and `/api/father/*` answer only when `settings.tenant == "father"`; 404 otherwise, so the
  personal HUD never grows a Father page by accident.

Steps: 5. Red tests `tests/test_father.py` (Claude) -> verify: red. 6. Build (Codex) -> verify: green; real run
under `KYRA_TENANT=father KYRA_DATA_DIR=<external scratch>` with the Northwind fixture workflow: a task with
a missing fact cannot be approved, the same task with the fact present can; screenshots of the five states.
